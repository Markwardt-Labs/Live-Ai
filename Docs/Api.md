# API

The public API has one entry point, `IPromptProvider`, which creates, loads, deletes and tests the sessions of one command line tool (and hands out the `IPromptSession`s), and reads the tool's subscription limits. A `PromptProvider` is made over an `IPromptEngine`, the side that knows how to start and read a tool, and an `IPromptModelCatalog` lists the models a tool can run. This document covers the *design and flow* of that surface: how the pieces fit together and the order things happen in. It does not restate member-level detail already covered in the source itself.

## Shape

A caller builds a `PromptProvider` from an engine (`ClaudeEngine`, `CodexEngine`, or `OpenCodeEngine` for models that run on this machine or on any server OpenCode can reach) and a data folder (where sessions are stored; `null` is `Markwardt.LiveAi` in the local application data folder). The models a tool can run come from `IPromptProvider.GetModels` (each a `PromptModel` with what it can do and the `PromptModelSetting`s it offers), and a session runs one of them once it is chosen; the library has no vocabulary of its own for model tiers or reasoning levels, so an application can list and show whatever each model offers. Providers over the same data folder share their storage, so one can load what another created, as long as they run the same tool.

`Create` takes only what cannot change afterwards: an optional API key (none means the subscription already configured in the tool) and an optional workspace path. The tool and where it is found belong to the provider's engine (`new ClaudeEngine(command, configFolder)`, `new CodexEngine(...)`, or a custom one, see Custom engines). The model is given in the options or set like every other setting, through `Configuration`, before the first prompt (a session without a model throws `PromptSessionModelException` from every call that needs the tool), and the values of its settings start at their defaults. `Load` takes the identifier and the API key again (a secret does not belong in an app data file, so it is never stored; where the tool and its state are is the provider's, and is not stored either). A provider only loads and deletes the sessions of its own tool: the name of the engine is stored with a session, and a session of another one is refused with an `ArgumentException`. Only the link to the conversation and the model with the values of its settings are stored, so a loaded session continues the same conversation on its model (brought up to date with what the tool offers now, and without one if the tool no longer offers it) but starts with the defaults of everything else, and the caller sets the ones it wants through `Configuration` before the next prompt, the same way it did after `Create`.

The library has its own identifier per session (`IPromptSession.Id`, a GUID in text form without hyphens), separate from the provider's session identifier: it is generated before the provider has seen the session, it is the same for both providers, and it is what a caller keeps. The link to the provider's own session is the library's concern and is not exposed: the library records it once the provider reports it, and callers only ever hold the library identifier. That link (the identifier, the provider, the working folder and the provider's session identifier) and the model with its settings are all the library stores; no other setting is.

A session reports its provider as a property of its own, and its model and the values of its settings (with the rest of what can be changed) through `Configuration`. The API key is not reported anywhere, because a secret should not travel back out.

What can be changed on a live session is one type, `IPromptSessionConfiguration`, which `IPromptSession.Configuration` returns: the model and its settings, persistence, the shell switch, the hooks that see the calls of the library's tools (`BeforeToolCall`, `AfterToolCall`), instructions, external MCP servers, the limits (`Limits`, one `PromptSessionLimits` record: the budget, `Timeout`, `WindowLimit`, `Retry` and `MaxToolCalls`), the workspace, tools and mounts. They are ordinary settable properties and collections, changed at any time. Nothing takes effect when one is set: the session takes all of them together when the next prompt starts, which is the point of making them lazy, since however many a caller changes the session decides once what it needs (rebuild the file tools, end a process that was started with other settings or is no longer to be kept alive; the model and its settings are not among those, a running process takes them with the prompt, except for OpenCode, which takes them when it starts), so there is at most one restart. A value that is not allowed (a model setting the model does not offer or does not accept, a tool name or a mount path that is not allowed or is taken, an MCP server that is neither a command nor an http address, a limit that is not positive) throws where it is assigned and changes nothing, and after the session is disposed every change throws `ObjectDisposedException`. A running prompt keeps the settings it started with. The provider and the identifier cannot be changed: a provider's sessions live in that tool's own storage, so changing either would not continue the conversation.

A session is a conversation, not a process: nothing runs between prompts unless a persistent process or the tool server is wanted, which are what disposing it ends. It is both `IDisposable` and `IAsyncDisposable`, with the two forms described under the persistent process.

## Flow

1. `IPromptProvider.Create` generates the GUID, makes the empty folder the tools run in (which the AI cannot reach), or uses the workspace path when one is given (an existing folder, which also becomes the session's `Workspace` with the `sandbox` argument, and is set again by every `Load`), stores the link and returns the session. The provider's own session does not exist yet.
2. `session.Request(input, options)` sends a prompt, waits for the end and returns the answer as a string (the messages joined; with a schema, the answer alone). What happens while it runs (see Events) is on `Output` as it happens. `Request<T>(input, options)` is an extension method that reads a typed answer. Everything about one prompt is one optional `PromptRequestOptions` record. A failure of the tool or of the AI surfaces as `PromptSessionException`, after the messages that came before it.
3. The first answered prompt makes the provider report its own session; the library stores the link. Every later prompt resumes that session, so the AI keeps its context.
4. `IPromptProvider.Load(id)` rebuilds the session from its stored link, in this process or another, with the default settings, and continues from step 2. If the provider's session is gone, `Load` fails with `PromptSessionNotFoundException` and keeps the stored session, since the cause can be a provider pointed at another configuration folder.

## Changing settings

A change to the configuration changes the session in memory only, and none of it is stored: the settings are set again whenever a session is created or loaded. The change applies from the next prompt (a prompt already running keeps the settings it started with). An undefined enum value throws `ArgumentOutOfRangeException` from the setter. A process that is kept alive and is no longer wanted (persistence turned off, or a setting it was started with changed) is ended in the background once its prompt is done, without waiting for the next prompt.

## Deleting sessions

`IPromptProvider.List()` returns what is stored for the provider's tool, newest first, as `PromptSessionInfo` (the identifier, when it was created where known, the workspace path, and whether the tool's conversation has started), so a caller does not have to keep the identifiers itself; sessions of another tool and links that cannot be read are left out. Only the link is stored, so the list says nothing about the settings or the conversation. `IPromptProvider.Delete(id)` removes a session for good: the stored link, the provider's own conversation (with the folders the tool leaves empty) and the empty folder made for the tool to run in, only when it is a folder the library made. It returns whether the session existed, and fails without deleting the link when the conversation cannot be removed, so it can be tried again. An open session must be disposed first, and the folders mounted to a session are never touched.

## Automatic, and limited by what is offered

The AI never asks for permission to do anything: it can use every tool it is offered. What it can change is decided by the workspace, what is mounted and which tools are configured, and the library enforces it in its own code for both providers. To let it read a folder but not change it, give or mount the store with `AsReadOnly()`; the writing file tools are still offered, but a write to that folder is refused with a message that says it is read-only. There is no session-wide switch for this, because a per-store wrapper says the same thing at the point where the access is, and a second, global switch only duplicated it.

## File tools

The AI works on files only through the library's own file tools, and unless the shell is enabled (see Shell) has no shell and no other way to the machine. What its paths mean is the session's `Workspace` and `Mounts`. The `Workspace` is an `IStore` (null by default) that is the AI's current working directory: a relative path it gives a tool is relative to it, like in a shell. `Mounts` is a dictionary from a relative path to an `IStore`, added to and removed from one at a time: a path that starts with a mount's path (names separated by `/`, such as `docs` or `my/test`; the longest that does) is inside that store, with the path of the mount taken off, so with a store mounted at `my/test` the path `my/test/thing/file.txt` is the file `thing/file.txt` of that store, wherever the workspace has files, and what the workspace has at that place is hidden by the mount. The tools (list, find, search, read, write, edit, copy, move, delete) work the same on all of it, so one session can work on a project folder as its workspace, a reference folder and a database mounted beside it, and copy or move between them. A mounted folder itself cannot be deleted, renamed, moved, overwritten or be the target of a move, however its path is spelled (`docs`, `docs/`, `docs/.`, `x/../docs`), and neither can a folder of the workspace that has a mount inside it. Listing the top shows the workspace's entries together with the first part of each mount path. A path that is absolute, or climbs above the workspace, is the workspace's own business: a store of a folder on disk made with `IStore.FromDisk(path)` takes an absolute path that lands inside its folder as another spelling of the relative one and refuses the rest, and `IStore.FromDisk(path, sandbox: false)` takes any path of the machine, absolute or relative; a store that is not on disk refuses paths that leave it. A session with neither a workspace nor mounts has no access to files at all: it is a conversation, with whatever tools the caller adds, and the AI is told so.

An `IStore` is five operations (list, open, create folder, delete, move). `Open(path, mode)` returns a stream of bytes, so any file can be handled, and the `StoreOpenMode` decides what it is: `Read` (an existing file, read only), `Open` (an existing file, read and write, content kept), `Create` (a new file; fails if anything is there), `Replace` (write, discarding what was there, making the file if missing) or `Append` (write at the end, making the file if missing). `ReadText` and `WriteText` are extension methods that read and write a file as UTF-8 text. `IStore.FromDisk(path, sandbox)` makes one for a folder on disk, which by default is confined to it (a path that leads outside, absolute or relative and also through a link, is refused) and with `sandbox: false` is only where relative paths start (and `IDiskStore.Path` and `IsSandboxed` reveal how it was made); `IStore.FromMemory()` makes an empty one that keeps files and folders in memory, for documents that are not on disk (write them with `WriteText`) or for a place to put what the AI makes (read it back with `List`, `Open` and `ReadText`); `IStore.FromZip(path)` (or `FromZip(stream)`) makes one from a zip archive, read into memory and written back only when `Save()` is called (`Save(stream)` exports it); a caller implements the interface for documents in a database or a remote store. The tools are built over it once (numbered reading with line limits, glob and regular expression search, exact-match edits with an optional replace-all), so a store only has to implement the five operations; `List` can list everything below a folder (`recursive`; an entry carries its path relative to the listed folder). `IsFolder`, `GetSize` (a folder's size is the sum over everything in it) and `Copy` are members of `IStore` with default implementations built from the five, so a store that can do better (a file system, a database) implements them and one that cannot gets them for free. `ListFiles` and `ListFolders` are extension methods that return the relative paths, as strings, of only the files or only the folders, also recursive. Copying and moving a folder takes everything in it, empty folders included, and a move between two stores the library knows how to move between (two disks, two memory stores) relocates instead of copying. `AsReadOnly()` on a store lets the AI read it but not change it, so a session can have, for example, a writable project folder and a read-only reference folder. `Audited(sink)` reports every access (listing, opening to read or to change, making folders, deleting, moving, copying) to a function after it has been made, with the error if it failed, for a log of what the AI did; it neither limits nor changes anything. `AsOverlay()` puts changes on top of a store in memory (an `IOverlayStore`): what the AI writes, deletes and moves stays in the overlay, `GetChanges()` lists what would change underneath (added, modified and deleted, a deleted folder as one change), and `Apply()` makes the store underneath what the overlay shows, or `Discard()` throws the changes away, so the AI can work freely on a folder, a zip or a database and the caller decides afterwards. `IStore.FromDisk` returns an `IDiskStore`, which reveals its `Path`; that is what lets a session store the mounts that are folders on disk (also `AsReadOnly` ones, with that flag) by their path and mount them again on `Load`. A folder that no longer exists is left out, and the mounts that are not folders on disk, such as memory or a database, cannot be stored, so the caller mounts those again.

The cost of no shell is that the AI cannot build, test or run git. A caller who wants only some commands adds a tool of their own that runs the commands they allow (see Tools), which keeps the decision of what may run with the caller; one who trusts the AI with everything enables the shell. The library tools' names (the file tools and `shell`) are taken; a caller's tool cannot use them. The user's own MCP servers and connectors in the Claude Code configuration are not available to the session, so a session sees only the tools the library gives it.

## Tools

The `Tools` of the configuration (a list, empty by default) holds functions of the caller's that the AI can call while it works. It holds only those: the library's own file tools are not in it, they are built and served in the background whenever something is mounted. A tool is a `PromptTool`: a name, a description (all the AI knows about it besides its input), a JSON Schema for its input, and a handler from the arguments to a text result. `PromptTool.Create<TInput, TOutput>` builds one from typed code the same way structured output does: the schema comes from `TInput` (an object), the arguments are read into it, and the output is written as JSON text (a string goes back as it is). The AI sees tool calls as ordinary tool use and the calls run in the caller's process, so a handler can use anything the caller has.

The library's own tools (the file tools, `shell`, `ask_user`, `view_image`, `fetch_url`, `search_web`, `generate_image`, `current_time`, `tool_search`, `delegate`, `diff_files` and `respond`) have reserved names that a caller's tool cannot take, compared without regard to case, so a caller's tool never replaces or hides one of them; the session also refuses to start a prompt if two offered tools would share a name. The `Asker` of the configuration (null by default) is a function from a question to the reply, `Func<string, CancellationToken, Task<string>>`: while it is set the AI is offered an `ask_user` tool that takes a `question`, calls the function with it, waits as long as it takes, and gives the AI the text it returns (null counts as empty). It is the way for the AI to ask the user something in the middle of its work, and the way to show it is up to the caller (a prompt in a console, a dialog, a chat message). Without a function the tool is not offered at all, so the AI does not know it could ask. The function is read when a prompt starts, to decide whether to offer the tool, and when the tool is called; setting or clearing it restarts a persistent process, like a change to `Tools`. The waiting counts toward the timeout of the request, a function that throws gives the AI an error result it can react to, and the call goes through the tool hooks like any other. A change to `Tools` applies from the next prompt; a persistent process restarts when the offered tools change. Names are 1 to 64 letters, digits, underscores and hyphens and unique, or adding it throws `ArgumentException` and changes nothing. A handler that throws does not fail the prompt: the AI is given the exception message as an error result and can react. A handler may be called from several threads at once, since the AI can call tools in parallel.

The library cannot know what a handler does, so which tools a session has is the caller's decision, made by what it configures. The arguments given to a handler are only valid for the call.

Offering tools holds a local port, so dispose the session when done.

## Shell

`EnableImages` and `EnableWeb` (both off by default, and not kept with a loaded session) give the AI `view_image`, which shows it a PNG, JPEG, GIF or WebP file of the workspace or a mount, and `fetch_url`, which reads text from an http or https address as this machine, unless `WebFilter` (a function from the address of every request, redirects included, to `true` to block it; `null` allows all) blocks it; the first is offered only while there are files, the model takes images and the engine can be shown them.

`EnableSearch` (off by default, not kept with a loaded session) lets the AI search the web: with the tool's own search where the engine has one (`IPromptEngine.NativeSearch`, true for Claude Code and Codex), which is allowed when the tool starts and is outside the hooks and `WebFilter`, and otherwise with the library's `search_web`, a rate limited best-effort reader of DuckDuckGo's HTML page that is outside `WebFilter` too. Every session is also offered `current_time`, `tool_search`, `delegate` (a task in a helper session, without or with the conversation so far, whose usage is added to the session's) and, with the file tools, `diff_files`; there is no switch for them.

`ImageGenerator` (null by default, not kept with a loaded session) is an `IPromptImageGenerator` that makes the images the AI asks for: while one is set and the session has files to save in, the AI is offered `generate_image`, whose arguments follow what the generator supports (`PromptImageFeatures`: transparency, a negative prompt, a seed). The library makes two, `IPromptImageGenerator.OpenAi` (the OpenAI image API, or a server that copies it; `IPromptImageGenerator.OpenAiModels` lists its image models, each a `PromptImageModel` with its features) and `IPromptImageGenerator.StableDiffusion` (an AUTOMATIC1111 or Forge server; `StableDiffusionModels` lists its checkpoints); anything else implements the interface.

`EnableShell` in the configuration (off by default, so a loaded session has it off until it is set again) gives the AI one more library tool, `shell`, which runs any command on the machine through `/bin/sh -c` (`cmd /c` on Windows), as the user the host process runs as, and returns the output (standard output and standard error together) with the exit code. It is the one tool that is not confined by anything else the library offers: mounts, read-only stores and the confinement of the file tools say nothing about what a command can reach, so it is meant for an AI and a task that deserve that trust (a command also sees the host's environment variables, and anything else the host process can reach), and it is a separate switch so that nothing else can enable it by accident. Which commands may run is decided with the tool call hooks (see Tool call hooks), where the command is the `command` argument of the `shell` call. Commands start in the workspace when it is a folder on disk and otherwise in the session's empty scratch folder, unless the AI gives a `working_directory`; standard input is empty so a command that waits for input ends; a command is stopped after `timeout_seconds` (120 by default, at most 3600) or when the prompt is cancelled, with everything it started; and very long output is cut at 64 KB. Like the file tools it is served in the background and is not listed in `Tools`, and the AI is told it has a shell.

## Tool call hooks

`BeforeToolCall` and `AfterToolCall` in the configuration (null by default) see every call of a tool the library offers the AI: the shell, the file tools and the tools in `Tools`. `BeforeToolCall` is a function from the `PromptToolCallEvent` of the call (the same record `Output` reports: its server, the tool, `Input` as JSON text and `Arguments` as a parsed object) to a `PromptToolDecision`: `PromptToolDecision.Allow` lets it run, `PromptToolDecision.Deny("reason")` refuses it, and so does throwing. A refused call does not run, and the AI is told that it was not allowed, with the reason, and not to get around that, so it can report it or choose another way. `AfterToolCall` is given the call, the `PromptToolResultEvent` (the text the AI was given back and whether the call failed) and how long the tool took once it has run, whether it worked or the tool threw; a refused call is not reported, and nothing the function throws reaches the AI. The `Id` of the two events is the one the AI tool gave the call where it says (Claude Code does, so it matches the events on `Output`), and otherwise the id of the request to the library's tool server, so a before and an after always match each other. Both are read when a call arrives, so they can be changed while a prompt runs, and neither is stored, so a loaded session has none until they are set. They do not see the tools of external MCP servers, which the AI's tool calls itself.

```csharp
session.Configuration.BeforeToolCall = (call, _) => Task.FromResult(
    call.Name == "shell" && !call.Arguments.GetProperty("command").GetString()!.StartsWith("dotnet test")
        ? PromptToolDecision.Deny("only dotnet test may run")
        : PromptToolDecision.Allow);
```

## Attachments

A prompt can come with files: `PromptOptions.Attachments` (of a request or of `Send`) takes `PromptAttachment`s, a name, a media type and the bytes; `PromptAttachment.FromFile` and `IStore.ReadAttachment` make them with the media type taken from the extension, reading the file when they are called. What happens to a file depends on its type: images (PNG, JPEG, GIF, WebP) are shown to the AI, with both providers; PDF documents are shown to the AI with Claude Code; text files (`text/*`, JSON, XML, YAML) are put into the prompt as text, in a code fence, after the prompt, with both providers; anything else is refused with `NotSupportedException` before anything is started, with a message that says to mount the file and let the AI read it with the file tools. Because text files are folded into the prompt, a prompt with only text files starts the ordinary process, and only images and PDFs change how the tool is started. The files are part of that one prompt: the provider keeps them in the conversation, so the AI can still refer to an image in a later prompt, but the library stores nothing of them, and a loop sends its files again with every send. Limits keep a prompt reasonable: 20 attachments, 20 MB each and 30 MB together, and 256 KB for a text file (a larger one is better mounted, where the AI can read it in parts); a text file that is not valid UTF-8 is refused instead of being sent as garbage.

## Structured input and output

The reflection-based entry points, `Request<TOutput>`, `Loop<TOutput>` and `PromptTool.Create<TInput, TOutput>`, are marked `[RequiresUnreferencedCode]` and `[RequiresDynamicCode]`: they build schemas and read JSON through reflection, so in a trimmed or native AOT application they need the members of their types kept (a non-string object given as the input of any request is written the same way). The library is not otherwise annotated, and there are no `JsonTypeInfo` overloads.

`Request<TOutput>` makes the AI answer with a `TOutput`: the library builds the JSON Schema of the type, the tool is made to answer under that schema, and the answer is read back into the type. An object goes in as the input of any of the calls, which writes it as JSON (with its own runtime type, when the call is made), and a prompt that is only that JSON has no sentence around it, so the object should carry its own instruction (a `Task` property, say). `Request` returns plain text (the messages joined; with a schema set, only the answer), `Request<T>` is an extension method that sets the schema of the type in the options and reads the answer back, and the `Schema` option takes a hand-written schema for any call (loops included; `Request` then returns the answer as JSON text). With a schema the last message is the answer as JSON text; the earlier messages are the AI's progress notes as usual.

A property that may hold any value (a `JsonElement`) is written as an empty schema and not as `true`, because strict tool parsers such as Ollama's refuse a boolean in place of a schema. Types are written with fixed options, so the shape of an input or answer is controlled with attributes on the type (`[JsonPropertyName]`, `[JsonConverter]` and so on); there is no serializer options argument, to keep the API small. The options are camel case, enums as their names, numbers only as JSON numbers, and required constructor parameters and non-nullable annotations enforced, so an answer that leaves out a required value is an error instead of a default. Both tools require an object at the root of the schema, so an output type that is not written as an object (a string, a number, an enumeration, a list or array) is asked for in an object with one required property, `value`, and unwrapped again: `Request<bool>("Is this safe?")` and `Request<string[]>("List the files.")` work, and the AI sees the wrapper only in the schema. Everything else is as for an object type, including the `PromptSessionOutputException` when the answer does not fit. Optional properties work, but Codex requires every property to be present, so for Codex they are made required and an optional value should be nullable. Free-form dictionaries are not supported by Codex's schema rules, and a type that uses one fails as a `PromptSessionException` from the tool.

An answer that is missing, not JSON, or not a `TOutput` throws `PromptSessionOutputException`, which carries the raw text the AI wrote (`Output`). It is not retried, since whether to ask again is the caller's decision. A schema applies to the one prompt it is sent with; the next prompt without a schema is plain text again, in the same conversation.

## Events

`Output` reports everything that happens while the AI works as it happens (each watcher is given the events in order from a queue of its own, on another thread and never under a lock of the session, so a watcher may call back into the session, and a slow one only delays itself), as `PromptEvent` records: a `PromptDeltaEvent` for each piece of a message as it is written (the whole message follows as the next `PromptMessageEvent`, so a caller that shows text as it comes takes the deltas and one that waits ignores them); a `PromptMessageEvent` for text; a `PromptToolCallEvent` (the MCP server, the tool and its arguments as JSON) and a `PromptToolResultEvent` (the same id, the output, and whether it failed) for every tool the AI uses, whether it is a library tool, one of the caller's or one of an external server; a `PromptUsageEvent` when the prompt ends, with the tokens read, cached and written and the cost where the tool reports one (Claude Code does, as the cost of that prompt also in a kept process; Codex does not, and its tokens are the sum of what its model calls used); and a `PromptWindowsEvent` with the subscription limits where the tool reports them while it works (Claude Code does with every prompt), and a `PromptInterruptedEvent` last when the prompt was interrupted.

## Options of a request and limits of a session

A request has few options of its own, in `PromptRequestOptions` (which derives from `PromptOptions`, the files and the note of `Send` too): the `Schema` the answer must follow and the `Mode`. They are read when the call starts, so one record can be kept and used for many calls. Everything else that shapes a prompt belongs to the session and is set on `session.Configuration`, so that one place says how the AI works and what it may use, and every request and every piece of input given with `Send` runs the same way: the model and its settings, the tools and mounts, and the limits below. Offering something to one prompt only is not possible; change the configuration before the prompt and back after it.

The limits are one record, `session.Configuration.Limits` (`PromptSessionLimits`, everything optional and no limit by default), set as a whole and checked as a whole when it is assigned; change one limit with `with` on the current record (`Limits = Limits with { Timeout = TimeSpan.FromMinutes(10) }`). `Timeout` (at most 24 days, as long as a timer can count; the same holds for the intervals and the loop timeout) ends a request that takes longer, counted from when it is asked (so including the wait for the session to be free), and `WindowLimit` (a `PromptWindowLimit`: the function `Reached` and the `Interval`, a minute by default) ends it when the subscription is used up as far as the caller allows: the status of the session's provider is read when the request starts and then on the interval, and the function is called with it. Either one cancels the work, which ends the tool's process, and the request fails with `PromptLimitException` whose `Limit` says which. A status that cannot be read (there are no limits on an API key) fails the request with that error instead of letting it run unchecked. `MaxToolCalls` stops an AI that goes round in circles: the request is cancelled when the call after the allowed ones is reported (which may have started by then) and fails with `PromptLimitException` for `PromptLimit.ToolCalls`. In a loop all of these apply to each send.

`Retry` (a `PromptRetry`, null by default for no retry) tries the prompt again when the AI fails with something likely to pass: `MaxAttempts` is the number of tries with the first included, and the waits grow from `InitialDelay` (two seconds) times `BackoffFactor` (two) up to `MaxDelay` (a minute). By default any `PromptSessionException` is retried except `PromptLimitException`, `PromptSessionOutputException` and `PromptToolStartException` (a tool that is not installed is not helped by waiting), and `ShouldRetry` replaces that rule. Only a failure before the first event is retried: something already reported to the caller cannot be taken back, so a failure after that is thrown, which is what keeps `Output` from showing a message twice. The waits count towards `Timeout`, and the caller's cancellation ends them.

The settings are taken when a request starts, and values that are not allowed throw from the setter.

## Usage and budgets

`session.Usage` is what the session has used since the object was made, added up from the usage the tool reports for each prompt (a loaded session or a branch starts at zero). `Budget` in the limits (`PromptBudget`: a number of tokens, counting those read, without the cached ones, and written, and an amount in US dollars where the tool reports a cost, which Claude Code does and Codex does not) makes the next prompt fail with `PromptLimitException` for `PromptLimit.Budget` once the session has used that much. A loop has its own budget in its limits, counted over its sends, which stops it. None of it is stored. The tools report usage when a prompt ends, so a budget is checked before a prompt and the one that passes it is finished: the overshoot is at most one prompt.

## Interrupting

`session.Interrupt()` stops the prompt that is running without cancelling it: the AI stops where it is, the prompt ends normally with what was written until then and a `PromptInterruptedEvent`, and the conversation goes on with the next prompt, so the AI can be corrected. A running process is asked to stop and stays alive (Claude Code ends its interrupted work with an error result that the library swallows, and Codex interrupts the turn through its app server, also in a process opened for one prompt); with a process of a custom provider, the process is ended and the next prompt resumes the conversation as the tool stored it, which for a first prompt that the tool has not reported a session for means starting over. It returns whether a prompt was running. A request made right after waits until the session is waiting again, and runs next unless a prompt was already waiting for the session and takes it first. To change course without stopping the AI at all, give it more input with `Send`. Cancelling is different: it throws and ends the process.

## Subscription status

`IPromptProvider.GetWindows()` reads how much of a subscription is used, without sending a prompt. It returns a list of `PromptWindow`s, the same for every tool, each with a `Name` for display, the share used (a number from 0 to 1, so 0.5 is half), the `Length` of the window and when it resets. Claude Code has a `Session` (five hours), a `Week` (seven days) and a `Week (<model>)` for each single model its plan limits, with the lengths filled in by the library since the tool does not report them; Codex has one or two windows with the lengths and names (`5 hours`, `Week`, `Month`) its plan gives. Which windows exist depends on the tool and the plan, so a limit looks at all of them rather than at one by name. `Pace` (an extension property of a window) says how fast a window was being used: the share of the limit used divided by the share of the window that had passed, so 1 is exactly on course to use it all at the reset, 2 is twice as fast, and it is `null` without a reset time or before any of the window had started. It is worked out for the moment the window was read (`PromptWindow.ReadAt`) and not for the moment it is asked, because the percentage describes the window as it was then: a list that is some minutes old would otherwise show a slower pace than it had. An engine reports its own windows through `IPromptEngine.GetWindows`, which by default reports no windows (an empty list), as for OpenCode, whose models have no subscription limits. A read takes a second or two and costs nothing, so it is cheap enough to poll. It needs a subscription login and fails with `PromptSessionException` on an API key, or when the tool does not answer within 30 seconds. Claude Code's windows are also reported in the `PromptWindowsEvent` (its `Windows`) of every prompt. A window limit is a function of that list: `WindowLimit(windows => windows.Any(...))`, and a `PromptLimitException` for it carries the windows (`Windows`) that reached it.

## Testing a tool

`IPromptProvider.Test(apiKey)` finds out whether the tool is actually usable: it runs the tool with the smallest prompt that will do ("Reply with the digit 1.") on the cheapest model its engine knows of (Claude Code's `haiku`, the model Codex describes as fast, the first model OpenCode lists) at the lowest setting of each choice, without tools, with a minimal system prompt where the tool allows one, and with nothing stored. That proves what looking for the command cannot: the tool is installed, signed in (or the key works) and reachable. The answer is a `PromptTestResult` with `IsAvailable` and, when not, the reason (a missing command, a wrong key, no login, out of quota, the tool ending without an answer). The test ends as soon as the tool has answered, and it has no time limit of its own, so a slow tool such as a local model that has to load is waited for; a caller that wants a bound passes a cancellation. A tool that does not work is a result and not an exception, so a caller can offer the ones that do; only cancellation throws. A test costs about a thousand tokens on Claude Code and ten thousand on Codex, whose own instructions are large, which is a few cents at most.

## Branching and rewinding

`session.Fork()` makes a second session that starts with everything the first has said and done and then goes its own way, so two approaches can be tried from one point. `session.Fork(entry)` does the same from an earlier point: the branch holds the conversation up to the end of the exchange (a prompt and everything the AI did to answer it) that an entry of the history belongs to, so it never starts in the middle of a tool call. Both wait for the prompt that is running, give the branch the configuration of the original (the workspace, mounts, tools and hooks shared), the same API key and a scratch folder of its own, and leave the original as it is. Claude Code branches by itself: the branch is stored as pointing at the original conversation (and the message to stop at), and its first prompt resumes that with the tool's fork option, which makes a new conversation and reports its identifier like any first prompt. Codex forks the thread at once. A branch of a session that has had no prompt is just a new session with the same configuration (a branch at an entry of it is an error), and a loaded branch that has not been prompted yet checks that the conversation it was made from still exists.

`session.Rewind(entry)` takes the session itself back to the end of that exchange, keeping its identifier: the later exchanges are no longer part of its conversation and the next prompt carries on from the entry. It is a branch the session moves to, so the original conversation stays in the tool's storage (it is not deleted, and is still there to open with the tool itself), and a kept process is replaced. Claude Code cannot branch at a point from before the conversation was compacted (the summary replaced those messages), and refuses it with `PromptSessionException` when it is chosen. A provider that cannot branch at a point throws `NotSupportedException`.

`session.AttachTo(aiSessionId, options)` moves the session to another provider session, another workspace folder, or both, and what is given is the new value, so a `null` is a choice: no provider session (the next prompt starts a new conversation) and no workspace path (no workspace, and the tool runs in an empty folder of the session in the system temp folder, the same one every time). The workspace is the `WorkspacePath` and `Sandbox` of a `PromptSessionOptions` (the record `Create`, `Load` and `AttachTo` share, each using the part that means something to it: `Create` all of it, `Load` only the `ApiKey`, since the workspace is stored with the session, and `AttachTo` only the workspace, since the session keeps its key; the other part is refused with `ArgumentException`). A workspace path is an existing folder, becomes the `Workspace` of the configuration (with the sandbox switch) and is stored like the one given to `Create`, so a load sets it again. The call waits for the running prompt, keeps the library identifier and the other settings, ends a kept process (which held the old conversation), and leaves what it moved away from alone: the old conversation stays in the tool's storage and the old folder is not touched. It fails with `PromptSessionNotFoundException`, `DirectoryNotFoundException` or `ArgumentException` before changing anything. Claude Code looks a conversation up by the folder it ran in, so continuing a conversation takes the `workspacePath` it was made with; moving the workspace and keeping the conversation therefore works for Codex, and for Claude Code only to a folder it was also made in. What the new conversation was told as instructions is unknown, so a tool that keeps the instructions it began with is told the current ones as a note.

## History

`session.GetHistory()` reads the conversation as the provider stored it, from the end of its file, as an `IAsyncEnumerable<PromptHistoryEntry>` newest first (it reads lazily, so taking the first few entries of a long conversation is cheap): the user's prompts, what the AI wrote, and its tool calls and their results, each with the time where the provider stored one. An entry is an event with a place: `entry.Event` is a `PromptInputEvent` for a prompt or message the AI was given, and otherwise the same `PromptMessageEvent`, `PromptToolCallEvent` and `PromptToolResultEvent` that `Output` reports (with the identifiers that tie a call to its result), so one piece of code can show live output and history; `entry.Text` is the text of whichever it is. The input events are history only: `Output` does not report them, as its watchers gave the input themselves. Cut it with the usual operators (`await session.GetHistory().Take(50).ToListAsync()`). The library keeps no history of its own, so this reads the tool's file, which is why a prompt appears as the tool stored it (text files folded in, images as a marker) and why it is empty for a session without a prompt. A branch that has not been prompted yet shows the conversation it was made from. Each entry carries its place in the stored conversation as a `PromptHistoryPoint` (`entry.Point`: the byte offset of its record and its place in that record), which `Fork` and `Rewind` take; the session methods take points so that a place can be kept without keeping the entry, and extension methods accept an entry for the same calls (`session.Fork(entry)`). `OlderThan(point)` on the history continues with the entries older than one already seen, to page back through a long conversation, and `NewerThan(point)` returns only the entries newer than one already seen and stops reading there, to watch a conversation grow. The places mean something only for the session they came from.

## Instructions

`Instructions` in the configuration are custom instructions for the AI (a persona, rules, a house style), added after the library's own guidance about its tools for every prompt. They are passed in the system prompt of Claude Code and the developer instructions of Codex, so they shape the work without being part of any prompt. Instructions can be changed at any time, also on a session that was loaded: the next prompt follows the current ones. Both tools keep the instructions a conversation started with when they resume it, so the library does what each tool allows to make a change reach the conversation. Claude Code is told to render its system prompt again on every resume, so the change is a real system prompt change. Codex has no such option; instead the library tells it with a note (see Notes): a developer message that says the instructions have changed and what they are now, or that the earlier ones no longer apply when they are cleared. That note is added when the instructions differ from the ones the session last used, and on the first prompt of a loaded or branched session that has instructions, since the library keeps no record of the ones the conversation began with (a session that is loaded again with the same instructions therefore adds the same message once more). A prompt that fails before anything happened does not use the note up, so the next one carries it.

## Notes

`session.Send(input, new PromptOptions { Notes = ["the build now passes"] })` gives the AI notes with the input (the files and the notes of an input are `PromptOptions`, the base of `PromptRequestOptions`, so `Request` takes the same two), as messages from the application and not as something the user said: that a file was changed by hand, that a deadline moved. Claude Code is given it as a system reminder in front of the user's text and Codex as a developer message before the prompt, so it does not cost an answer of its own, and it stays in the conversation afterwards. Several notes are delivered in the order they were given, once. A note is always sent with an input, so it never waits alone; notes that were not delivered because the work failed to start stays for the next, and a note on a provider that is run as a custom command is written as a line in front of the prompt.

## Context and compaction

`session.GetContext()` says how much of the model's context window the conversation fills now (`PromptContext`: `Tokens`, `Limit` and `Used`, a number from 0 to 1), the tool's own instructions and tool descriptions counted in, so that a long conversation can be compacted before it overflows. `session.Compact()` makes the tool summarize the conversation, which frees room: Claude Code continues the compacted conversation under a new session identifier, which the library follows, and Codex compacts the thread. Both use the kept process when the session has one and otherwise run in a process of their own for the operation, wait for the prompt that is running, and need a provider that can keep a process (a custom provider cannot, and throws `NotSupportedException`). Before the first prompt of a Codex conversation there is nothing to report and the context has no tokens and no size; Claude Code reports its instructions and tools even then. Compacting a conversation that is too short to compact fails with the tool's own message.

```csharp
if ((await session.GetContext()).Used > 0.8)
{
    await session.Compact();
}
```

## External MCP servers

`McpServers` in the configuration (a name to a `PromptMcpServer`, either `Stdio(command, arguments)` for a program the tool starts or `Http(url, bearerTokenVariable)`) gives the AI the tools of MCP servers that exist already, next to the library's own. The tools are started with only the servers the library names, so the servers in the user's own configuration stay out and these are the only extras. All their tools are allowed without asking, so add only servers that deserve that trust. A secret is named and not given: the bearer token is the name of an environment variable of the host process (Claude Code expands it into the header, Codex reads the variable itself), and the environment variables of a program are passed to the tool as written. The tool starts and talks to the server, not the library, so a server that fails to start only offers no tools. Names follow the tool name rules and are not `liveai`.

## Custom engines

A caller can add a command line tool besides Claude Code and Codex by implementing `IPromptEngine` and giving it to a `PromptProvider`, which then creates, loads, deletes and tests its sessions like the built-in ones, with no registration. Its `Identifier` is what a session stores, so a session is loaded again by a provider over an engine of the same name (compared ignoring case). Only `Identifier`, `CreateStart` and `Parse` have to be implemented; an engine that wants more than a process per prompt (a kept process, history, branching) implements the other members too. A simple engine only says how to start the process for one prompt and how to read a line of its output: it is given a `PromptEngineStart` (the model and effort, the session to continue or branch from, the working folder, the API key, the instructions as text, the schema, the MCP servers to configure with the library's own server's address and bearer token, and the paths of the images written as files) and returns the process, and it turns each output line into `PromptEngineEvent`s (the tool's session identifier, replies, tool calls and usage, the end, failures). The prompt is written to the process's standard input, which is then closed. Everything else has a default that does nothing: no history, no branching, no status, nothing to delete, files written for the length of the prompt. Such an engine never stays alive between prompts, and works with everything else: tools, mounts, structured answers, loops, limits, interruption (by ending the process), the tester and the status (through its own status).

## Testing code that uses the library

The `Markwardt.LiveAi.Testing` namespace has fakes of the entry points, so code that uses the library can be tested without a tool, a login or a data folder. `FakePromptSession` answers from a script (`Reply`, `Fail`, `Hang`, and `ReplyWith` for what is not scripted) and records every prompt it was given (`Prompts`); its requests are the real ones, so files, structured answers, options, timeouts, retries, limits, loops, events, interruption, budgets, branching and history behave as in production. `FakePromptSession` and `FakePromptProvider` take a `TimeProvider` (`time:` and `Time`) that the timeouts, retry delays, loop schedules and prompt times run on, so a test can move the clock instead of waiting. `FakePromptProvider` makes them (and `OnCreate` scripts each one) and loads and deletes them in memory; its `TestResult` and `Windows` are what `Test` and `GetWindows` return. A fake session also records the notes it was told (`FakePrompt.Notes`), counts its compactions (`Compactions`), reports the context a test sets (`Context`), and branches and rewinds at an entry of its history. `FakePromptSession.Windows` (or `FakePromptProvider.Windows` for all the sessions it makes) are the subscription windows that window limits read. A prompt without a scripted answer fails with a message that shows the prompt, so a test cannot pass by accident.

## Persistent process

By default every prompt gets a process of its own and nothing is left running between prompts. `IsPersistent` (a configuration setting, off by default) keeps the AI's process alive instead, for either provider: it starts with the next prompt, takes the following ones, and is not ended by the library on its own, which saves the start of a process per prompt. Setting it back to `false` ends the live process in the background: the assignment returns at once, a prompt that is running finishes first, and the next prompt gets a process of its own again. A persistent session holds a running process, so dispose it (`await using`) when done; `DisposeAsync` lets a running prompt finish, fails the ones waiting behind it and then asks the process to exit (its input is closed and it gets a few seconds before it is ended), while `Dispose` cancels the running prompt and ends the process at once. Disposal does nothing for a session that was never persistent.

The model and its settings are given to the running process with the prompt and never restart it (except for OpenCode): Claude Code is told with control requests before the prompt and Codex takes them with every prompt. The library does end a persistent process in four cases: a prompt is cancelled (its state is unknown), a setting that is passed to the tool when it starts (the instructions, the external MCP servers, the library's tools and the places they are served at) was changed (changing one ends the process in the background once its prompt is done), the schema of a structured prompt changed for a Claude Code process (Codex takes the schema with each prompt), and the process had died on its own. Alternating between output types, or between structured and plain prompts, therefore starts a new Claude Code process each time, while repeating one type reuses it. The next prompt then starts a new one that resumes the same conversation, so none of this loses context.

## State, input and output

A session is a conversation with a state: `Waiting` (idle), `Working` (the AI is busy with input it was given) or `Responding` (the AI is answering a direct request). `session.Output` is a hot `IObservable<PromptEvent>` of everything the main conversation outputs, whoever caused it: messages and their deltas, tool calls and results, usage, subscription windows, interruptions and failures, plus a `PromptStateEvent` whenever the state changes. A watcher gets what happens after it subscribes and nothing is replayed (`session.State` is the current state; `GetHistory` reads the past). It completes when the session is disposed, and work that fails is a `PromptFailureEvent` and does not end it.

`session.Send(input)` gives the AI input at any time except while it is responding, where it throws a `PromptSessionStateException`. Input reaches the AI at once. While the AI is working it is taken into that work (Claude Code and Codex both take input in the middle of their work), and while it waits it starts work; what the AI does with it is seen on `Output`. The `Task` completes as soon as the input has been written to the running AI process, or has been queued when it cannot be written at once (the work is not running a process that takes input, or it ended meanwhile); it does not wait for the AI to act on it, which is what `Output` shows. A custom engine that cannot keep a process holds the input until the work ends.

## Asking: direct, mixed or in a fork

`session.Request(input, options)` (and `Request<T>`, which is built on it) is for request/response semantics: its answer comes back to the caller (typed with `Request<T>`; the timeout, the retries and the limits are settings of the session), and the `Mode` option (`PromptRequestMode`) chooses where the AI answers it. A request is always about one input, which is why it is separate from `Send`.

- **Direct** (the default) asks in the main conversation. The session goes to `Responding` until the AI has answered, the events also go to `Output`, and the request throws a `PromptSessionStateException` unless the session is `Waiting`. This is the work the AI would do for input, with the answer being its output (structured when a schema is given).
- **Mixed** mixes the request into the work the AI does anyway. It is given like input, in `Waiting` or `Working` (`Responding` throws), and into the work in progress,, with a unique identifier, and the AI is asked to answer by calling a `respond` tool with that identifier and, when there is a schema, an answer object that follows it. The tool checks the answer (an object, with the properties the schema requires) and tells the AI what is wrong so that it can answer again. The request completes with one message holding the answer; everything else the AI does stays on `Output`. If the AI ends its work without answering, the request fails. The tool is part of every session's tools (the library's tool server is therefore always started), so a request can join work that is already running, and a request in this mode cannot have a model, reasoning, tools or mounts of its own, since it joins work it does not control. Its usage, tool calls and messages are not separated from the work's.
- **Fork** copies the conversation as the tool has stored it (so not what the AI is in the middle of doing) into a session and process of its own, asks there directly, and throws the copy away, deleting what the tool stored for it. It works in any state, nothing it does reaches `Output`, and the main session is untouched. Its usage is not added to the main session's.

## Prompt loops

`session.Loop(input, ...)` returns an `IPromptLoop<TReply>` that sends the request to its session again and again, for work such as watching something and acting on it. The first send starts at once, and its `Schedule` (a `PromptLoopSchedule`) decides when the next one does: `Continuous` (what `Loop(input)` gives with no schedule, and the default) as soon as the last send is done, `Manual` only when `Trigger()` is called, and `Every(interval)` (`PromptLoopSchedule.Every(interval)`) when the last send is done and the interval has passed since it started, so a quick send waits out the rest of the interval and a slow one is followed at once. Sends never overlap in any mode. The schedule is one value so that its mode and interval change together, and it can be replaced at any time, also during a wait that is going on (`loop.Schedule = PromptLoopSchedule.Continuous`). A trigger sends immediately in every mode, also during the wait for an interval (which then starts over), and does nothing while a send is in progress. `Input` and `Options` can be changed at any time and apply to the next send. `Replies` is an `IObservable<TReply>` for watching the loop: each send publishes its answer, a watcher that subscribes is first given the latest answer, which is what keeps it from missing the first one when the loop has already started, and the sequence ends with completion when the loop stops and with the exception when a send fails. Like `Output`, every watcher has an ordered queue of its own on another thread, so a slow one delays only itself; a watcher that throws is dropped quietly. `Task` completes when the loop has stopped. Disposing the loop (it is both `IDisposable` and `IAsyncDisposable`) stops it, and the task then completes normally: `DisposeAsync` lets a send in progress finish and starts no other, while `Dispose` stops at once and cancels the send in progress; a send that fails stops the loop and faults the task with the exception, because retrying a failing prompt on a timer would hide the error. Each send is a request in the mode of the loop's request, so the default (direct) needs the session to be waiting and a send that finds it busy fails like any other direct request, which faults the loop; a loop in another mode (mixed or fork) can run next to input and other requests.

`Loop` takes a `PromptLoopLimits<TReply>` that makes the loop stop by itself, normally and without an error, at the first limit it reaches: `Timeout` (how long the loop may run; it also cancels a send in progress), `MaxRuns` (the last reply is still published), `Until` (called with each reply after it is published) and `WindowLimit` (a `PromptWindowLimit`, replacing the session's while the loop runs and applied to every send, which stops the loop instead of failing it) and `WaitForWindow`, a function from the windows that reached the limit to the window to wait out, which makes a loop that reaches the window limit wait for that window to reset (and a few seconds more) and then send again instead of stopping (for example `windows => windows.Single(window => window.Name == "Session")`): only the caller knows which window its limit was about, `loop.ResumesAt` says until when it waits, the `Timeout` still ends it, and it needs a `WindowLimit` to know when to wait. When the function returns nothing, or a window with no reset time in the future, the loop stops as without the option. `StopReason` says why it stopped. A `Timeout` or `WindowLimit` of the session applies to each send and, being a failure of that send, faults the loop. The limits are given when the loop is made, not set afterwards, because the first send starts at once.

A loop is typed when the AI is made to answer in the shape of a type: `Loop<TOutput>(...)` expects `TOutput` in every send and publishes each answer as a `TOutput`, with `Until` taking the same type; an answer that is not one fails the loop with `PromptSessionOutputException` like `Request<TOutput>` does. A loop of plain text is an `IPromptLoop<string>`.

## Logging

`new PromptProvider(engine, dataFolder, logger)` takes an `ILogger` (from `Microsoft.Extensions.Logging.Abstractions`, the library's only package dependency) that its sessions report to. The messages are about what the library does and carry the session identifier: the state changes of a session and the processes and tool servers it starts (debug), input given to work that is running and whether the process took it (debug), a fork, rewind or attach (information), a request stopped by one of its limits (information), and a try that failed and will be repeated and work that failed (warning, with the exception). Prompts, answers, files and tool arguments are never logged. The messages are generated with the `LoggerMessage` source generator, so a level that is not enabled costs a check and nothing more.

## Errors

- `PromptSessionException` - the tool could not be started, or the AI reported a failure (wrong API key, no subscription, out of quota), or a stored link is unreadable.
- A tool's own failure is not an error of the session: it is returned to the AI.
- `PromptSessionOutputException` (a `PromptSessionException`) - the answer to a structured prompt is missing or is not the requested type.
- `PromptLimitException` (a `PromptSessionException`) - a request reached the `Timeout`, `WindowLimit` or `MaxToolCalls` of the session's limits, or the session its budget.
- `PromptToolStartException` (a `PromptSessionException`) - the tool could not be started, typically because it is not installed.
- `ArgumentException` - an output type or schema whose root is not an object, or a tool, mount or MCP server name that is not allowed, or a session given to `Load` or `Delete` that was made by a provider of another tool.
- `PromptSessionNotFoundException` (a `PromptSessionException`) - `Load` for an identifier that is not a session identifier, has nothing stored, or whose provider session is gone (the stored session is kept).
