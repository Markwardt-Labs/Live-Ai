# API

The public API has one entry point, `IPrompter`, which creates, loads, lists, deletes and tests the sessions of every supported tool and hands out the `IPromptSession`s. What a caller says about a tool is a record derived from `PromptSetup`, which carries only what that tool needs; the engines that start and read the tools, the models they offer and the image services are all internal, so the caller says what it wants (a tool, how capable, how much effort) and the library works out the rest. This document covers the *design and flow* of that surface: how the pieces fit together and the order things happen in. It does not restate member-level detail already covered in the source itself.

## Shape

A caller makes a `Prompter` from a data folder (where sessions are stored; `null` is `Markwardt.LiveAi` in the local application data folder) and optionally a logger and a clock. `Create` takes a `PromptSetup`, an abstract record that holds the workspace and whose derived types are the tools: `ClaudeSetup` (Claude Code), `CodexSetup` (Codex) and `LocalSetup` (models on this machine or the network, through OpenCode and a model server such as Ollama). The `Prompter` picks the tool by the type of the setup and keeps one internal tool service per tool and place it is found in the `Environment` (command, configuration folder, server, models, context sizes), so sessions of one tool share a model list. Prompters over the same data folder share their storage, so one can load what another created.

The setup holds what cannot change afterwards and what a session of the tool needs: an optional API key (none means the key of the environment, and without one the subscription already configured in the tool), an optional workspace path, for local models optional `Overrides` (a `PromptServerSettings` with the server, the models and the context sizes the session sets differently from the environment). Where things run is not the session's but the environment's: `IPrompter.Environment` (a `PromptEnvironment`) holds the command and configuration folder of each tool, the API key that new Claude Code and Codex sessions use unless their setup has its own (the session then stores the key it was created with), the image generation setup, the configuration new sessions start with (`Capability`, `Effort`, `IsShellAllowed`, `IsSystemAccessAllowed`, `IsWebAllowed`, `IsImageGenerationAllowed` and `Instructions`, with the usual defaults unless set, which a session copies when it is created and keeps from then on, whatever the environment says later; `Create` refuses a capability or an effort that is not defined) and the local `PromptServerSettings` (server, the models either one for every capability or one per capability, and the context size per capability) for all sessions of the prompter. It is not stored with sessions, so a loaded session runs on the environment of the prompter that loads it, with the overrides it was stored with on top; the models must be named by the environment or the overrides, since the library cannot know which model of a local server to run. The model is never chosen by the caller. The configuration holds a `Capability` (`Fast`, `Balanced`, `Strong`, `Max`) and an `Effort` (`Low`, `Medium`, `High`, `Max`), and the library selects the model and its settings in the background when a prompt starts, from the models the tool offers (listed once a minute and kept, with models the library knows as a fallback when the tool cannot be asked): the capability picks the tier by the names of the models (Claude Code is `haiku`, `sonnet`, `opus`, `fable`), the nearest tier when one is missing with the higher on a tie, and names it does not know are spread over the list in order; the effort picks the level of the same name among the ones the model offers, the highest for `Max`, and otherwise spreads the levels. `Load(id)` and `Delete(id)` take no setup: the stored link holds the setup, so the tool is read from the identifier alone and its place from the environment. The API key is stored with the rest of the setup, so a loaded session runs on the same key.

The library has its own identifier per session (`IPromptSession.Id`, a GUID in text form without hyphens), separate from the tool's session identifier: it is generated before the tool has seen the session, it is the same for every tool, and it is what a caller keeps. `IPromptSession.Provider` and `PromptSessionInfo.Provider` say which provider a session runs on, a `PromptProvider` (`Claude`, `Codex` or `Local`), which is what the type of its setup chose; the descriptors name the tool for a person (`Claude Code`). The link to the tool's own session is the library's concern and is not exposed: the library records it once the tool reports it. What is stored with a session is that link (the identifier, the tool, the working folder, the workspace and the system access switch), the setup it was created with (with the API key, without the workspace) and its whole configuration; the tools, MCP servers, asker and cache are not stored.

A session reports what can be changed through `Configuration`, and its folder as `WorkspacePath`. The API key is not reported anywhere, because a secret should not travel back out.

What can be changed on a live session is two types. `IPromptSessionConfiguration`, which `IPromptSession.Configuration` returns, holds what is stored with the session: the capability and effort, the shell, system access, web and image generation switches and the instructions. `IPromptSessionTransientConfiguration`, which `IPromptSession.Transient` returns, holds what the application plugs into the session object and is never stored: the tools, the external MCP servers and the asker (`Tools`, `McpServers`, `Asker`), which a loaded session starts without. They are ordinary settable properties and collections, changed at any time. Nothing takes effect when one is set: the session takes all of them together when the next prompt starts, which is the point of making them lazy, since however many a caller changes the session decides once what it needs (rebuild the file tools, end a process that was started with other settings), so there is at most one restart. The model and its settings are not among those: a running process takes them with the prompt, except for OpenCode, which takes them when it starts. A value that is not allowed (an undefined enum value, a tool name that is not allowed or is taken, an MCP server that is neither a command nor an http address) throws where it is assigned and changes nothing, and after the session is disposed every change throws `ObjectDisposedException`. A running prompt keeps the settings it started with. The tool and the identifier cannot be changed: a tool's sessions live in its own storage, so changing either would not continue the conversation.

A session is a conversation that keeps one process of the tool alive whenever the tool can (Claude Code, Codex and OpenCode all can), which saves the start of a process per prompt and is what disposing the session ends. It is both `IDisposable` and `IAsyncDisposable`, with the two forms described under the persistent process.

## Flow

1. `IPrompter.Create` generates the GUID, makes the workspace folder (`Workspaces/<session id>` in the data folder, kept until the session is deleted or moved elsewhere), or uses the workspace path when one is given (an existing folder, which becomes the session's `WorkspacePath` and comes back with every `Load`; whether the file tools can leave it is `Configuration.IsSystemAccessAllowed`, false by default and changeable at any time), stores the link and returns the session. The tool's own session does not exist yet.
2. `session.Request(input, options)` sends a prompt, waits for the end and returns the answer as a string (the messages joined; with a schema, the answer alone). What happens while it runs (see Events) is in the event stream as it happens. `Request<T>(input, options)` is an extension method that reads a typed answer. Everything about one prompt is one optional `PromptRequestOptions` record. A failure of the tool or of the AI surfaces as `PromptSessionException`, after the messages that came before it.
3. The first answered prompt makes the tool report its own session; the library stores the link. Every later prompt resumes that session, so the AI keeps its context.
4. `IPrompter.Load(id)` rebuilds the session from its stored link, in this process or another, with the configuration it was stored with, and continues from step 2. If the tool's session is gone, `Load` fails with `PromptSessionNotFoundException` and keeps the stored session, since the cause can be a tool pointed at another configuration folder.

## Changing settings

A change to the configuration applies from the next prompt (a prompt already running keeps the settings it started with) and is stored with the session: when a prompt starts and, if it changed since, when the session is disposed, so a `Load` brings the configuration back. An undefined enum value throws `ArgumentOutOfRangeException` from the setter. A process that is kept alive and was started with a setting that has since changed is ended in the background once its prompt is done, without waiting for the next prompt.

## Deleting sessions

`IPrompter.List()` returns what is stored, the most recently loaded first, as `PromptSessionInfo` (the identifier, the provider, when it was last loaded, which starts as when it was created, and the workspace path), so a caller does not have to keep the identifiers itself; links that cannot be read, and links of a tool this version of the library does not know, are left out. A session stored by an earlier version of the library is upgraded when it is read, keeping the original beside the file, and what the earlier layout never stored (the shell, web and image generation switches and the instructions, for a session of the first layout) has its default until the caller sets it. `IPrompter.Delete(id)` removes a session for good: the stored link (and the backup an upgrade kept of it), the tool's own conversation (with the folders the tool leaves empty) and the workspace folder with its files, only when it is a folder the library made. It returns whether the session existed, and fails without deleting the link when the conversation cannot be removed, so it can be tried again. An open session must be disposed first, and a workspace folder is never touched.

## Automatic, and limited by what is offered

The AI never asks for permission to do anything: it can use every tool it is offered. What it can change is decided by the workspace, the session storage, the cache and which tools are configured, and the library enforces it in its own code for both providers. There is no read-only mode for a workspace: to keep its changes away from the original, give it a copy of the folder, or put what it should only read in the session storage.

## File tools

The AI works on files only through the library's own file tools, and unless the shell is enabled (see Shell) has no shell and no other way to the machine. What its paths mean is the session's workspace, session storage and cache. The workspace is the folder given as `WorkspacePath` in the setup, or a folder the library makes for the session in its data folder (`Workspaces/<session id>`) when none was given, and `IPromptSession.WorkspacePath` reads it: a relative path the AI gives a tool is relative to it, like in a shell. `IPromptSession.Workspace` is an `IStore` over the same paths, for the caller. Besides the workspace there are two stores in the top level, named by `PromptStorageNames`: the session storage `.liveai-session` and the cache `.liveai-cache` (`.liveai-session/folder/file.txt`). Both start empty, are not stored and are lost when the session is disposed, keep their data in memory up to `Storage.MemoryLimit` and move the rest to files in the background, and the cache also drops a file that was not read or written for `Storage.Retention`. A third place, `PromptStorageNames.Temp` (`.liveai-temp`), is a real folder in the workspace for data that commands use. The tools (list, find, search, read, write, edit, copy, move, delete, diff) work the same on all of them, so the AI can copy or move between them. The two mounted folders themselves cannot be deleted, renamed, moved, overwritten or be the target of a move, however their path is spelled (`.liveai-session`, `.liveai-session/`, `.liveai-session/.`). Listing the top shows the workspace's entries together with them. A path that is absolute, or climbs above the workspace, is the workspace's own business: while system access is off, the default, an absolute path that lands inside the folder is another spelling of the relative one and the rest is refused, and with it on any path of the machine, absolute or relative, is taken; the session storage and the cache refuse paths that leave them. The AI is told what it can reach.

An `IStore` is five operations (list, open, create folder, delete, move). `Open(path, mode)` returns a stream of bytes, so any file can be handled, and the `StoreOpenMode` decides what it is: `Read` (an existing file, read only), `Open` (an existing file, read and write, content kept), `Create` (a new file; fails if anything is there), `Replace` (write, discarding what was there, making the file if missing) or `Append` (write at the end, making the file if missing). The library makes every store (the workspace folder, confined to it by default, and the session storage and cache, which keep data in memory and move it to files when it does not fit); the only one a caller gets is `IPromptSession.Workspace`, to put documents in it (`WriteText`) and read back what the AI made (`List`, `Open`, `ReadText`), and the AI works on the same store through the file tools (numbered reading with line limits, glob and regular expression search, exact-match edits with an optional replace-all). `ReadText`, `WriteText`, `ReadAttachment`, `ListFiles` and `ListFolders` are extension methods, and `IsFolder`, `GetSize` (a folder's size is the sum over everything in it) and `Copy` are members of `IStore` with default implementations built from the five. `List` can list everything below a folder (`recursive`; an entry carries its path relative to the listed folder). Copying and moving a folder takes everything in it, empty folders included, and a move between two stores the library knows how to move between (two disks, two memory stores) relocates instead of copying.

The cost of no shell is that the AI cannot build, test or run git. A caller who wants only some commands adds a tool of their own that runs the commands they allow (see Tools), which keeps the decision of what may run with the caller; one who trusts the AI with everything enables the shell. The library tools' names (the file tools and `shell`) are taken; a caller's tool cannot use them. The user's own MCP servers and connectors in the Claude Code configuration are not available to the session, so a session sees only the tools the library gives it.

## Tools

The `Tools` of the session's transient configuration (`IPromptSession.Transient.Tools`, a list, empty by default) holds functions of the caller's that the AI can call while it works. It holds only those: the library's own file tools are not in it, they are built and served in the background for every session. A tool is a `PromptTool`: a name, a description (all the AI knows about it besides its input), a JSON Schema for its input, and a handler from the arguments to a text result. `PromptTool.Create<TInput, TOutput>` builds one from typed code the same way structured output does: the schema comes from `TInput` (an object), the arguments are read into it, and the output is written as JSON text (a string goes back as it is). The AI sees tool calls as ordinary tool use and the calls run in the caller's process, so a handler can use anything the caller has.

The library's own tools (the file tools, `shell`, `ask_user`, `view_image`, `fetch_url`, `download_url`, `search_web`, `generate_image`, `current_time`, `tool_search`, `delegate`, `task_wait`, `task_output`, `task_stop`, `diff_files` and `respond`) have reserved names that a caller's tool cannot take, compared without regard to case, so a caller's tool never replaces or hides one of them; the session also refuses to start a prompt if two offered tools would share a name. The `Asker` of the session (`IPromptSession.Asker`, null by default) is a `PromptAsker`, a delegate from a question to the reply: while it is set the AI is offered an `ask_user` tool that takes a `question`, calls the function with it, waits as long as it takes, and gives the AI the text it returns (null counts as empty). It is the way for the AI to ask the user something in the middle of its work, and the way to show it is up to the caller (a prompt in a console, a dialog, a chat message). Without a function the tool is not offered at all, so the AI does not know it could ask. The function is read when a prompt starts, to decide whether to offer the tool, and when the tool is called; setting or clearing it restarts a persistent process, like a change to `Tools`. A function that throws gives the AI an error result it can react to. A change to `Tools` applies from the next prompt; a persistent process restarts when the offered tools change. Names are 1 to 64 letters, digits, underscores and hyphens and unique, or adding it throws `ArgumentException` and changes nothing. A handler that throws does not fail the prompt: the AI is given the exception message as an error result and can react. A handler may be called from several threads at once, since the AI can call tools in parallel.

The library cannot know what a handler does, so which tools a session has is the caller's decision, made by what it configures. The arguments given to a handler are only valid for the call.

Offering tools holds a local port, so dispose the session when done.

## Shell

`view_image` is always offered (while the model takes images and the tool can be shown them): it shows the AI a PNG, JPEG, GIF or WebP file and reaches exactly what the file tools reach, the session storage and the cache always and the workspace only when the session has a `WorkspacePath`, confined to it unless `IsSystemAccessAllowed` is true. `IsWebAllowed` (off by default) gives the AI the web with no restriction: `fetch_url`, which reads text from an http or https address as this machine (`raw: true` gives a page with its markup), `download_url`, which saves any file from an address into a store without it passing through the conversation (by default in `.liveai-cache/downloads`, never replacing a file, and refusing one larger than `Storage.FileLimit`), and a search, with the tool's own where it has one (Claude Code and Codex), which is allowed when the tool starts, and otherwise with the library's `search_web`, a rate limited best-effort reader of DuckDuckGo's HTML page.

Every session is also offered `current_time`, `tool_search`, `delegate` (a task in a helper session, without or with the conversation so far, whose usage is added to the session's) and, with the file tools, `diff_files`; there is no switch for them. `shell` and `delegate` take `background` to return a task identifier at once and keep working, which `task_wait`, `task_output` and `task_stop` follow.

`PromptEnvironment.ImageGeneration` (null by default) holds the setup of the service that makes the images the AI asks for, an empty abstract `PromptImageSetup` whose derived types are the services: `OpenAiImageSetup` (an API key only) and `LocalImageSetup` (an AUTOMATIC1111 or Forge server and the required `Models` mapping from capability to checkpoint). The names that can go into the `Models` of the local settings and `LocalImageSetup.Models` are listed by the static `ListModels` method of each, which asks the server and is the only place a caller sees models. Neither sets a capability: the image generator is for the AI, which picks the capability for each task through the `capability` argument of its tool (a fast model for sketches and many variants, a strong one for a final image), and the size, quality and count are its to ask for too. For OpenAI the capability picks `gpt-image-1-mini` (`fast`), `gpt-image-2.6-flare` (`balanced`) or `gpt-image-2.6-sunburst` (`strong` and `max`), or the newest listed model of that kind; for Stable Diffusion it picks the checkpoint of `Models`, and the argument is offered only when the checkpoints differ. A session says whether the AI may use it with `IsImageGenerationAllowed` in its configuration (off by default, stored with the session). While that is on and the environment has a setup, the AI is offered `generate_image`, whose arguments follow what the service supports (a capability, transparency, a negative prompt, a seed). The setup is read from the environment when a prompt starts, so the key lives in the environment and is not stored with sessions.

`IsShellAllowed` in the configuration (off by default, stored with the session) gives the AI one more library tool, `shell`, which runs any command on the machine through `/bin/sh -c` (`cmd /c` on Windows), as the user the host process runs as, and returns the output (standard output and standard error together) with the exit code. It is the one tool that is not confined by anything else the library offers: the confinement of the file tools says nothing about what a command can reach, so it is meant for an AI and a task that deserve that trust (a command also sees the host's environment variables, and anything else the host process can reach), and it is a separate switch so that nothing else can enable it by accident. Commands start in the workspace, unless the AI gives a `working_directory`; standard input is empty so a command that waits for input ends; a command is stopped after `timeout_seconds` (120 by default, at most 3600) or when the prompt is cancelled, with everything it started; and very long output is cut at 64 KB. Like the file tools it is served in the background and is not listed in `Tools`, and the AI is told it has a shell. Nothing sits between the AI and the shell to approve its commands, so enable it only for work that deserves that trust.

## Attachments

A prompt can come with files: `PromptSendOptions.Attachments` (of a request or of `Send`) takes `PromptAttachment`s, a name, a media type and the bytes; `PromptAttachment.FromFile` and `IStore.ReadAttachment` make them with the media type taken from the extension, reading the file when they are called. What happens to a file depends on its type: images (PNG, JPEG, GIF, WebP) are shown to the AI, with both providers; PDF documents are shown to the AI with Claude Code; text files (`text/*`, JSON, XML, YAML) are put into the prompt as text, in a code fence, after the prompt, with both providers; anything else is refused with `NotSupportedException` before anything is started, with a message that says to put the file in the session storage and let the AI read it with the file tools. Because text files are folded into the prompt, a prompt with only text files starts the ordinary process, and only images and PDFs change how the tool is started. The files are part of that one prompt: the provider keeps them in the conversation, so the AI can still refer to an image in a later prompt, but the library stores nothing of them. Limits keep a prompt reasonable: 20 attachments, 20 MB each and 30 MB together, and 256 KB for a text file (a larger one is better put in the session storage, where the AI can read it in parts); a text file that is not valid UTF-8 is refused instead of being sent as garbage.

## Structured input and output

The reflection-based entry points, `Request<TOutput>` and `PromptTool.Create<TInput, TOutput>`, are marked `[RequiresUnreferencedCode]` and `[RequiresDynamicCode]`: they build schemas and read JSON through reflection, so in a trimmed or native AOT application they need the members of their types kept (a non-string object given as the input of any request is written the same way). The library is not otherwise annotated, and there are no `JsonTypeInfo` overloads.

`Request<TOutput>` makes the AI answer with a `TOutput`: the library builds the JSON Schema of the type, the tool is made to answer under that schema, and the answer is read back into the type. An object goes in as the input of any of the calls, which writes it as JSON (with its own runtime type, when the call is made), and a prompt that is only that JSON has no sentence around it, so the object should carry its own instruction (a `Task` property, say). `Request` returns plain text (the messages joined; with a schema set, only the answer), `Request<T>` is an extension method that sets the schema of the type in the options and reads the answer back, and the `Schema` option takes a hand-written schema for any call (`Request` then returns the answer as JSON text). With a schema the last message is the answer as JSON text; the earlier messages are the AI's progress notes as usual.

A property that may hold any value (a `JsonElement`) is written as an empty schema and not as `true`, because strict tool parsers such as Ollama's refuse a boolean in place of a schema. Types are written with fixed options, so the shape of an input or answer is controlled with attributes on the type (`[JsonPropertyName]`, `[JsonConverter]` and so on); there is no serializer options argument, to keep the API small. The options are camel case, enums as their names, numbers only as JSON numbers, and required constructor parameters and non-nullable annotations enforced, so an answer that leaves out a required value is an error instead of a default. Both tools require an object at the root of the schema, so an output type that is not written as an object (a string, a number, an enumeration, a list or array) is asked for in an object with one required property, `value`, and unwrapped again: `Request<bool>("Is this safe?")` and `Request<string[]>("List the files.")` work, and the AI sees the wrapper only in the schema. Everything else is as for an object type, including the `PromptSessionOutputException` when the answer does not fit. Optional properties work, but Codex requires every property to be present, so for Codex they are made required and an optional value should be nullable. Free-form dictionaries are not supported by Codex's schema rules, and a type that uses one fails as a `PromptSessionException` from the tool.

An answer that is missing, not JSON, or not a `TOutput` throws `PromptSessionOutputException`, which carries the raw text the AI wrote (`Output`). It is not retried, since whether to ask again is the caller's decision. A schema applies to the one prompt it is sent with; the next prompt without a schema is plain text again, in the same conversation.

## Events

Subscribing to the session reports everything that happens while the AI works as it happens (each watcher is given the events in order from a queue of its own, on another thread and never under a lock of the session, so a watcher may call back into the session, and a slow one only delays itself), as `PromptEvent` records: a `PromptDeltaEvent` for each piece of a message as it is written (the whole message follows as the next `PromptMessageEvent`, so a caller that shows text as it comes takes the deltas and one that waits ignores them); a `PromptMessageEvent` for text; a `PromptToolCallEvent` (the MCP server, the tool and its arguments as JSON) and a `PromptToolResultEvent` (the same id, the output, and whether it failed) for every tool the AI uses, whether it is a library tool, one of the caller's or one of an external server; a `PromptUsageEvent` when the prompt ends, with the tokens read, cached and written and the cost where the tool reports one (Claude Code does, as the cost of that prompt also in a kept process; Codex does not, and its tokens are the sum of what its model calls used); and a `PromptWindowsEvent` with the subscription limits where the tool reports them while it works (Claude Code does with every prompt), and a `PromptInterruptedEvent` last when the prompt was interrupted.

## Options of a request

A request has few options of its own, in `PromptRequestOptions` (which derives from `PromptSendOptions`, the files and the note of `Send` too): the `Schema` the answer must follow and the `Mode`. They are read when the call starts, so one record can be kept and used for many calls. Everything else that shapes a prompt belongs to the session and is set on `session.Configuration` and the session itself, so that one place says how the AI works and what it may use, and every request and every piece of input given with `Send` runs the same way: the model and its settings, the tools and the switches. Offering something to one prompt only is not possible; change the setting before the prompt and back after it.

The settings are taken when a request starts, and values that are not allowed throw from the setter.

## Usage

`session.Usage` is what the session has used since the object was made, added up from the usage the tool reports for each prompt (a loaded session or a branch starts at zero). None of it is stored; the tools report usage when a prompt ends, and a cost only where the tool reports one (Claude Code does, Codex does not).

## Interrupting

`session.Interrupt()` stops the prompt that is running without cancelling it: the AI stops where it is, the prompt ends normally with what was written until then and a `PromptInterruptedEvent`, and the conversation goes on with the next prompt, so the AI can be corrected. A running process is asked to stop and stays alive (Claude Code ends its interrupted work with an error result that the library swallows, and Codex interrupts the turn through its app server). It returns whether a prompt was running. A request made right after waits until the session is waiting again, and runs next unless a prompt was already waiting for the session and takes it first. To change course without stopping the AI at all, give it more input with `Send`. Cancelling is different: it throws and ends the process.

## Descriptors

`session.Descriptors` is a read-only dictionary of what the session knows about how it is run. The keys are plain strings and are not constants, because they are meant to be read: both the keys and the values are written for a person, so a list of them can be shown as it is. `Provider` (the tool, such as `Claude Code`) is there from the start, and once a prompt has chosen the model there are `Model` (its display name, such as `Opus 4.7`), `Model ID` (its identifier, only when it differs) and one entry for each setting the model runs with, named as the tool names it, with a value that reads well: a choice with a capital (`Effort` is `High`), a switch as `On` or `Off`, a number with separators (`Context window` is `16,384`). Which names exist depends on the tool, so look one up. Every change makes a new snapshot and pushes a `PromptDescriptorsEvent` with it to the event stream, which happens when a prompt starts on another model or other settings (a change of capability or effort, for one); a loaded session has only the provider until its first prompt.

## Subscription status

Subscription limits are read by `IPrompter.Test`, which returns the windows with the result when the tool answered. A `PromptWindow` is the same for every tool: a `Name` for display, the share used (a number from 0 to 1, so 0.5 is half), the `Length` of the window and when it resets. Claude Code has a `Session` (five hours), a `Week` (seven days) and a `Week (<model>)` for each single model its plan limits, with the lengths filled in by the library since the tool does not report them; Codex has one or two windows with the lengths and names (`5 hours`, `Week`, `Month`) its plan gives. Which windows exist depends on the tool and the plan, so look at all of them rather than at one by name; OpenCode has none. `Pace` (an extension property of a window) says how fast a window was being used: the share of the limit used divided by the share of the window that had passed, so 1 is exactly on course to use it all at the reset, 2 is twice as fast, and it is `null` without a reset time or before any of the window had started. It is worked out for the moment the window was read (`PromptWindow.ReadAt`) and not for the moment it is asked. A read takes a second or two and costs nothing. It needs a subscription login, so the windows are `null` on an API key or when the tool does not answer within 30 seconds. Claude Code's windows are also reported in the `PromptWindowsEvent` (its `Windows`) of every prompt.

## Testing a tool

`IPrompter.Test(options)` finds out whether the tool of the options is actually usable: it runs the tool with the smallest prompt that will do ("Reply with the digit 1.") on the cheapest model the library knows of (Claude Code's `haiku`, the model Codex describes as fast, the first model OpenCode lists) at the lowest setting of each choice, without tools, with a minimal system prompt where the tool allows one, and with nothing stored. That proves what looking for the command cannot: the tool is installed, signed in (or the key works) and reachable. The answer is a `PromptTestResult` with `IsAvailable`, the reason when not (a missing command, a wrong key, no login, out of quota, the tool ending without an answer) and the subscription `Windows`. The test ends as soon as the tool has answered, and it has no time limit of its own, so a slow tool such as a local model that has to load is waited for; a caller that wants a bound passes a cancellation. A tool that does not work is a result and not an exception; only cancellation throws. A test costs about a thousand tokens on Claude Code and ten thousand on Codex, whose own instructions are large, which is a few cents at most.

## Branching and rewinding

`session.Fork()` makes a second session that starts with everything the first has said and done and then goes its own way, so two approaches can be tried from one point. `session.Fork(entry)` does the same from an earlier point: the branch holds the conversation up to the end of the exchange (a prompt and everything the AI did to answer it) that an entry of the history belongs to, so it never starts in the middle of a tool call. Both wait for the prompt that is running, give the branch the configuration of the original (the workspace and tools shared), the same API key, and an empty cache of its own (and, when the original works in a folder the library made, an empty folder of its own), and leave the original as it is. Claude Code branches by itself: the branch is stored as pointing at the original conversation (and the message to stop at), and its first prompt resumes that with the tool's fork option, which makes a new conversation and reports its identifier like any first prompt. Codex forks the thread at once. A branch of a session that has had no prompt is just a new session with the same configuration (a branch at an entry of it is an error), and a loaded branch that has not been prompted yet checks that the conversation it was made from still exists.

`session.Rewind(entry)` takes the session itself back to the end of that exchange, keeping its identifier: the later exchanges are no longer part of its conversation and the next prompt carries on from the entry. It is a branch the session moves to, so the original conversation stays in the tool's storage (it is not deleted, and is still there to open with the tool itself), and a kept process is replaced. Claude Code cannot branch at a point from before the conversation was compacted (the summary replaced those messages), and refuses it with `PromptSessionException` when it is chosen. A provider that cannot branch at a point throws `NotSupportedException`.

`session.Move(workspacePath)` moves the session to another workspace folder and keeps its conversation, doing what the tool needs for that: Claude Code looks a conversation up by the folder it ran in, so the library copies the conversation to the new folder (the old copy stays, and a delete removes every copy), while Codex and OpenCode need nothing. A `null` is a choice: the folder the library makes for the session, which is made again (empty) if it was deleted. A workspace path is an existing folder, keeps the system access switch of the session and is stored like the one given to `Create`, so a load brings it back. The call waits for the running prompt, keeps the library identifier and the other settings, ends a kept process (which ran in the old folder) and leaves the old folder alone. It fails with `DirectoryNotFoundException` or `PromptSessionException` before changing anything.

`prompter.Move(id, workspacePath)` does the same for a stored session that is not open, without loading it, so it also works when the folder the session was in is already gone (a session cannot be loaded then, since its folder must exist): the caller moved the project on disk, or elsewhere, and tells the library where it is now. The library tracks the place of a workspace and moves nothing itself: the tool's conversation is brought to the new folder as above, the folder the library made for a session that had none is removed, and the link is stored with the new folder, the settings and the system access switch as they were. It fails before changing anything with `DirectoryNotFoundException` for a folder that does not exist, `PromptSessionNotFoundException` for an unknown session and `PromptSessionException` when the tool's conversation cannot be found to bring along; an open session should be disposed first.

## History

`session.GetHistory()` reads the conversation as the provider stored it, from the end of its file, as an `IAsyncEnumerable<PromptHistoryEntry>` newest first (it reads lazily, so taking the first few entries of a long conversation is cheap): the user's prompts, what the AI wrote, and its tool calls and their results, each with the time where the provider stored one. An entry is an event with a place: `entry.Event` is a `PromptInputEvent` for a prompt or message the AI was given, and otherwise the same `PromptMessageEvent`, `PromptToolCallEvent` and `PromptToolResultEvent` that the event stream reports (with the identifiers that tie a call to its result), so one piece of code can show live output and history; `entry.Text` is the text of whichever it is. The input events are history only: the event stream does not report them, as its watchers gave the input themselves. Cut it with the usual operators (`await session.GetHistory().Take(50).ToListAsync()`). The library keeps no history of its own, so this reads the tool's file, which is why a prompt appears as the tool stored it (text files folded in, images as a marker) and why it is empty for a session without a prompt. A branch that has not been prompted yet shows the conversation it was made from. Each entry carries its place in the stored conversation as a `PromptHistoryPoint` (`entry.Point`: the byte offset of its record and its place in that record), which `Fork` and `Rewind` take; the session methods take points so that a place can be kept without keeping the entry, and extension methods accept an entry for the same calls (`session.Fork(entry)`). `OlderThan(point)` on the history continues with the entries older than one already seen, to page back through a long conversation, and `NewerThan(point)` returns only the entries newer than one already seen and stops reading there, to watch a conversation grow. The places mean something only for the session they came from.

## Instructions

`Instructions` in the configuration are custom instructions for the AI (a persona, rules, a house style), added after the library's own guidance about its tools for every prompt, and stored with the session. They are passed in the system prompt of Claude Code and the developer instructions of Codex, so they shape the work without being part of any prompt. Instructions can be changed at any time, also on a session that was loaded: the next prompt follows the current ones. Both tools keep the instructions a conversation started with when they resume it, so the library does what each tool allows to make a change reach the conversation. Claude Code is told to render its system prompt again on every resume, so the change is a real system prompt change. Codex has no such option; instead the library tells it with a note (see Notes): a developer message that says the instructions have changed and what they are now, or that the earlier ones no longer apply when they are cleared. That note is added when the instructions differ from the ones the session last used, and on the first prompt of a loaded or branched session that has instructions, since the library keeps no record of the ones the conversation began with. A prompt that fails before anything happened does not use the note up, so the next one carries it.

## Notes

`session.Send(input, new PromptSendOptions { Notes = ["the build now passes"] })` gives the AI notes with the input (the files and the notes of an input are `PromptSendOptions`, the base of `PromptRequestOptions`, so `Request` takes the same two), as messages from the application and not as something the user said: that a file was changed by hand, that a deadline moved. Claude Code is given it as a system reminder in front of the user's text and Codex as a developer message before the prompt, so it does not cost an answer of its own, and it stays in the conversation afterwards. Several notes are delivered in the order they were given, once. A note is always sent with an input, so it never waits alone; notes that were not delivered because the work failed to start stays for the next.

## Context and compaction

`session.GetContext()` says how much of the model's context window the conversation fills now (`PromptContext`: `Tokens`, `Limit` and `Used`, a number from 0 to 1), the tool's own instructions and tool descriptions counted in, so that a long conversation can be compacted before it overflows. `session.Compact()` makes the tool summarize the conversation, which frees room: Claude Code continues the compacted conversation under a new session identifier, which the library follows, and Codex compacts the thread. Both use the process the session keeps, and wait for the prompt that is running. Before the first prompt of a Codex conversation there is nothing to report and the context has no tokens and no size; Claude Code reports its instructions and tools even then. Compacting a conversation that is too short to compact fails with the tool's own message.

```csharp
if ((await session.GetContext()).Used > 0.8)
{
    await session.Compact();
}
```

## External MCP servers

`McpServers` of the transient configuration (a name to a `PromptMcpServer`, either `Stdio(command, arguments)` for a program the tool starts or `Http(url, bearerTokenVariable)`) gives the AI the tools of MCP servers that exist already, next to the library's own. The tools are started with only the servers the library names, so the servers in the user's own configuration stay out and these are the only extras. All their tools are allowed without asking, so add only servers that deserve that trust. A secret is named and not given: the bearer token is the name of an environment variable of the host process (Claude Code expands it into the header, Codex reads the variable itself), and the environment variables of a program are passed to the tool as written. The tool starts and talks to the server, not the library, so a server that fails to start only offers no tools. Names follow the tool name rules and are not `liveai`.

## Testing code that uses the library

The `Markwardt.LiveAi.Testing` namespace has fakes of the entry points, so code that uses the library can be tested without a tool, a login or a data folder. `FakePromptSession` answers from a script (`Reply`, `Fail`, `Hang`, and `ReplyWith` for what is not scripted) and records every prompt it was given (`Prompts`); its requests are the real ones, so files, structured answers, options, events, interruption, branching and history behave as in production. `FakePromptSession` and `FakePrompter` take a `TimeProvider` (`time:` and `Time`) that the prompt times run on, so a test can move the clock. `FakePrompter` makes sessions for any setup (and `OnCreate` scripts each one), records the setups it was given (`Created`, `Tests`) and loads, lists and deletes them in memory; its `TestResult` is what `Test` returns. A fake session also records the notes it was told (`FakePrompt.Notes`), counts its compactions (`Compactions`), reports the context a test sets (`Context`), and branches and rewinds at an entry of its history. A prompt without a scripted answer fails with a message that shows the prompt, so a test cannot pass by accident.

## Persistent process

A session keeps the AI's process alive between prompts whenever the tool can, for every built-in tool: it starts with the first prompt and takes the following ones, which saves the start of a process per prompt. A session holds a running process, so dispose it (`await using`) when done; `DisposeAsync` lets a running prompt finish, fails the ones waiting behind it, stores the configuration if it changed and then asks the process to exit (its input is closed and it gets a few seconds before it is ended), while `Dispose` cancels the running prompt and ends the process at once.

The model and its settings are given to the running process with the prompt and never restart it (except for OpenCode): Claude Code is told with control requests before the prompt and Codex takes them with every prompt. The library does end the process in four cases: a prompt is cancelled (its state is unknown), a setting that is passed to the tool when it starts (the instructions, the external MCP servers, the library's tools and the places they are served at) was changed (the process ends in the background once its prompt is done), the schema of a structured prompt changed for a Claude Code process (Codex takes the schema with each prompt), and the process had died on its own. Alternating between output types, or between structured and plain prompts, therefore starts a new Claude Code process each time, while repeating one type reuses it. The next prompt then starts a new one that resumes the same conversation, so none of this loses context.

## State, input and output

A session is a conversation with a state: `Waiting` (idle), `Working` (the AI is busy with input it was given) or `Responding` (the AI is answering a direct request). The session itself is a hot `IObservable<PromptEvent>` (subscribe to it) of everything the main conversation outputs, whoever caused it: messages and their deltas, tool calls and results, usage, subscription windows, interruptions and failures, plus a `PromptStateEvent` whenever the state changes. A watcher gets what happens after it subscribes and nothing is replayed (`session.State` is the current state; `GetHistory` reads the past). It completes when the session is disposed, and work that fails is a `PromptFailureEvent` and does not end it.

`session.Send(input)` gives the AI input at any time except while it is responding, where it throws a `PromptSessionStateException`. Input reaches the AI at once. While the AI is working it is taken into that work (Claude Code and Codex both take input in the middle of their work), and while it waits it starts work; what the AI does with it is seen in the event stream. The `Task` completes as soon as the input has been written to the running AI process, or has been queued when it cannot be written at once (the work is not running a process that takes input, or it ended meanwhile); it does not wait for the AI to act on it, which is what the event stream shows.

## Asking: direct, mixed or in a fork

`session.Request(input, options)` (and `Request<T>`, which is built on it) is for request/response semantics: its answer comes back to the caller (typed with `Request<T>`), and the `Mode` option (`PromptRequestMode`) chooses where the AI answers it. A request is always about one input, which is why it is separate from `Send`.

- **Direct** (the default) asks in the main conversation. The session goes to `Responding` until the AI has answered, the events also go to the event stream, and the request throws a `PromptSessionStateException` unless the session is `Waiting`. This is the work the AI would do for input, with the answer being its output (structured when a schema is given).
- **Mixed** mixes the request into the work the AI does anyway. It is given like input, in `Waiting` or `Working` (`Responding` throws), and into the work in progress,, with a unique identifier, and the AI is asked to answer by calling a `respond` tool with that identifier and, when there is a schema, an answer object that follows it. The tool checks the answer (an object, with the properties the schema requires) and tells the AI what is wrong so that it can answer again. The request completes with one message holding the answer; everything else the AI does stays in the event stream. If the AI ends its work without answering, the request fails. The tool is part of every session's tools (the library's tool server is therefore always started), so a request can join work that is already running, and a request in this mode cannot have a model, reasoning or tools of its own, since it joins work it does not control. Its usage, tool calls and messages are not separated from the work's.
- **Fork** copies the conversation as the tool has stored it (so not what the AI is in the middle of doing) into a session and process of its own, asks there directly, and throws the copy away, deleting what the tool stored for it. It works in any state, nothing it does reaches the event stream, and the main session is untouched. Its usage is not added to the main session's.

## Logging

`new Prompter(dataFolder, logger)` takes an `ILogger` (from `Microsoft.Extensions.Logging.Abstractions`, the library's only package dependency) that its sessions report to. The messages are about what the library does and carry the session identifier: the state changes of a session and the processes and tool servers it starts (debug), input given to work that is running and whether the process took it (debug), a fork, rewind or move (information) and work that failed (warning, with the exception). Prompts, answers, files and tool arguments are never logged. The messages are generated with the `LoggerMessage` source generator, so a level that is not enabled costs a check and nothing more.

## Errors

- `PromptSessionException` - the tool could not be started, or the AI reported a failure (wrong API key, no subscription, out of quota), or a stored link is unreadable.
- A tool's own failure is not an error of the session: it is returned to the AI.
- `PromptSessionOutputException` (a `PromptSessionException`) - the answer to a structured prompt is missing or is not the requested type.
- `PromptToolStartException` (a `PromptSessionException`) - the tool could not be started, typically because it is not installed.
- `ArgumentException` - an output type or schema whose root is not an object, or a tool or MCP server name that is not allowed.
- `PromptSessionNotFoundException` (a `PromptSessionException`) - `Load` for an identifier that is not a session identifier, has nothing stored, or whose tool session is gone (the stored session is kept).
