# Architecture

This document explains the high-level design decisions behind the library's implementation: *why* it's built the way it is, not the class-by-class mechanics of *how*.

## The command line tools do the work, never an SDK

Both providers are driven through their own command line tools (`claude -p`, `codex app-server`), also when an API key is given. The alternatives were calling the model APIs or an agent SDK directly. They were rejected because the point of a session is the tool's agent loop: its file and command tools, its permission and sandbox model, its context handling and its session storage. An API client would have to reimplement all of that and would behave differently with a key than with a subscription. The cost is a dependency on the user having the tools installed, and on parsing their JSON line output (or, for Codex, speaking its JSON-RPC protocol, which is documented by a schema the tool itself generates), which belongs to the tools and can change.

## A process per prompt, or one that stays

By default a prompt gets a process and the process is gone after it, which keeps the library free of process lifetime: a session needs no disposal, survives the host process restarting, and a crashed tool only fails the prompt it was running. The cost is a process start per prompt.

Both tools can instead keep one process and take prompts as they come (Claude Code on its `stream-json` input, Codex as `codex app-server`). That is a session setting (`IsPersistent` in the configuration), not a separate kind of session, because the stored link plus the provider's own stored session already carry the whole conversation: a persistent process is only the per-prompt process with its exit delayed, so it can be ended at any moment (a cancel, a changed flag, a crash, the caller turning it off) and the next prompt resumes from the provider's session with nothing lost. That is also why it is safe to tear it down in the background when the property is turned off, and why a `Load` from another process needs no hand-over of a live process. The price is a running process that someone must end, which is why a session is disposable. The library never ends a persistent process on a timer: keeping it alive is the point of asking for it.

Codex was moved from `codex exec` to its app server for what a process that holds a thread can do and an exec cannot: take the model, the effort and the schema with each turn, interrupt a turn without ending the process, compact the thread, fork it at a turn, report the size of its context, take a message that is not the user's, and stream the text as it is written. The same code path serves a process per prompt and a kept one (the app server is simply started and ended around one turn), instead of two transports to keep alike, and the library no longer copies the tool's files to branch a conversation. The one place `codex exec` remains is the tester, whose job is one cheap prompt with nothing stored.

## Resume through the provider's own session storage

Context between prompts is carried by the provider's stored session, resumed by its identifier on every prompt after the first. The library does not keep histories. Its own storage holds only the mapping from the library's session identifier to the provider's (with the provider and the working folder), and no setting: the caller applies its settings whenever it creates or opens a session, so there is nothing stored to go stale or migrate. That keeps the stored link tiny, makes resumption work across processes with no replay, and means a session also remains usable from the tool itself.

## A library GUID in front of the provider's identifier

Callers hold a GUID the library generated instead of the provider's identifier. The provider's identifier does not exist until a prompt has run (Codex chooses it, Claude is only known from its result) and has a different shape per tool. The stored link maps one to the other and is written as soon as the session is created, so a session can be loaded before its first prompt.

## Dependency injection is a layer over the factories

A provider is built with `new PromptProvider(engine, dataFolder)` (or is one of the two statics), with nothing to register and no dependency on a container, so the library has a single package dependency, `Microsoft.Extensions.Logging.Abstractions`, for the optional logger (`new PromptProvider(engine, dataFolder, logger)`): the abstractions are the types a host's logging already uses, nothing is logged without one, and prompts, answers and files are never logged. There is no service-collection extension and no settings object: what a host would register is the provider, and a host that wants injection registers the one it builds, as a singleton. The alternative of registering every internal service (store, runner, tool host) was rejected: they are implementation details that a host should not be able to swap or depend on, and one provider creates and loads on the same store.

## Structured output through the tools' own schema support

Structured output uses each tool's native schema option (`--json-schema` for Claude Code, the `outputSchema` of a turn for Codex) instead of asking for JSON in the prompt and parsing what comes back. The prompt-only approach needs no provider code and works on a persistent process, but the model can decorate or break the JSON, and the library would have to guess where it starts; with the native option the tool enforces the shape. The cost is provider code (Claude puts the value on its result event, Codex needs a stricter schema) and, for a persistent Claude process, a restart when the schema changes, since the option is fixed at start.

## Tools are served over a local MCP server

Both tools can call out to an MCP server, and that is the only extension point they share, so caller-defined tools are offered through a small MCP server that the library runs inside the caller's process, on a random loopback port. The alternatives were rejected: a stdio helper process would need a second program and a channel back to the host, and Claude Code's own in-process channel (the one its Agent SDK uses) is specific to one tool, only partly documented, and tied to a part of Anthropic's terms this library avoids. A hand-written server (three JSON-RPC methods over HTTP) was chosen over an MCP package and a web host, which would bring a large dependency for a handful of methods.

The server is a door into the caller's process, so it is closed three ways: it only listens on the loopback address, every request needs a random secret that is given to the AI's tool through an environment variable and never on a command line, and it lives only as long as the tools it serves. Tools can still do anything their handlers do, so which tools a session has is the caller's decision: the library cannot keep a promise about code it does not control.

## The library's file tools are the only file access

The AI works on files only through tools the library provides, over an `IStore`, and has no shell unless the caller turns one on. The command line tools' own file tools are not an option, for three reasons: control (the stores are confined for both providers, which Codex's sandbox cannot do for reads; a caller can put the AI on a virtual or remote store or on several; the AI cannot reach anything the library did not offer), uniform behaviour across providers, and cost. The cost was measured on small tasks with the fast models: Claude Code used about a quarter of the tokens and a third of the cost with only MCP file tools, because its own prompt and tool definitions are large, at similar speed; Codex used about two to four times the tokens and one and a half to three times the time, because its model reads back what it changed. Both finished the tasks correctly.

The price is that there is no shell by default, so the AI cannot build, test or run git unless the caller adds a tool for it or enables the shell. That is deliberate: a shell can do anything the library's confinement is there to prevent, and what may run is the caller's decision. The shell is therefore its own explicit switch (`EnableShell`), off by default, rather than something a mount or a tool can imply; it is set again on every session like the other settings, which is why it is an explicit act to turn it on, and it is a library tool like the file tools so that it needs no native tool of either command line tool, whose own shells stay disabled. The tools copy the argument names and behaviour the models are used to (numbered reads, exact-match edits that must be unique), and add what a shell would otherwise do in bulk: replace-all in an edit, and copy, move and delete.

## A working directory is a choice, not a default

The AI reaches exactly what the caller gave it, and nothing is implied. Without a workspace and without mounts a session cannot touch a file. The caller can give the AI a working directory, the `Workspace`, which is any store: relative paths are relative to it, like a shell's current directory, and a store of a folder on disk lets the AI also use the absolute paths of the machine and starts the shell there. The alternative of a session rooted in a folder by default was rejected because that would be an access nobody asked for, and because it makes the common safe case (a conversation, or a conversation with a data store) the one that needs undoing. The tools still need a working directory of their own, and the provider's stored sessions are keyed by it, so each session also gets an empty folder that the AI is told is irrelevant, unless the caller passes a workspace path when creating it: then that folder is both the tools' working directory and the `Workspace`, stored with the link so that a load sets it again, which saves the caller from keeping the path and from setting the workspace after every load.

Whether a path can leave the folder is the disk store's decision (`sandbox`), not the tools': the tools pass an absolute path or one that climbs above the top on as written, and a sandbox refuses it where it is. That keeps one rule in one place, lets a caller open the machine to the AI on purpose (a coding agent in a repository, with the files around it), and keeps the confinement that the other stores and the default give.

More than one store is not a list the tools take: the stores are mounted at relative paths, and a path that starts with a mount's path is inside that store. A mount can be where it is wanted (`my/test`, `docs`), shadows what the workspace has there, and nests inside another. The tools, their paths and the way the AI thinks about files stay the same, and an operation between two stores (copy, move) is just an operation on paths. The alternative of a store argument on every tool was rejected because it makes every call longer and every path ambiguous. Read-only is a property of a store (a wrapper) and not of a mount, so it composes with anything.

## Secrets are not stored

The API key is held in memory by the session and passed to the tool through its environment variable, never on the command line (visible to other users in the process list) and never in the stored link. A loaded session therefore needs the key again.

## Access is enforced where it is

What the AI can change is decided by the stores mounted to the session (a store can be made read-only on its own) and by the tools the caller configures, so the promise is kept by the library's own code for both providers. A session-wide read-only switch was removed: it only hid the writing tools, which a read-only store already refuses at the point of access with a message the AI can read, and for the caller's own tools it could only trust a flag on each. The library does not rely on a command line tool's sandbox, which differs between the two (Claude can be held to its working directory, while Codex's read-only sandbox can read the rest of the machine) and which the library has no control over.

## One stream of events, with the text as a view of it

Everything a tool reports while it works (messages and the deltas of a message being written, tool calls and their results, usage, subscription status) is one stream of `PromptEvent` records, which reaches the caller on `Output` as it happens, and the text a request returns is the messages of it. The alternative of separate callbacks or a side channel was rejected because order matters (a result belongs between the messages around it) and one stream has one cancellation, one failure and one end. Delivery to a watcher goes through a queue of its own with a thread that drains it, because a callback run by the publisher would run under the lock of the session and a slow or re-entrant watcher would stall or deadlock the session; the price is that a watcher sees an event a moment after it happened, in order, and that a slow one only grows its own queue.

Time is a `TimeProvider` that the provider is given and passes to its sessions, requests and loops, so timeouts, retry delays, window polling and loop schedules can be tested with a clock the test moves. The processes of the engines and the tool server wait on the real clock, since they wait on real processes. Providers therefore report a generic "event" next to their replies, and anything the library does not model is dropped, so a tool adding line types still cannot break a session.

## Limits are the request's, enforced by cancellation

A timeout and a window limit are enforced in the request, by cancelling the token the executor runs under, and not by the providers or the session. That makes them work the same for both tools, for every way of asking (ask, stream, events, loops), and without any timer in the provider code: cancelling already ends the tool's process and everything it started. The cost is that a limit is only as exact as a cancellation; the work the tool had started is lost, and its conversation is whatever it had stored by then. Failing with a distinct `PromptLimitException` keeps a limit apart from the caller's own cancellation and from a failure of the AI. Loops add the limits that only a loop has (total time, number of runs, a stop condition) and treat reaching one as a normal end, because a loop that was told when to stop and did so has not failed.

## The subscription status comes from the tools' own commands

Both tools can report the usage of a subscription without a model call, so the provider asks the tool instead of sending a prompt or calling the providers' account endpoints with the tokens the tools store (undocumented, liable to change, and credentials that belong to the tools). Claude Code answers its `/usage` command in non-interactive mode locally, with 0 tokens, but only as text, so the library parses the lines for the session, the week and the week of each model, and their reset times, which it prints in the user's zone by name; the format is the tool's and can change, and a line that no longer matches means that window is missing, or the read fails when none match. Codex's app server (marked experimental) answers a rate limit request over JSON-RPC on standard input and output, with structured windows; the library starts it, asks once and ends it. Both reads start a process, so they take a second or two, which is why a limit polls on an interval the caller chooses. The shares used are the tools' own (a fraction, 0.5 for half, whichever way the tool writes it) and their windows differ by plan, so what is read is a list of windows (a name, a percentage, a length, a read time and a reset time) and not a record with a field per window of each tool, nor a status object around the list: that is the one shape both fit, it lets a limit or a display work on any tool without knowing which it has, and what a window means (a session, a week, a model's week) stays in its name for people to read. The length of a Claude Code window is not reported, so the library fills in the one the tool documents; the window is what makes a pace possible, a percentage used against the share of the window that had passed when it was read, which is the number that tells a caller whether to slow down before the limit is reached. Each window carries its own read time so the pace stays right however old the status is; working it out against the clock would make an old status look slower than it was.

## The tester proves it by asking

Whether a tool works is only known by using it: the command can exist and still be signed out, over quota, or given a wrong key. So `Test` runs the tool with the smallest real prompt and treats any failure as a result with a reason, instead of probing for the command or the login file, which would say nothing about a key or the network and would depend on where each tool keeps its state. The price is a few tokens per test, which is why it is a call the caller makes and not something the library does before each session.

## Branching uses what each tool offers

A branch is a new library session over a copy of the provider's conversation. Claude Code can copy by itself when it resumes (and can stop the copy at a message), so the branch's link holds a pointer to its origin and the point and the tool makes the copy at the first prompt (the library has nothing to copy and cannot get the copy wrong). Codex forks a thread through its app server, also at a turn, and answers with the new thread at once. Both are the tools' own operations, which was preferred to the library copying a conversation file, as it did before: that relied on a file format (an identifier in the header and in the file name) which the tool owns and could change. The alternative of replaying the conversation into a new session would cost tokens and lose the tool's own state. A branch has its own scratch folder and starts with a copy of the original's settings, sharing its tools and mounts as objects, since those are the caller's.

The points of a conversation are the entries of its history, identified by a small value (`PromptHistoryPoint`, the byte offset of the stored record and the place within it) and not by the entry itself, because that is all the providers use to find a place and it lets a caller keep a bookmark without keeping the text; the offset is not an ordinal because an ordinal would need the whole file read to find, while an offset is found by seeking from the end. A branch at one keeps the whole exchange the entry belongs to, because that is the finest point both tools branch at without leaving a half done exchange (a tool call without its result) in the copy. A rewind is a branch the session moves to; it does not delete what comes after, because deleting a person's conversation is not something a library should do as a side effect of going back, and it costs only the space of the original. Claude Code cannot branch at a message the summary of a compaction replaced, so a point from before one is refused when it is chosen and not when the next prompt fails.

## External servers are definitions, not connections

An external MCP server is passed to the AI's tool, which starts or reaches it, instead of being proxied through the library's own server. A proxy would let the library see and gate every call, but it would have to speak the whole protocol to servers of any kind, run their programs, and keep their sessions. Handing the definition over keeps the library small and keeps the servers independent of the host's lifetime, at the price that the library cannot gate their tools (it allows all of them) and cannot tell whether one started. That is also why a definition stores only the name of the environment variable that holds a token: the secret stays where the host keeps it.

## A provider is the public face, an engine is the tool, and a custom engine is only three members

What a caller does with a tool (create, load, list, delete and test its sessions, read its limits) is the same for every tool, so it is one public interface, `IPromptProvider`, and one class, `PromptProvider`, over an `IPromptEngine` that holds what is specific to a tool: how to start it and read what it writes. The split keeps the provider's behaviour (storage, the check that a stored session belongs to this tool, the test) written once, and the engines small. `IPromptProvider.Claude` and `IPromptProvider.Codex` are ready instances with default settings; settings that belong to a tool (its command, its configuration folder) are constructor arguments of its engine (`ClaudeEngine`, `CodexEngine`), so there is no registry and several of the same tool (for two accounts, say) work side by side, each as a provider of its own. Opening up every internal detail so that a caller could add a tool was rejected: an engine the caller adds (an `IPromptEngine` that implements only `Identifier`, `CreateStart` and `Parse`, the rest having defaults) only has to describe a process for one prompt and read one output line, which is all the two built-in ones do apart from options of their own. Only the engine's name is stored with a session, which is why a provider only loads the sessions of its own tool. The contract hides what is specific to the built-in tools (the stream-json framing, the JSON-RPC conversation, persistent processes) and keeps the rest optional with defaults that do nothing, so a first engine is short. The cost is that a custom engine cannot stay alive between prompts, compact, report its context or branch at a point, or take documents natively; that was left out until a tool needs it.

## Retrying only what cannot have been seen

A retry repeats a prompt, so it must not repeat what the caller already received. The request retries only when the failure comes before its first event, which covers the failures that are worth retrying (a rate limit or an overloaded service answers at once) and keeps messages and tool calls from appearing twice. Deciding from the error type, with a predicate to replace it, was chosen over parsing the text of failures, which belongs to the tools and changes; the one error that is known not to pass, a tool that is not installed, has its own type for that reason.

## Budgets are checked between prompts

The tools report what a prompt used when it ends, so a token or cost budget cannot stop a prompt part way without the library estimating tokens itself. It is checked before each prompt (or send of a loop) and the one that passes it is finished: the overshoot is at most one prompt, which was preferred to a made-up estimate. The budget belongs to a session and not to the provider: a total over several sessions needs shared state that every session adds to and checks, which makes sessions depend on each other, and a caller that wants one adds up the `Usage` of its sessions itself. A guard that works while a prompt runs exists for the thing that really runs away, the number of tool calls, which the library sees as it happens.

## A session has a state and an output, and a request chooses where it runs

A conversation with an AI that works for a while is not request/response: the AI is busy, new things arrive, and the caller mostly wants to watch. So the session is a state (waiting, working, responding) with one output stream of everything the main conversation does, and input that can be given at any time. The old model, where every call was a request that waited its turn, hid that and made "tell it something while it works" impossible without a request to carry the answer.

Request/response is still wanted (a typed answer, a timeout, retries, limits), and it is a different thing: it needs an answer that belongs to one input. It therefore stays as a request with a mode that says where the AI answers it. Direct uses the main conversation and makes the state `Responding`, which refuses input meanwhile: a typed answer from a turn that is also receiving other input could not be told apart. Mixed accepts that the answer is mixed into other work and finds it by what the AI hands to a tool with a unique identifier, which gives a correlated, validated answer without parsing the output. The tool is offered in every session because a tool cannot be added to work that has started, and a request that must wait for the next work is not mixed into anything; the price is a tool server for sessions that have no other tool. Fork asks in a copy so that nothing mixes, at the cost of a process and of not seeing work in progress. They answer different needs, which is why they are options and none is the default for everything.

There are no rounds of input: input is given at once and is taken into the work the AI is doing, because that is what a person does when they add a thought to a task in progress, and a queue that waits for the work to end would make the AI act on stale instructions. Both built-in tools can take it mid-work (Claude Code as a further user message on its stream-json input, Codex with `turn/steer`), so they do. An engine that cannot (a custom one) falls back to holding the input until the work ends, which keeps the contract and loses only the immediacy. The fork's usage and the failures of a mixed request are kept apart from the main output deliberately, so that `Output` stays what the main conversation did.

A request is a call with an optional options record (`PromptRequestOptions`) and not a builder. The builder made every option a method that returned a new object, which was eager about validation but needed a second type to hold what the first had collected, could not be kept as a value and passed around, and made the loop hold a request that was tied to a session. The options that every input has (files and a note) are a base record, `PromptOptions`, which `Send` takes; `PromptRequestOptions` derives from it and adds what only a request has (the schema, the mode, whether it interrupts), so `Send` and `Request` cannot drift apart on what they share and a request's options can be handed to `Send`. How the AI works (the model, the reasoning, the tools, the mounts) and the limits (the timeout, the window limit, the retries, the limit on tool calls) are deliberately not options of a request but settings of the session. A per-request model or toolset made the same session behave differently from one call to the next, restarted a kept process for the difference, and had no meaning for input given with `Send`, which joins work that is already running; with the settings in one place, every piece of input runs under the same rules, a loop or a mixed request cannot ask for something the running work cannot take, and a caller that wants a different setup for one prompt changes the configuration around it. A record is a value: it is built once, kept, changed with `with`, handed to a loop, and read when the call starts, which is also when it is checked. The core of the session is one call, `Request`, which returns the text of the answer (a result with the events and the usage would repeat `Output` and `Usage`, which already carry them as they happen; the loop, which adds up the usage of its sends for its budget, reads them from the session through an internal interface); the plain text, the typed answer and the loops are extension methods on top of them, so a type that implements the session (the fake) gets them for free and the typed support cannot differ between implementations.

The limits of a session are one record (`PromptSessionLimits`) and not five properties because they answer one question, when a request stops or repeats, and are checked together: assigning a record either takes all of it or nothing, and `with` changes one part. A history entry is an event with a place (`PromptHistoryEntry.Event`, `Point`, `Time`) and not a record of its own with a role, so a program that renders `Output` renders the history with the same code; the only event that history has and `Output` does not is the input the AI was given, since the watchers of `Output` gave it themselves. A non-object answer type is wrapped in an object with one `value` property inside the library because both tools demand an object at the root, which is a limit of the tools and not something a caller should shape a type around.

## Interrupting keeps the conversation

Cancelling a prompt ends the tool's process and throws, and that is right for a caller that is done with it. Correcting the AI needs the opposite: the work so far stays in the conversation and the next prompt carries on from it. A running process of either tool can be asked to stop (Claude Code with a control request, Codex with `turn/interrupt`) and then takes the next prompt as it is; a tool driven by a process per prompt is ended and the conversation is resumed from what the tool stored, which the design already relies on for every prompt. Either way the interrupted prompt completes normally, so the caller sees what was written, and the event that says it was interrupted tells it from one that finished.

## Overlays and audits are stores

Letting the AI change things and deciding afterwards, and logging what it did, are both just stores that wrap another, so every tool, mount and session setting works with them unchanged and there is no new notion of a pending change in the session. An overlay keeps what was written in memory and which paths of the store underneath are hidden by a deletion, so a deletion never has to touch what is underneath and a deleted folder that is made again starts empty. Applying is not atomic (the stores underneath have no transactions), so a failure leaves the overlay as it was and it can be applied again. An audit is reported after the access, with its error, because a log of what happened is more useful than a log of what was attempted, and its function failing does not undo an access that was made.

## The fakes use the real request

Test doubles for the request pipeline that behave differently from the real one would test the double. The fake session therefore does not implement it: it runs the real one (`PromptRequester`), over an executor that answers from a script, so options, limits, retries, loops, events and typed answers are the production code, and only the process is replaced. The fake keeps the parts of a session that a test of the caller's code can depend on (configuration with its checks, the state and the modes, usage and budget, interruption, branching, history) and none that need a machine (files, ports, processes).

## Hooks see the library's tools, not the tool's own

The caller can approve, refuse and log the calls of the tools the library offers, which are served in the caller's process and so can wait for an answer before they run. Calls of an external MCP server are made by the AI's tool directly, so the library could only watch them go by, and a hook that cannot stop anything is a log, which the events already are. One pair of hooks for every tool (before and after) replaced a shell approval: the shell is one tool among them, and approving "commands" and nothing else would have left the file tools and the caller's own with no way to be held back. The hooks are given the event records that `Output` reports, so one description of a call serves the log and the approval, and they are read when a call arrives, like the shell approval was, so changing them applies to a prompt that is running.

## Notes, context and compaction go through the same process as a prompt

A note, a read of the context and a compaction are operations on the conversation, so they use the process a prompt would (the kept one, or one opened for the operation) and the same setup, which makes the numbers the tool reports the ones a prompt would meet. A note travels with the next prompt, which both tools take as a message that is not the user's (a system reminder, a developer message), instead of sending a prompt of its own, which would cost a turn and an answer nobody asked for.
