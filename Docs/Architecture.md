# Architecture

This document explains the high-level design decisions behind the library's implementation: *why* it's built the way it is, not the class-by-class mechanics of *how*.

## The command line tools do the work, never an SDK

Every provider is driven through its own command line tool (`claude -p`, `codex app-server`, `opencode serve`), also when an API key is given. The alternatives were calling the model APIs or an agent SDK directly. They were rejected because the point of a session is the tool's agent loop: its file and command tools, its permission and sandbox model, its context handling and its session storage. An API client would have to reimplement all of that and would behave differently with a key than with a subscription. The cost is a dependency on the user having the tools installed, and on parsing their JSON line output (or, for Codex, speaking its JSON-RPC protocol, which is documented by a schema the tool itself generates, and for OpenCode its HTTP API), which belongs to the tools and can change.

## One process that stays, because ending it loses nothing

A session keeps one process of its tool and takes prompts as they come (Claude Code on its `stream-json` input, Codex as `codex app-server`, OpenCode as its server), whenever the tool can. An earlier design made that a switch with a process per prompt as the default, which kept the library free of process lifetime: no disposal, survival of a host restart, a crashed tool only failing its prompt. It was removed because the switch bought little: the stored link plus the tool's own stored session already carry the whole conversation, so a kept process is only the per-prompt process with its exit delayed, and it can be ended at any moment (a cancel, a changed setting, a crash, a dispose) with the next prompt resuming from the tool's session and nothing lost. That is also why a `Load` from another process needs no hand-over of a live process. What the always-kept process costs is a running process that someone must end, which is why a session is disposable, and the library never ends one on a timer: keeping it alive is the point.

Codex was moved from `codex exec` to its app server for what a process that holds a thread can do and an exec cannot: take the model, its settings and the schema with each turn, interrupt a turn without ending the process, compact the thread, fork it at a turn, report the size of its context, take a message that is not the user's, and stream the text as it is written, and the library no longer copies the tool's files to branch a conversation. The one place `codex exec` remains is the tester, whose job is one cheap prompt with nothing stored.

## Resume through the tool's own session storage

Context between prompts is carried by the tool's stored session, resumed by its identifier on every prompt after the first. The library does not keep histories. Its own storage holds the mapping from the library's session identifier to the tool's (with the tool and the working folder), the options the session was created with and the session's configuration (capability, effort, the switches, instructions, image options). The configuration is stored so that a session comes back as it was and `Load` needs only an identifier: the stored options say which tool and where it is found, so no caller has to remember them. Anything only meaningful to a live object stays out: the workspace path and sandbox of the options (kept on the link instead), the tools, MCP servers, asker and cache. Configuration is written when a prompt starts and when the session is disposed with a change, not on every assignment, so a burst of changes is one write. The link stays small, resumption works across processes with no replay, and a session also remains usable from the tool itself.

## A library GUID in front of the provider's identifier

Callers hold a GUID the library generated instead of the provider's identifier. The provider's identifier does not exist until a prompt has run (Codex chooses it, Claude is only known from its result) and has a different shape per tool. The stored link maps one to the other and is written as soon as the session is created, so a session can be loaded before its first prompt.

## Dependency injection is a layer over the factories

A prompter is built with `new Prompter(dataFolder)`, with nothing to register and no dependency on a container, so the library has a single package dependency, `Microsoft.Extensions.Logging.Abstractions`, for the optional logger (`new Prompter(dataFolder, logger)`): the abstractions are the types a host's logging already uses, nothing is logged without one, and prompts, answers and files are never logged. There is no service-collection extension and no settings object: what a host would register is the prompter, and a host that wants injection registers the one it builds, as a singleton. The alternative of registering every internal service (store, runner, tool host) was rejected: they are implementation details that a host should not be able to swap or depend on, and one prompter creates and loads on the same store.

## Structured output through the tools' own schema support

Structured output uses each tool's native schema option (`--json-schema` for Claude Code, the `outputSchema` of a turn for Codex) instead of asking for JSON in the prompt and parsing what comes back. The prompt-only approach needs no provider code and works on a persistent process, but the model can decorate or break the JSON, and the library would have to guess where it starts; with the native option the tool enforces the shape. The cost is provider code (Claude puts the value on its result event, Codex needs a stricter schema) and, for a persistent Claude process, a restart when the schema changes, since the option is fixed at start.

## Tools are served over a local MCP server

All the tools can call out to an MCP server, and that is the only extension point they share, so caller-defined tools are offered through a small MCP server that the library runs inside the caller's process, on a random loopback port. The alternatives were rejected: a stdio helper process would need a second program and a channel back to the host, and Claude Code's own in-process channel (the one its Agent SDK uses) is specific to one tool, only partly documented, and tied to a part of Anthropic's terms this library avoids. A hand-written server (three JSON-RPC methods over HTTP) was chosen over an MCP package and a web host, which would bring a large dependency for a handful of methods.

The server is a door into the caller's process, so it is closed three ways: it only listens on the loopback address, every request needs a random secret that is given to the AI's tool through an environment variable and never on a command line, and it lives only as long as the tools it serves. Tools can still do anything their handlers do, so which tools a session has is the caller's decision: the library cannot keep a promise about code it does not control.

## The library's file tools are the only file access

The AI works on files only through tools the library provides, over an `IStore`, and has no shell unless the caller turns one on. The command line tools' own file tools are not an option, for three reasons: control (the stores are confined for both providers, which Codex's sandbox cannot do for reads; a caller can put the AI on a virtual or remote store or on several; the AI cannot reach anything the library did not offer), uniform behaviour across providers, and cost. The cost was measured on small tasks with the fast models: Claude Code used about a quarter of the tokens and a third of the cost with only MCP file tools, because its own prompt and tool definitions are large, at similar speed; Codex used about two to four times the tokens and one and a half to three times the time, because its model reads back what it changed. Both finished the tasks correctly.

The price is that there is no shell by default, so the AI cannot build, test or run git unless the caller adds a tool for it or enables the shell. That is deliberate: a shell can do anything the library's confinement is there to prevent, and what may run is the caller's decision. The shell is therefore its own explicit switch (`IsShellAllowed`), off by default, rather than something a tool or the workspace can imply; it is stored with the session like the other settings, but turning it on is always an explicit act, and it is a library tool like the file tools so that it needs no native tool of either command line tool, whose own shells stay disabled. The tools copy the argument names and behaviour the models are used to (numbered reads, exact-match edits that must be unique), and add what a shell would otherwise do in bulk: replace-all in an edit, and copy, move and delete.

## A working directory is a choice, not a default

The AI reaches exactly one folder and the cache, and nothing else is implied. Every session has a workspace: the caller can give one when creating the session (the workspace path), or the library makes a folder for the session in its own data folder, named after the session, which is kept until the session is deleted or moved elsewhere. Relative paths are relative to it, like a shell's current directory, and with the default sandbox every path stays inside it; without the sandbox the AI also uses the absolute paths of the machine, and the shell starts there. Every session also has a cache, an in-memory store that is lost when the session is disposed, for what should not be kept. The alternative of a session with no folder at all was rejected because the tools need a working directory anyway, the provider's stored sessions are keyed by it, and a scratch folder in the temp directory lost what the AI made. Running the tool in the workspace is also what lets it find the instruction files of the project (`CLAUDE.md`, `AGENTS.md`) the way it does when started there; the library does not read or inject them itself. A session whose workspace was made by the library has a folder that nobody else knows about, which is why the library deletes it; a folder the caller gave is never deleted.

Whether a path can leave the folder is the disk store's decision (the `IsSandboxed` setting of the session, which is stored and can be changed at any time, rebuilds the store), not the tools': the tools pass an absolute path or one that climbs above the top on as written, and a sandbox refuses it where it is. That keeps one rule in one place, lets a caller open the machine to the AI on purpose (a coding agent in a repository, with the files around it), and keeps the confinement that the other stores and the default give.

The cache is not a second store argument of the tools: it sits in the one path space the tools see, at the path `CACHE:`, and a path that starts with it is inside the cache. The tools, their paths and the way the AI thinks about files stay the same, and an operation between the workspace and the cache (copy, move) is just an operation on paths. The alternative of a store argument on every tool was rejected because it makes every call longer and every path ambiguous. The cache is a plain in-memory store and not a folder on disk so that it is lost when the session ends with nothing to clean up, and its name is one that is unlikely to be a folder of the workspace.

## Secrets are stored with the session, and only there

The API key is passed to the tool through its environment variable, never on the command line (visible to other users in the process list), and never logged. It is stored with the session, in the options and in the OpenAI image options, so that a loaded session runs on the same key and `Load` needs only an identifier. The alternative of leaving it out made a loaded session silently run on another account, or fail, until the caller supplied the key again. The cost is a secret in plain text in the session file, which is why the file is created readable by the current user only (Linux and macOS; on Windows it has the permissions of the data folder), which is the same protection the tools give their own sign in files. A caller that cannot accept that does not give the library a key and relies on the tool's sign in. The records that carry a key (the session and image options, and the library's internal records of them) are printed with the key hidden as `***`, since a record's `ToString` would otherwise put it into logs and failure messages; equality still compares it.

## Access is enforced where it is

What the AI can change is decided by the workspace, the cache and the tools the caller configures, so the promise is kept by the library's own code for both providers. A session-wide read-only switch was removed: it only hid the writing tools, and for the caller's own tools it could only trust a flag on each; a caller who wants the AI to read without changing gives it a copy of the folder, or puts the data in the cache. The library does not rely on a command line tool's sandbox, which differs between the two (Claude can be held to its working directory, while Codex's read-only sandbox can read the rest of the machine) and which the library has no control over.

## One stream of events, with the text as a view of it

Everything a tool reports while it works (messages and the deltas of a message being written, tool calls and their results, usage, subscription status) is one stream of `PromptEvent` records, which reaches the caller in the event stream as it happens, and the text a request returns is the messages of it. The alternative of separate callbacks or a side channel was rejected because order matters (a result belongs between the messages around it) and one stream has one cancellation, one failure and one end. Delivery to a watcher goes through a queue of its own with a thread that drains it, because a callback run by the publisher would run under the lock of the session and a slow or re-entrant watcher would stall or deadlock the session; the price is that a watcher sees an event a moment after it happened, in order, and that a slow one only grows its own queue.

Time is a `TimeProvider` that the prompter is given and passes to its sessions and requests, so the times of prompts and the pauses of the web search can be tested with a clock the test moves. The processes of the engines and the tool server wait on the real clock, since they wait on real processes. Providers therefore report a generic "event" next to their replies, and anything the library does not model is dropped, so a tool adding line types still cannot break a session.

## The subscription status comes from the tools' own commands

Claude Code and Codex can report the usage of a subscription without a model call (OpenCode has no subscription, so it reports no windows), so the library asks the tool instead of sending a prompt or calling the providers' account endpoints with the tokens the tools store (undocumented, liable to change, and credentials that belong to the tools). Claude Code answers its `/usage` command in non-interactive mode locally, with 0 tokens, but only as text, so the library parses the lines for the session, the week and the week of each model, and their reset times, which it prints in the user's zone by name; the format is the tool's and can change, and a line that no longer matches means that window is missing, or the read fails when none match. Codex's app server (marked experimental) answers a rate limit request over JSON-RPC on standard input and output, with structured windows; the library starts it, asks once and ends it. Both reads start a process, so they take a second or two, which is why a limit polls on an interval the caller chooses. The shares used are the tools' own (a fraction, 0.5 for half, whichever way the tool writes it) and their windows differ by plan, so what is read is a list of windows (a name, a percentage, a length, a read time and a reset time) and not a record with a field per window of each tool, nor a status object around the list: that is the one shape both fit, it lets a limit or a display work on any tool without knowing which it has, and what a window means (a session, a week, a model's week) stays in its name for people to read. The length of a Claude Code window is not reported, so the library fills in the one the tool documents; the window is what makes a pace possible, a percentage used against the share of the window that had passed when it was read, which is the number that tells a caller whether to slow down before the limit is reached. Each window carries its own read time so the pace stays right however old the status is; working it out against the clock would make an old status look slower than it was.

## The tester proves it by asking

Whether a tool works is only known by using it: the command can exist and still be signed out, over quota, or given a wrong key. So `Test` runs the tool with the smallest real prompt and treats any failure as a result with a reason, instead of probing for the command or the login file, which would say nothing about a key or the network and would depend on where each tool keeps its state. The price is a few tokens per test, which is why it is a call the caller makes and not something the library does before each session.

## Branching uses what each tool offers

A branch is a new library session over a copy of the provider's conversation. Claude Code can copy by itself when it resumes (and can stop the copy at a message), so the branch's link holds a pointer to its origin and the point and the tool makes the copy at the first prompt (the library has nothing to copy and cannot get the copy wrong). Codex forks a thread through its app server, also at a turn, and answers with the new thread at once. Both are the tools' own operations, which was preferred to the library copying a conversation file, as it did before: that relied on a file format (an identifier in the header and in the file name) which the tool owns and could change. The alternative of replaying the conversation into a new session would cost tokens and lose the tool's own state. A branch has its own automatic workspace folder (or the same folder the caller gave) and starts with a copy of the original's settings, sharing its tools as objects, since those are the caller's, and with an empty cache of its own.

The points of a conversation are the entries of its history, identified by a small value (`PromptHistoryPoint`, the byte offset of the stored record and the place within it) and not by the entry itself, because that is all the providers use to find a place and it lets a caller keep a bookmark without keeping the text; the offset is not an ordinal because an ordinal would need the whole file read to find, while an offset is found by seeking from the end. A branch at one keeps the whole exchange the entry belongs to, because that is the finest point both tools branch at without leaving a half done exchange (a tool call without its result) in the copy. A rewind is a branch the session moves to; it does not delete what comes after, because deleting a person's conversation is not something a library should do as a side effect of going back, and it costs only the space of the original. Claude Code cannot branch at a message the summary of a compaction replaced, so a point from before one is refused when it is chosen and not when the next prompt fails.

## External servers are definitions, not connections

An external MCP server is passed to the AI's tool, which starts or reaches it, instead of being proxied through the library's own server. A proxy would let the library see and gate every call, but it would have to speak the whole protocol to servers of any kind, run their programs, and keep their sessions. Handing the definition over keeps the library small and keeps the servers independent of the host's lifetime, at the price that the library cannot gate their tools (it allows all of them) and cannot tell whether one started. That is also why a definition stores only the name of the environment variable that holds a token: the secret stays where the host keeps it.

## A prompter is the public face, options say which tool, and the engines are internal

What a caller does with a tool (create, load, list, delete and test its sessions) is the same for every tool, so it is one public interface, `IPrompter`. What names a tool is an empty abstract `PromptSessionOptions` whose derived records (Claude, Codex, Ollama) hold only the parameters that tool needs; the prompter chooses the engine by the type of the options, in one place, instead of the options knowing how to build an engine, so the options stay plain data that serializes, and `Load` and `Delete` take only an identifier because the stored link holds the options. Below it an internal provider per tool and place holds the behaviour written once (storage, the check that a stored session belongs to this tool, the test, the model choice) over an internal engine that holds what is specific to a tool: how to start it and read what it writes. Engines, models and settings stay internal: letting callers add a tool, list models or pick a reasoning level was dropped because each tool names these differently and the caller only ever wants the same two things, how capable and how hard-working. The cost is that a new tool means a new options record and engine in the library, not a class in the caller; that is acceptable while the tools are few.

## The model is chosen from a capability and an effort

Callers set `Capability` (`Fast`, `Balanced`, `Strong`, `Max`) and `Effort` (`Low`, `Medium`, `High`, `Max`), and the library selects the model and its reasoning level when a prompt starts. Four capability tiers instead of three because the tools have a model between the standard and the largest (Claude Code's `haiku`, `sonnet`, `opus` and `fable`). The tier is found by the names of the models, which is a heuristic, so it degrades gracefully: the nearest tier is used when one is missing (the higher on a tie), unnamed models are spread over the list in order, and a list that cannot be read falls back to models the library knows. The list is read once a minute per key, since asking a tool costs a process. Effort maps to the level of the same name among the ones the model offers, the highest for `Max`, otherwise the levels are spread, because the tools offer different numbers of levels. The alternative of exposing models and settings was rejected as above; a caller that needs a specific model is not served, deliberately.

## A route to local models through an agent with an HTTP server

Claude Code and Codex are driven for what they are, and neither supports running a model that is not the vendor's (Anthropic says plainly that it does not support routing Claude Code to non-Claude models; Codex documents a local mode but gives no guarantees), so local models are reached through OpenCode, a command line agent built to use any model, driven like the others as a tool and not as a library. OpenCode was chosen over the other candidates because it was the one that did everything the library needs in a test against a scripted model: a remote MCP server with a bearer header, resume by identifier, fork, list, delete, cancel.

It is driven through the HTTP server it starts itself (`serve --stdio`) and not through its Agent Client Protocol server (`acp`), although the protocol is a standard and the HTTP API is marked experimental. The protocol has no way to do three things the library offers: steer input into a prompt that runs (a second prompt is refused while one is active), fork at an earlier point, and rewind. The HTTP API has all three (steer and queue delivery, fork before a message), and the protocol's server cannot be attached to one the library runs, so the two cannot be mixed. The risk of the experimental label was measured, not assumed: across 44 releases in seven weeks the paths of the operations the engine uses did not change (only their operation names, once), and the changes of the last ten days were all additions. The engine therefore reads responses leniently (what it needs, ignoring the rest) and is written for 2.x; a move to another version should be checked against the real binary, since the tests run against a fake server.

Three things in OpenCode 2.x shaped the engine. By default it exposes the tools of an MCP server to the model only as JavaScript in a sandbox, so the engine turns that off per server. It loads MCP servers in the background and only when the project is first used, so the first prompt can reach the model before any tool exists; the engine loads the project and polls the servers until they are connected (and fails if its own tool server is not, since a silent session without tools is worse than an error). And a model that errors is retried forever with growing waits, so the engine treats the first retry as the failure. The first two were found with a scripted model that was told to call a tool and was never offered it, and the second also appeared as an intermittent miss on a slow, busy machine, which is why a failed connection is retried and the start-up timeout is raised.

## A session has a state and an output, and a request chooses where it runs

A conversation with an AI that works for a while is not request/response: the AI is busy, new things arrive, and the caller mostly wants to watch. So the session is a state (waiting, working, responding) with one output stream of everything the main conversation does, and input that can be given at any time. The old model, where every call was a request that waited its turn, hid that and made "tell it something while it works" impossible without a request to carry the answer.

Request/response is still wanted (a typed answer, a timeout, retries, limits), and it is a different thing: it needs an answer that belongs to one input. It therefore stays as a request with a mode that says where the AI answers it. Direct uses the main conversation and makes the state `Responding`, which refuses input meanwhile: a typed answer from a turn that is also receiving other input could not be told apart. Mixed accepts that the answer is mixed into other work and finds it by what the AI hands to a tool with a unique identifier, which gives a correlated, validated answer without parsing the output. The tool is offered in every session because a tool cannot be added to work that has started, and a request that must wait for the next work is not mixed into anything; the price is a tool server for sessions that have no other tool. Fork asks in a copy so that nothing mixes, at the cost of a process and of not seeing work in progress. They answer different needs, which is why they are options and none is the default for everything.

There are no rounds of input: input is given at once and is taken into the work the AI is doing, because that is what a person does when they add a thought to a task in progress, and a queue that waits for the work to end would make the AI act on stale instructions. Every built-in tool can take it mid-work (Claude Code as a further user message on its stream-json input, Codex with `turn/steer`, OpenCode by queueing), so they do. The fork's usage and the failures of a mixed request are kept apart from the main output deliberately, so that the event stream stays what the main conversation did.

A request is a call with an optional options record (`PromptRequestOptions`) and not a builder. The builder made every option a method that returned a new object, which was eager about validation but needed a second type to hold what the first had collected, and could not be kept as a value and passed around. The options that every input has (files and a note) are a base record, `PromptSendOptions`, which `Send` takes; `PromptRequestOptions` derives from it and adds what only a request has (the schema, the mode, whether it interrupts), so `Send` and `Request` cannot drift apart on what they share and a request's options can be handed to `Send`. How the AI works (the capability, the effort, the tools) is deliberately not an option of a request but a setting of the session. A per-request model or toolset made the same session behave differently from one call to the next, restarted a kept process for the difference, and had no meaning for input given with `Send`, which joins work that is already running; with the settings in one place, every piece of input runs under the same rules, a mixed request cannot ask for something the running work cannot take, and a caller that wants a different setup for one prompt changes the configuration around it. A record is a value: it is built once, kept, changed with `with`, and read when the call starts, which is also when it is checked. The core of the session is one call, `Request`, which returns the text of the answer (a result with the events and the usage would repeat the event stream and `Usage`, which already carry them as they happen; tests that need the whole result read it from the session through an internal interface); the plain text and the typed answer are built on them as extension methods, so a type that implements the session (the fake) gets them for free and the typed support cannot differ between implementations.

A history entry is an event with a place (`PromptHistoryEntry.Event`, `Point`, `Time`) and not a record of its own with a role, so a program that renders the event stream renders the history with the same code; the only event that history has and the event stream does not is the input the AI was given, since the watchers of the event stream gave it themselves. A non-object answer type is wrapped in an object with one `value` property inside the library because both tools demand an object at the root, which is a limit of the tools and not something a caller should shape a type around.

## Interrupting keeps the conversation

Cancelling a prompt ends the tool's process and throws, and that is right for a caller that is done with it. Correcting the AI needs the opposite: the work so far stays in the conversation and the next prompt carries on from it. A running process of either tool can be asked to stop (Claude Code with a control request, Codex with `turn/interrupt`) and then takes the next prompt as it is; a tool driven by a process per prompt is ended and the conversation is resumed from what the tool stored, which the design already relies on for every prompt. Either way the interrupted prompt completes normally, so the caller sees what was written, and the event that says it was interrupted tells it from one that finished.

## The fakes use the real request

Test doubles for the request pipeline that behave differently from the real one would test the double. The fake session therefore does not implement it: it runs the real one (`PromptRequester`), over an executor that answers from a script, so options, events and typed answers are the production code, and only the process is replaced. The fake keeps the parts of a session that a test of the caller's code can depend on (configuration with its checks, the state and the modes, usage, interruption, branching, history) and none that need a machine (files, ports, processes).

## Notes, context and compaction go through the same process as a prompt

A note, a read of the context and a compaction are operations on the conversation, so they use the process a prompt would (the kept one, or one opened for the operation) and the same setup, which makes the numbers the tool reports the ones a prompt would meet. A note travels with the next prompt, which both tools take as a message that is not the user's (a system reminder, a developer message), instead of sending a prompt of its own, which would cost a turn and an answer nobody asked for.
