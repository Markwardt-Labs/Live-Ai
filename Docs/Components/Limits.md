# Limits and status

`PromptLimitWatch`, the providers' status readers (`ClaudeUsage`, `CodexLimits`) and the limits of `PromptLoop<TReply>` stop work that has gone on too long or that would use up a subscription, and read the subscription's state to decide.

## Per-prompt limits

A request under a timeout or a window limit (the session's settings, plus a loop's) starts a `PromptLimitWatch` when it is asked and gives the executor the watch's token instead of the caller's. The token is linked to three sources: the caller's token, a timer for the timeout, and a source the status watcher cancels. Which of them ended the work is decided afterwards from the sources themselves, in a fixed order: the caller's cancellation is passed on unchanged (a caller who cancels must not see a limit error), then a failed status read, then a reached window limit, then the timer. The request catches the cancellation at the two places it can surface (reading the files and moving through the events) and throws what the watch explains. A prompt that ends by itself is never affected; the watch is disposed when the enumeration ends, which cancels and awaits the status watcher so that no read of the status outlives the prompt.

The status watcher is a background loop of its own: read the status through the executor, call the caller's function, wait the interval. The first read starts at once and runs beside the prompt instead of before it, so a limit costs no start-up delay, and the price is that a prompt may begin before a limit that is already reached cancels it. A read that fails stops the prompt with that failure, because a limit that cannot be checked and is ignored would be no limit.

## Reading the status

Each provider reads its own status (`IPromptEngine.GetWindows`), and a session reaches it through its engine, so that a request can read the status without knowing which one it runs on. Each read starts a short process, through the runner's general exchange (write lines, read lines, end the process when the caller stops reading), under a 30 second limit of its own that is reported as a failure, not as the caller's cancellation. Reads are independent processes, not serialized.

For Claude Code it runs `claude -p /usage --output-format json --no-session-persistence`, which prints a result whose text has a line for the current session and one for the week of all models, each with a percentage (read as a fraction from 0 to 1) and a reset time such as `Oct 26, 6:50pm (America/Chicago)`; a time without a date means its next occurrence, a date without a year the nearest one that is not long past, and the zone is looked up by name (the local zone when unknown); lines for single models are ignored. Text with no such line means a login without limits. For Codex it runs `codex app-server`, sends `initialize`, `initialized` and `account/rateLimits/read`, takes the answer with id 2 (an error answer, or limits without a window, fails the read) and ends the process.

## Loop limits

`PromptLoopLimits<TReply>` is read once, when the loop is made, and checked in the same places the loop already stops. The timeout is a source of its own that is linked with the disposal source into one token for the sends and the waits, so it ends a send in progress and a wait alike; the run records whether it was the disposal or the timer, and the task completes normally in both cases. The maximum number of runs and the until function are checked right after a reply is published, so the last reply is always seen by the watchers. The window limit is passed with each send to the session's internal collector, which adds it to the session's own limits for that send (the loop's replaces the session's window limit while it is set), and a status-limit failure of a send (from that or from the session's) ends the loop with its own stop reason instead of faulting it, while a timeout of the request still faults it, since that is a send that failed. `StopReason` is written by the one task that runs the loop, before the replies are completed or failed, so a watcher that sees the end can already read why.

A typed loop is the same class with a function that reads each answer into the type; the request supplies the schema and the reader, so a loop publishes values and `Until` receives the same values.

## Retries, tool calls and budgets

The retry loop is in the request, around the executor's sequence: it counts attempts, remembers whether anything was reported, and when a failure comes first, waits (under the same token as the limits, so a timeout or a cancellation ends the wait with the right error) and starts the sequence again. The tool call count is checked on each tool call event before it is passed on, and the failure is thrown by the request, which disposes the executor's sequence and with it ends the process. Budgets compare a `PromptUsage` with the limits: the session adds the usage of each prompt as the events pass and checks before the next turn; a loop adds up the usage of the result of each send and checks after publishing the reply, so the last reply is not lost.

## Waiting for the subscription to reset

A loop with `WaitForWindow` turns the stop of a window limit into a wait. The exception of a prompt stopped by the window limit carries the windows that reached it (`PromptLimitException.Windows`), and the caller's function chooses from them the window to wait out: the library cannot tell which window the limit was about (a plan has a session, a week and a week for each model, and a model that is used up has nothing to do with a limit on the session), and guessing from which windows are full waited for the wrong one. The loop waits until the reset of the chosen window plus a margin, and sends again. The first window read of the next send runs the caller's limit again, so if the limit still holds the function is asked again and the loop waits for the next reset. A function that returns nothing, or a window without a reset in the future, ends the loop with the window limit, as without the option, so a limit that cannot be waited out does not turn into a busy loop. `ResumesAt` says until when the loop waits, and the wait is part of the loop's timeout.
