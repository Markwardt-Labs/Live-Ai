# Engines

`ClaudeEngine`, `CodexEngine`, `OpenCodeEngine`, `ClaudeProcess`, `CodexProcess`, `OpenCodeProcess` and `TurnRunner` turn a stored session and a prompt into a running command line tool and its output into events. An engine (`IPromptEngine`) describes the process and reads what it writes; the public `PromptProvider` owns the stored sessions and gives a session its engine; `TurnRunner` owns the process; a process object (`IPromptProcess`) talks to a tool that holds a conversation.

## Two ways to drive a tool

A tool is driven either by one process per prompt or through a process that holds the conversation. Per prompt (a custom provider that cannot keep a process): `CreateStart` builds the process from the `PromptEngineStart` (the stored record, the API key, the schema and the library's tool server turned into plain values), the session's working folder is its working directory (which also scopes the tool's own session lookup on resume), and the prompt is written to standard input (so its length and content never meet command line quoting or limits) and read back as lines by `TurnRunner`.

Through a conversation process (Codex, Claude Code and OpenCode, whenever the engine reports `CanPersist`): the provider starts the tool with `CreatePersistentStart`, `TurnRunner.Open` launches it, and the provider's `Attach` wraps it in the object that takes prompts (`Run`), compacts (`Compact`), reports the context (`GetContext`), interrupts and stops, and `Steer` takes input while a prompt is running. A tool with such a process gets one opened for the work and disposed after it unless the session is persistent, so one code path serves both settings, and the model, its settings and the schema of the answer travel with each prompt (`PromptInput`) and are not part of the process (except for a tool that reports `StartsWithModel`, which takes them when it starts and gets a new process when they change).

## The tool's own web search

An engine whose tool can search the web reports `NativeSearch`, and the session passes `Search` to its start when `EnableSearch` is on. Claude Code is started with `--tools WebSearch --allowedTools ...,WebSearch` (permission mode `dontAsk` keeps everything else refused), and Codex with `web_search: "live"` in the config of `thread/start` and `thread/resume`; a Codex `webSearch` item becomes a `web_search` tool call and its result. OpenCode reports no native search (its own is limited to its hosted providers), so a session on it gets the library's `search_web`.

## The model and its settings

A session runs the model it was given (`Configuration.Model`) and passes the values of that model's settings (`Configuration.ModelSettings`) to the engine as `PromptEngineStart.Model`/`Settings` and `PromptInput.Model`/`Settings`. The library has no vocabulary of its own for them (no tiers, no reasoning levels): each engine says what it offers in `GetModels` and reads the setting identifiers it published, so an application can list a model's settings without knowing the tool.

Neither the model nor the effort is fixed when a Codex or Claude Code process starts. Codex takes `model` and `effort` with every turn. Claude Code takes them as arguments for a process per prompt, and a running process takes `{"subtype":"set_model"}` and `{"subtype":"apply_flag_settings","settings":{"effortLevel":...}}` control requests, which `ClaudeProcess` sends, and waits for the answer to, before it writes a prompt whose model or effort differs from what it last used. So `SameProcess` leaves both out for them, and changing them never restarts a kept process. OpenCode is the exception: its model providers and context size are part of the configuration it is started with, so it reports `StartsWithModel` and a changed model or setting gets a new process.

## Access

Claude Code runs with `--tools ""`, which removes every built-in tool including its shell, and `--permission-mode dontAsk`, so the only tools are the ones offered over MCP and each is named in `--allowedTools`; there is no bypass of permissions to need. Codex runs `codex app-server` with `--disable shell_tool` and a read-only sandbox (`sandbox_mode` and, on the thread, `sandbox`), which refuses the patch tool that `--disable shell_tool` does not remove (no config key was found that does); the approval policy is `never`, and the MCP server is set to `default_tools_approval_mode="approve"`, because otherwise Codex refuses a tool that does not claim to be read-only, in a read-only sandbox, before it reaches the library. The sandbox does not restrict the library's tools, which run in the caller's process. The model is told its sandbox is read-only, and the descriptions of the tools are what make it use them to write.

Claude Code also gets `--strict-mcp-config` in every mode, so only the server the library passes is loaded and not the user's own servers, project servers or account connectors. Without it every session saw them (and paid for their tool definitions: a trivial prompt cost about 260,000 input tokens on a machine with several connectors). Codex has no equivalent that leaves the user's configuration otherwise alone, so servers in the user's Codex configuration are still loaded.

Neither tool is ever run without its permission system or its sandbox being on, because the AI has no native tool left that would need it to be off. A Codex sandbox that cannot start on the host (for example a container that forbids user namespaces) does not matter to the library's tools, which run in the caller's process.

## Guidance

Both tools are also told, in a short instruction (`--append-system-prompt` for Claude Code, the `developerInstructions` of the thread for Codex), how they can work, in one of several forms: no tools at all; only the caller's tools and no access to files; the shell tool alone or with the file tools; or file tools, which says that there is no shell, that the folder the tool runs in is empty and not its workspace, and that files are reached only through the file tools of the MCP server. When there is a workspace the text says that a path is relative to it unless it starts with the path of a mounted folder, and says whether the shell starts in the workspace (a workspace that is a folder on disk) or in an empty scratch folder; without one, that every path starts with the path of a mounted folder. It is needed because the tools' own model of the world is a working directory with files in it: with the session's empty working folder and a sandbox that is described as read-only, Codex sometimes concluded that it could not touch any files and gave up without calling a tool (one run in six in a test of two folders), and with the instruction it did not (eight runs in eight; Claude Code four in four). Custom instructions are appended after it, under a heading that says whose they are. When external MCP servers are configured the text names them too, and with no library tools it no longer claims the AI has no tools. Codex's sub-agents are disabled as well, since a sub-agent is a second chance to lose sight of the tools.

## Notes and changed instructions

A note (the `note` of `IPromptSession.Send`) travels with the input in `PromptInput.Notes`, and the provider puts it into the conversation the way the tool takes something that is not the user's. Claude Code gets a `<system-reminder>` text block in front of the user's text in the same message (or in front of the plain text for a process per prompt), which is how the tool's own messages to the model are marked; the note stays in the conversation like any message. Codex gets one `thread/inject_items` request per note before `turn/start`, an item of type `message` with the role `developer`, which the app server appends to the model-visible history and writes to the thread's file. A custom provider gets the note as a line of text in front of the prompt. Both real tools were checked to follow a note ("from now on answer in French") on the prompt it came with and on the later ones, with a process per prompt and with a kept one.

Both tools keep the instructions a conversation started with when it is resumed. Claude Code records its system prompt on the first request and reuses it verbatim on every resume, even when a later launch passes different text; `--system-prompt-snapshot off` makes it render the prompt again for each request, and the provider passes it on every resume (and branch), so a changed `--append-system-prompt` takes effect with nothing else to do. Codex ignores the instructions of `thread/resume` too (checked), and offers nothing like that option, so `KeepsInstructions` makes the session turn a change of instructions into a note ("the instructions have changed, follow these instead", or "the earlier ones no longer apply") for the same injection. A model sometimes still answers in the old way when the user's prompt itself asks for it, since the note is an instruction like any other.

## Attachments

Claude Code takes images and PDFs as content blocks in a user message, which only its `stream-json` input accepts, so a prompt with such files is written as one message line on the process input, the files first and the text last, as base64, like any other prompt. Codex takes images only, as `localImage` items of the turn's input that name a file. The session writes the images to a folder of its own inside the session's working folder for the length of the prompt and removes it afterwards, also when the prompt fails or is cancelled. Text files never reach the provider as files: they are written into the prompt text, in a fence longer than any run of backticks in the file, so a file cannot end its own block. Which types a provider takes is its own answer (`Accepts`), so the rule that sorts a file into "shown", "put into the prompt" or "refused" is the same for both. Both tools were checked with real images, a PDF and a resumed session, including that the AI remembers an image sent in an earlier prompt.

## Reading output

Claude Code writes one JSON object per line. Codex's app server writes one JSON-RPC message per line: responses to the requests of the library, notifications, and now and then a request of its own. The providers keep these kinds of event: the provider's session identifier, a reply, the end of the turn, a failure, and an "event" that carries a text delta, a tool call, a tool result, the usage of the prompt or the subscription status. Everything else (thinking, for one) is ignored, as is a line that is not JSON of the expected shape, so a tool adding new line types does not break a session.

- Claude: a reply is the text blocks of an assistant message that does not belong to a subagent, and a tool call is a `tool_use` block of it (a text before it is flushed first, so the order of the blocks is kept; a name `mcp__server__tool` is split into its server and tool). A `tool_result` block of a user message is the result of a call. A `stream_event` whose `content_block_delta` carries `text_delta` is a delta of the main conversation (`--include-partial-messages` asks for them in every mode; the whole `assistant` message follows them). A `rate_limit_event` carries the subscription windows (`five_hour` and `seven_day`, as a fraction used and a reset time, which is kept as the fraction). The `result` line also carries the usage and the cost; the cost is the total of the process so far, so a kept process reports the difference to the previous prompt. The session identifier comes only from a successful `result` line, which also ends the turn; an error `result` is a failure, and its session is not recorded because an invalid first turn may never have created one.
- Codex: the thread comes from the answer to `thread/start` or `thread/resume` and is reported once `turn/start` is answered (a thread without a turn has no file yet, and a link to it would look deleted); `item/agentMessage/delta` is a delta; a completed `agentMessage` item is a reply; an `mcpToolCall` item is a call when it starts and its result when it completes; `thread/tokenUsage/updated` carries the usage of one model call (`last`) and the turn's usage is their sum (the cached part is taken out of the input count), which is why only updates that name the running turn count; and `turn/completed` ends the turn, with the error of a failed one (a message that is itself a JSON error body is unwrapped to the inner message) and no failure for an interrupted one. A request of the app server (an approval, a question) is answered with an error, since the library has decided what the AI may do and nobody is there to ask. The older `codex exec` output is still read for the tester, which runs one cheap prompt with nothing stored.

## Structured output

A prompt may come with a JSON Schema whose root is an object. Claude Code takes it inline (`--json-schema`, fixed when its process starts, so a prompt with a different schema, or none, needs a new kept process) and reports the value as `structured_output` on its result line, with no assistant text of its own; the provider turns that value into the last reply, so every provider ends a structured turn with its answer as the last reply. Codex takes the schema as the `outputSchema` of each turn (`SchemaPerTurn`, so a kept process is never tied to one) and its last agent message is the answer, already JSON.

Codex's API runs schemas in strict mode, which refuses a schema whose objects lack `additionalProperties: false` or do not list every property as required, and the .NET schema exporter writes neither. So the Codex provider rewrites the schema before use: in every object schema, at any depth, including array items, `anyOf` branches and `$defs`, it sets `additionalProperties` to `false` and `required` to all the properties. Property maps are walked as maps of schemas, so a property that happens to be named `properties` or `type` is treated as a property. Claude Code's schema is passed as it is.

## The Claude Code process

`ClaudeProcess` runs `claude -p --input-format stream-json` and writes one JSON line per prompt (`Frame`) until its input is closed. It writes a frame, reads lines until the provider reports a finished or failed turn, and stops there, leaving the process waiting for the next frame. A failed turn (an API error, for example) ends the turn but not the process. If the output ends first, the process died: the exit and its error output become the failure. Whatever way a prompt's enumeration ends without a finished turn (cancellation, an error, the caller stopping early), the process is killed along with everything it started, because it would still be working on the prompt. Disposing closes the input and waits three seconds for a clean exit before killing it.

Input can be given while a prompt runs (`Steer`): the process writes a further user message, and Claude Code merges it into the work that is running, so the work still ends with a single `result`. The process starts with `--replay-user-messages`, which makes the tool echo each user message it has taken into the work (`isReplay`); that is what tells the reader how many messages the next `result` will cover. It counts the messages it has written that were not echoed yet, and only a `result` with none outstanding ends the prompt, so a message written just before the tool finished is still answered instead of being lost or left to confuse the next prompt. A failed `result` always ends it. Once no prompt is running, `Steer` returns `false` and the session queues the input. A failed `result` while a steered message is still unechoed ends the process: the tool may go on with that message, and its output would otherwise be read as the answer to the next prompt.

Everything else is a control request on the same input, answered by a control response with the same `request_id` that the process reads before it goes on (a minute at most, then it is killed and the operation fails): `set_model` and `apply_flag_settings` for the model and the effort; `get_context_usage`, whose answer has the tokens the conversation takes (`totalTokens`: the system prompt, the tool descriptions, the memory files, the skills and the messages, not the room kept free) and the size of the window (`maxTokens`), which works on a process that was just started on a stored conversation, before any prompt; and the interrupt. Compacting is the slash command `/compact` as a user message: the tool summarizes the conversation, writes a boundary line and continues in a new session, so the result line reports a new session identifier, which the session records like it does after any prompt. The first prompt in a compacted conversation still sees what the summary kept (checked).

## The Codex app server

`CodexProcess` runs `codex app-server` and speaks to it in lines. It sends `initialize` and `initialized` when it is first used, then `thread/start` (with the working folder, the approval policy, the sandbox and the developer instructions) or `thread/resume` for a stored thread, and a turn is `turn/start` with the input items, the model, the effort and the schema. Requests are answered by id; notifications that arrive while it waits for an answer are kept and read by the turn. The thread is created lazily, at the first operation, so asking for the context of a session that was never prompted costs a process but writes nothing.

`turn/steer` adds input to the turn that runs (it needs the identifier of that turn, which is why it returns `false` before one has started); the process writes it without waiting for the answer, because the answer arrives on the same output the turn is read from, and a note goes in first as a `thread/inject_items` developer message. `turn/interrupt` stops the turn that runs and the app server finishes it with the status `interrupted`; the process and the thread go on. `thread/compact/start` makes the app server run a compaction as a turn of its own and announce it with `turn/completed`. The size of the context comes from the `thread/tokenUsage/updated` notification: its `last` is the last model call, whose total is what the next call starts from, and `modelContextWindow` is the size of the window; the app server sends one on resume for a conversation that has turns, so the read waits a few seconds for it and reports nothing when none comes (a thread with no turn).

## Process lifetime

`TurnRunner` reads standard error in the background so a full pipe cannot stall the tool, and reports it only when the process exits non-zero without the provider having reported a failure; that is the case of a tool that rejects its arguments or crashes. A failure to write because the process already exited is ignored, since the exit status then explains it. Whatever way the enumeration ends (completion, error, cancellation, or the caller stopping early), the process and everything it started are killed in a `finally`, so no tool outlives its prompt.

## External MCP servers

The servers of the session's configuration are passed beside the library's own. Claude Code gets them all in the one `--mcp-config` document (`stdio` with command, arguments and environment; `http` with the address and, for a token variable, an `Authorization: Bearer ${VARIABLE}` header that the tool expands itself) and `mcp__<name>` in `--allowedTools`, which allows every tool of the server. Codex gets `-c mcp_servers.<name>.*` overrides on the app server (command, arguments and environment, or address and `bearer_token_env_var`) and the same approval mode as for the library's server. No tool ever sees a secret in a command line: only names of variables are passed.

## Branching

Claude Code branches when it resumes: a record that points at a conversation to branch from is started with `--resume <id> --fork-session`, which makes a new conversation and reports its identifier on the first result, and from then on the record resumes that one. A branch at a point adds `--resume-session-at <message id>`, with the id of a message of the conversation: the new one holds the messages up to it, and the original is untouched (checked). The point is found in the stored file: the entry is located by its position, the turn it belongs to is the stretch from the prompt before it to the next prompt (a user line with text, not one that only holds tool results), and the id is that of the last assistant line of the stretch, so a branch never ends in the middle of a tool call. A point from before a compaction is refused, since the tool cannot resume at a message that the summary replaced.

Codex branches with `thread/fork` in a short app server of its own, which answers with the new thread at once (nothing is copied by the library any more): without `lastTurnId` the fork holds the whole conversation, and with it the fork holds the turns up to and including that one. The turn of an entry is found in the rollout: a forward read keeps the id of the last `task_started` line at or before the entry's position. This was checked with the real tool, including that a fork at the first turn does not know what the second turn said.

A rewind is a branch that the session itself moves to: it stores the new provider session (or the origin and the point) in its own link and ends a kept process, which held the old conversation. The original conversation stays in the tool's storage, since deleting a conversation that a person might still want is not something a library should do without being asked.

## History

Both tools store the conversation as JSON lines that the providers read directly. Claude Code's file holds user and assistant entries whose content is text or blocks (text, tool use, tool result, image, document); sub-agent and meta entries are skipped. Codex's holds many record types, and the history uses the user and agent messages and the end of each MCP call (which has the tool, the arguments and the result in one record); its own internal scripting calls are not shown. A line that cannot be read is skipped.

## History from the end of the file

Both tools append to a JSON lines file, so the newest entries are at its end. `ReverseLineReader` reads the file backwards in blocks, splits it into lines at line feeds in bytes (so a character that crosses a block is never cut) and gives each line with the byte offset at which it starts; the providers turn a line into its entries, last first, and give each entry that offset and its place in the line as its `Point` (a `PromptHistoryPoint`, which is also what an engine's `Branch` receives, and from which only the offset is used to find the turn). A page of the newest entries therefore reads only the end of the file, and the session stops enumerating as soon as it has enough or reaches the entry it was asked to stop at. A last line that is still being written is not valid JSON and is skipped. `ForwardLineReader` reads the same lines from the start with the same offsets, which is how a branch finds the turn of an entry.

## Interrupting

Claude Code takes a control request on its input, `{"type":"control_request","request_id":...,"request":{"subtype":"interrupt"}}`, answers with a control response, ends the turn that was running with an error result (`error_during_execution`, `aborted_streaming`) that carries what was written, and then takes the next message in the same process. The process writes that frame; the response line is ignored, and the error result is swallowed by the session because it knows it asked. Codex takes `turn/interrupt` with the thread and the running turn, also in a process opened for one prompt. Sending a second message to a running Claude process does not interrupt it: the message is queued and runs after the turn, so there is no shortcut around the control request. A tool driven by a process per prompt has no such request, so for it the session ends the process, which the resume-from-storage design makes harmless.

## Deleting a conversation

Claude Code's conversation is a file `<id>.jsonl` under its projects folder, with a folder of the same name for sub-agent output; deleting both and then the project folder if it is empty removes everything a session made, since each library session has a project folder of its own (named after its scratch folder). Codex's is a rollout file under dated folders, and the dated folders that become empty are removed up to the sessions root.

## The OpenCode server

`OpenCodeProcess` runs `opencode serve --stdio --port 0`, the HTTP server of OpenCode 2.x, and talks to it with requests and a stream of server-sent events. With `--stdio` the server picks a free port, reports it as one JSON line on standard output, and ends when its standard input closes, so it dies with the process that started it even if that is killed; without it the server ignores a closed input and would be left behind. A random password (`OPENCODE_SERVER_PASSWORD`, made by the engine for each start) protects it with basic authentication, and every request names the working folder of the session in the `x-opencode-directory` header.

Opening reads the address, subscribes to `/api/event` first (so no event is missed), waits for the tools, then creates the session (`POST /api/session`) or looks up the stored one (`GET /api/session/{id}`, whose 404 becomes the failure of the request). The tools are waited for because OpenCode connects to its MCP servers in the background and a prompt sent before they are connected is given none: `GET /api/mcp` loads the project, which starts the connections, and is polled until every server is out of `pending`. A server that is `failed` is asked to connect again (up to twice) through the API, and the library's own server, which carries the file tools, the shell and `respond`, is required: if it cannot be connected the request fails, because the AI would otherwise run without any tool and say so only in its answer. An external server of the session that never connects does not hold the prompt back. OpenCode's own start-up timeout for a server is raised to thirty seconds in the configuration, so a slow machine does not fail the connection in the first place.

What the tool is allowed to do is decided entirely by the configuration it is started with, given inline in `OPENCODE_CONFIG_CONTENT` so that no file of the user's is written or read for it. The MCP servers of the session (the library's own first) are added with `codemode: false`, because by default OpenCode 2.x hides the tools of a server behind a JavaScript sandbox that the model must write code for, which small local models do badly; the permissions are one rule that denies everything and one rule per server that allows `server_*`, which leaves the model nothing but the session's tools (OpenCode's own file, shell and web tools are off, so the library's tools are the only way to reach the machine); the guidance and the instructions of the session are a file named by the hash of its text in a folder under the temporary folder, listed under `instructions` so that they become part of the system prompt, which is why a change of instructions needs only the new process the session already starts for it. Tokens travel in environment variables that the configuration refers to (`{env:NAME}`), never in the text of the configuration. OpenCode drops a model whose limits are incomplete without a message, so the engine always gives both the context and the output limit.

A prompt is `POST /api/session/{id}/prompt` with the text and, for each image, a `files` entry with a data URI. Its output is read from the events of the session: `session.text.delta` and `session.text.ended` are the deltas and the whole message; `session.tool.input.started` gives the name of a call (split into the server and the tool by the names of the servers the session started it with), `session.tool.called` the call with its input, and `session.tool.success` or `session.tool.failed` the result; `session.step.ended` carries the tokens and the cost of each model call, which add up to the usage of the prompt, and the last one is the size of the context, with the window taken from `GET /api/model`; `session.execution.succeeded` and `session.execution.interrupted` end the prompt and `session.execution.failed` fails it. A model that errors is not failed by OpenCode but retried again and again with growing waits (`session.retry.scheduled`), so the first retry is taken as the failure: the request fails with its message and the work is interrupted, and the library's own retry decides whether to ask again. A schema has no field in the API, so it is put into the text of the prompt, and an answer wrapped in a code fence is unwrapped.

The model and its variant are set with `POST /api/session/{id}/model` when a prompt asks for something other than what is set. The variant is the `variant` setting of a model, which only models that OpenCode lists variants for have; a model without one is never given a variant.

Input is steered into a prompt that runs with `delivery: "steer"`: the server takes it at the next step of the same turn (after a tool call, say), so the answer covers both and the turn ends once (`Steer` is `false` when nothing is running, and the session then queues the input). Interruption is `POST .../interrupt`. Compaction is `POST .../compact`, whose events end with `session.compaction.failed` (a failure, with the reason: a model whose summary does not follow OpenCode's template fails it) or with the end of the execution. The context of a process that has not prompted yet (a stored session that was just loaded) is read from the last answer of the exported conversation, with the window from the server.

A branch or a rewind to a point is a fork before a message: the engine exports the conversation, finds the first input after the exchange of the point, and runs `opencode api --standalone POST /api/session/{id}/fork` with `{"before": id}` (no body field when the point is in the last exchange, which copies everything). The point of a history entry is the time of its message in milliseconds and the index of the entry in it. These, the deletion (`opencode session delete`), the history (`opencode session export`) and the test (`opencode run --standalone --format json`, prompt on standard input, whose lines `Parse` turns into the reply and the end) are commands that need no running process; `--standalone` keeps them from leaving the background service that OpenCode 2.x otherwise starts. A tool whose models are not reachable keeps retrying, so the test reports it unavailable only when the tool itself says so or ends (it has no time limit of its own). OpenCode has no subscription limits, so it keeps the default of no windows.

The engine offers three kinds of model. The models of the servers on this machine it was given (`localServers`, Ollama on its usual address by default) are listed live, with the identifier `provider/model` (`ollama/...` for Ollama on its usual port, `local-<port>` for another server). The models of the `OpenCodeModelProvider`s it was given are listed as they are described. The rest come from OpenCode's own configuration (`opencode api --standalone GET /api/model`), without its built-in hosted free models, which are not on this machine. A model of a local server is added to the configuration when a process starts for it, and the context size is that of its `context` setting: the server decides how large a context it gives the model (for Ollama, its `OLLAMA_CONTEXT_LENGTH`), so the setting has to match for OpenCode to know when the context is full. The setting's default is the size a loaded model reports, and otherwise 4096, which is what Ollama uses on most graphics cards unless it is told otherwise. OpenCode lists no reasoning variants for a local model, so a local model offers the context setting only.

## Models and their settings

Listing the models is on the engine (`GetModels`, with the API key the list is for): a model is a choice of the session, not data the engine is built with, so no engine is needed before the models can be chosen. A tool that is not installed, a server that is not running and an answer that cannot be read all give an empty list, so "not installed" and "no models" look the same and `IPromptProvider.Test` is what tells them apart. The provider keeps a list for a minute per API key, and asks the tool again once when a stored session names a model the list lacks.

Each tool lists what it can. Claude Code is asked with the `initialize` control request of its stream-json protocol, which answers with the models its own picker shows and, for each, the effort levels it accepts; no tokens are spent, and its `default` entry is left out since it names one of the others. Codex prints its catalog (`codex debug models`), of which the models it marks visible are kept, with their reasoning efforts, the one it prefers as the default, and whether they take images. A setting is a list of choices ordered from the lowest to the highest, a toggle or a number in a range, with a default; values are text. Fast mode and turning thinking off are not offered yet, since how Claude Code applies them is not settled.

A stored session keeps its model and the values of its settings (nothing else), written when a prompt starts with something other than what is stored. When it is loaded the tool is asked for the models once and the stored values are brought up to date: a setting the model no longer has is dropped, a value it no longer accepts goes back to the default, and a new setting gets its default. A model that is no longer listed (after one fresh asking) is not kept: the session starts without one and has to be given another. When the tool cannot be asked at all the stored model is kept as it is, and checked once at its first prompt.

Names are not validated when a model is chosen from outside the list: a model that does not exist fails at the first prompt, with the tool's own message.

## Custom engines

`IPromptEngine` has defaults for everything but `Identifier`, `CreateStart` and `Parse`, so an engine a caller writes is the simple kind: it receives the `PromptEngineStart` (built by the session from the stored record: the guidance text and the instructions as one string, the schema parsed from its text, the library's MCP server first with its secret and the external servers after it), never offers a conversation process (so compaction, the context and a branch at a point are not supported for it, and the session reports that with `NotSupportedException`), has accepted attachments written as files for the length of the prompt, gets the prompt as plain text on standard input with the notes of the session in front of it, and branches only when it implements `Branch`. The built-in engines are public classes whose constructors take the command, the configuration folder and the models of the tool (every argument is optional, so `new ClaudeEngine()` is the usual setup), and they read their own subscription status (`GetWindows`), as a list of `PromptWindow`s, the same for every engine. A provider matches the identifier stored with a session against the identifier of its engine and refuses another one.
