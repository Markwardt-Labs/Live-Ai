# File tools

`IStore`, `DiskStore`, `MemoryStore`, `MountedStore`, `StorePaths` and `PromptLibraryTools` give the AI the library's own way of working on files: a small store interface, the disk and memory implementations, and the tools built over any implementation. The stores are internal except for the interface, which is public because the files of a session (`IPromptSession.Workspace`) are one. The tools are served to the AI like a caller's tools; this component is what is behind them.

## The store interface

Five operations: list a folder (as an asynchronous sequence of entries, optionally everything below it, an entry is a path relative to the folder that was listed, also when it is not recursive), open a file as a stream of bytes, create a folder (with its parents; nothing happens if it exists, a file in the way is an error), delete, move. Reading and writing are one operation because they are one thing to a file system: a mode (`StoreOpenMode`) says whether the file must exist, whether it is made, whether its content is kept, and which way the stream goes, and that keeps a store from having to implement a read, a write, an append and an edit as four separate paths. Streams make the store indifferent to what a file holds and to its size: nothing is read into memory unless the caller does it. The modes are `Read` (an existing file, readable only), `Open` (an existing file, readable and writable, its content kept and the position at the start, for editing in place), `Create` (a new file, writable; anything already there, file or folder, is an error and nothing is replaced), `Replace` (writable, made if missing, existing content discarded) and `Append` (writable, made if missing, positioned at the end). The write modes make the folders they need; `Read` and `Open` fail for a file that does not exist, and a path that is a folder is an error for the write modes and a missing file for the read ones. A store may allow more than a mode needs (a memory stream is also readable in `Replace`) but never less, and what was written is stored by the time the stream is disposed. The text of a file is not an operation: `ReadText` and `WriteText` are extension methods over the streams, decoding UTF-8 (or the encoding of a byte order mark, with undecodable bytes replaced) and encoding UTF-8 without a byte order mark. Everything else the AI can do is built from these once, in `PromptLibraryTools`, so a store of any kind (disk, memory) implements five methods and gets numbering, search, glob and edits for free. A relative path reaching it from the tools is already normalized: relative to the root of the store, `/` separated, with no `.` or `..` segments, and the empty string for the root itself. An absolute path, or one that climbs above the root, is passed on exactly as the AI wrote it (see Paths), and it is the store that says what it means. Its exceptions' messages are the tool errors the AI reads, so they say what went wrong.

## Paths

One resolver cleans every relative path (`StorePaths`): redundant slashes and `.` segments disappear and `..` is resolved, giving the simplest spelling, which is empty for the top; a path that climbs above the top has no spelling. The tool layer turns backslashes into `/` and then resolves the path; a path that is absolute or has no spelling is not an error there but is sent on unchanged, so that the store the path ends up in decides: a store for files that are not on disk reads a leading `/` as the root and refuses a path that climbs, a sandboxed disk store refuses whatever is outside its folder, and a disk store without a sandbox takes it. The mounted store and `Copy` resolve what they receive again, so a caller going around the tools gets the same answer. Resolving twice is deliberate: protections that compare a path with "the cache itself" are only sound if every spelling of that path has been reduced to the same one, and a check on the raw string once let `.liveai-cache/.` and `.liveai-cache//` past the guard on a mount's root.

## The disk implementation

`DiskStore.Open` makes a `DiskStore` for a folder, which must exist. A relative path is relative to the folder, and an absolute path is a path on the machine; `sandbox` (the opposite of the session's `IsSystemAccessAllowed`) says what is reachable. In a sandbox (the default) every path is resolved and refused if it ends up outside the folder, the absolute ones included, so an absolute path inside the folder is simply another spelling of the relative one. Links are followed segment by segment before the check, so a link inside the folder that points outside is refused, and a link that points inside works; the folder itself is resolved the same way, so one that is itself a link is used as its target. Without a sandbox nothing is refused for where it is: the folder is only where relative paths start, and an absolute path or one that climbs above it is taken (the root of the machine is still protected from being deleted, moved or copied over, since that is never meant). Reading opens the file shared with other readers, and every writing mode takes it exclusively, which keeps a write from being read half done (so a write fails while a reader still has the file open, and streams are disposed promptly). Writing in place keeps the permissions of the file. delete takes a file or a folder with everything in it, move never replaces its destination, and the folder itself can be neither deleted nor moved. A move is a relocation of the file or folder on the disk, so it keeps the contents, timestamps and empty folders, and the source is checked before anything is created for the destination. Moving a folder into itself is refused with a message that does not show host paths.

## The tools

- **`list_directory`** lists one folder, folders first with a trailing `/`.
- **`find_files`** matches a glob. A pattern without `/` matches file names at any depth and one with `/` matches the whole path; `**` crosses folders. At most 1000 results.
- **`search_files`** is a regular expression over file contents, returning `path:line:text`, optionally limited to a folder or a glob, with an ignore-case flag. At most 200 matches; binary files (a NUL character) are skipped, `.git` is not searched, long lines are shortened, and the pattern has a five second limit.
- **`read_file`**, like `edit_file` and `search_files`, reads a file into memory as text, which the tool layer limits to 10 MB (a larger file is refused by the first two and skipped by search); the store itself has no limit. It returns lines numbered `number<TAB>text`, 2000 lines by default with `offset` and `limit` to move, a note when there is more, shortened long lines, and a refusal for binary files.
- **`write_file`** creates or replaces a whole file.
- **`edit_file`** replaces exact text. `old_string` must match once, or `replace_all` must be set; an empty or unchanged `old_string` is refused. It reads and rewrites the whole file, so line endings elsewhere are kept.
- **`delete_file`**, **`move_file`** and **`copy_file`** are what a shell would otherwise be needed for. Copy and move never replace their destination.
- **`diff_files`** compares two text files line by line and returns a unified diff, or says they are identical (line endings are ignored; files that differ in more than 2000 lines are refused as too many for a diff).

Argument names are snake_case (`old_string`, `replace_all`), which is the form models are used to; the input records name them with `JsonPropertyName` attributes, so the tools use the same serializer options as everything else. `.git` is skipped when walking but not hidden from `list_directory` or `read_file`, so the AI can still look at it when it asks directly.

## Copying

`Copy`, `IsFolder` and `GetSize` are `IStore` members with default implementations, so a store that implements only the five operations has them. The default `Copy` is built from list, create folder and open (streams, so binary files survive), and works between the workspace and the storage folders. The disk store copies with the file system (a file copy per file, links resolved and confined like every other operation, and a link that loops back is an error) and the memory store copies its entries under its lock; both validate before they change anything. The mounted store hands a copy within one of its stores to that store and otherwise uses the default through its own listing and streams. The default `Copy` refuses a missing source, an existing destination and copying a folder into itself, and copies files as streams, byte for byte, opening the destination with `Create` so that nothing can be replaced even if it appears after the check. The default `IsFolder` looks the path up in the listing of its folder (the root is a folder), and the default `GetSize` takes the length of a readable stream that can seek and counts the bytes of one that cannot, summing a folder recursively. The defaults refuse a path that leads outside (`ArgumentException`) while the disk store, like its other operations, refuses it as an access error; the disk and memory stores answer from the file system and from their own entries. `ListFiles` and `ListFolders` return the relative paths of the files or of the folders in the listing, as strings. On disk a recursive listing enters a folder only if it resolves inside the store and has not been entered yet, so a link out is listed but not followed and a link back up cannot loop. A folder is copied with everything in it, empty folders included (created with create folder). A copy that fails half way removes what it made (a file: only that file, and nothing if the destination could not be created; a folder: the whole destination tree) and leaves the source alone.

## Workspace and the storage folders

`MountedStore` is what the tools work on, built from the session's workspace (a disk store, always present) and the session storage and the cache (tiered stores mounted at the paths `.liveai-session` and `.liveai-cache`, see the storage component). The workspace is the AI's working directory: a relative path is relative to it. A path that starts with a mount's name is inside it, with that part taken off: `.liveai-cache/thing/file.txt` is `thing/file.txt` of the cache, whatever the workspace has at that place, which the mount hides. Any other relative path goes to the workspace as the resolver spelled it; an absolute one, or one with no spelling, goes to the workspace as written. The store can also be built without a workspace (the tests do), in which case everything else is refused, with a message that says every path starts with a mount.

A folder on the way to a mount exists for the listing, whether or not the workspace has it: listing the top shows the workspace's entries and the mounts, and listing it recursively adds what they hold and leaves out what the workspace has under those names. A mount's root is never touched, and neither is a folder of the workspace that has a mount in it: deleting them, writing to them as if they were files, moving them, and moving or copying onto them are all refused (the folder would lose files that are hidden, not deleted), and every spelling of their path reaches that same refusal because the path is resolved first. A move inside one store is that store's move. A move between two asks the source first, through an internal capability that disk, memory and tiered stores have, to move into the other directly; the answer is no when it cannot without copying, for example between a disk and memory, and nothing has changed. Only then is it a copy followed by deleting the original tree, so a copy that fails leaves the source whole and no partial destination. The mounts exist in every session, so the file tools are always offered. The workspace the tools see is wrapped so that a path in `.liveai-temp` is reported to the temporary folder of the workspace (see the storage component). The shell is the one tool that is not confined by any of this; it starts in the workspace.

## In-memory store

A `MemoryStore` starts empty and keeps files as bytes (UTF-8, no byte order mark), like everything written to it. A stream for writing works on a copy of the bytes and hands them back when it is flushed and when it is disposed; that a file is made or emptied takes effect when it is opened, as on a disk, so a second `Create` of the same path already fails. A `Read` is a new read-only stream over the same bytes. Folders are real objects: one can be empty, can be created, and can be moved and deleted like a file when empty, which is the behaviour of a disk. Opening for writing creates the folders it needs, opening a folder or going through a file fails, and a move checks everything before it changes anything, creates the folders of its destination and never replaces anything or moves a folder into itself. Every operation runs under one lock, because the tool server can call from several threads, and listings are snapshots.

## Not done
