# Sessions

`PromptSessionLink`, `PromptSessionRecord`, `PromptSessionStore`, `PromptProvider`, `PromptSessionOpener` and `PromptSession` own a session's identity and persistence: the GUID, the stored link to the provider's session, and what it takes to resume.

## Store

Each session is one JSON file, `Sessions/<id>.json`, under the data folder (by default `Markwardt.LiveAi` in the user's local application data folder). It holds only the link (`PromptSessionLink`): the provider, when it was created (absent from links stored before that was recorded), the path of the folder the tools run in, the workspace folder and its sandbox switch when the session was created with one, the provider's session identifier once known, and, for a branch the tool makes itself at the first prompt, the identifier of the conversation it is made from and the message to continue from. No setting is stored (capability, reasoning, instructions, mounts, tools, the shell switch and the rest), so a session that is opened from its link starts with the default settings and the caller sets them again. That keeps the file to the one thing that cannot be rebuilt, the mapping to the provider's conversation, and leaves nothing to migrate when a setting is added. Unknown fields in a file are ignored. The link is written when a session is created or branched and when the provider reports its session identifier, never otherwise. Writes go to a uniquely named file in the same folder and are moved over the target, so a crash or a reader in another process sees either the old link or the new one, never half of one. Unreadable JSON is reported as `PromptSessionException` naming the GUID rather than treated as missing, so a damaged file is not mistaken for an unknown session. `List` reads every file, leaves out the unreadable ones (one damaged file must not hide the rest) and the links of other tools, and orders by creation time, newest first, with undated links last.

The in-memory `PromptSessionRecord` is what a session starts its processes from (it becomes a `PromptEngineStart` for the engine): the link, with the engine of the provider that created or loaded it in place of its stored name, plus the capability, reasoning, instructions and external MCP servers taken from the settings when a prompt starts. It is never written, only reduced back to a link.

## Linking to the provider's session

A session starts with no provider identifier. When a turn reports one (see the Providers component for where it comes from) and it differs from the stored one, `PromptSession` stores the new link before the turn continues. An identical report is not rewritten. When the first result of a branch reports the new identifier, the branch's reference to its origin (and to the message it continues from) is cleared in the same write. Because the identifier is only recorded from a turn that got far enough to report it, a first prompt that was cancelled or failed leaves the session unlinked and the next prompt starts the provider's session fresh instead of resuming one that may not exist.

## A deleted provider session

Both tools keep their sessions as files, which users and the tools' own cleanup remove: Claude Code as `projects/<project>/<session id>.jsonl` under its config folder, Codex as `sessions/<date folders>/rollout-<timestamp>-<thread id>.jsonl` under its home folder. `Load` checks for that file when the session is linked to one. If it is gone the session cannot be resumed with this provider, so `Load` throws `PromptSessionNotFoundException`; the stored link is kept, because the cause can be a provider pointed at another configuration folder than the one that made the session, and a caller who knows the session is lost deletes it. The check looks in every project folder rather than computing the one for the working folder, because the tool's folder naming for a path is its own detail (long paths are shortened). A session that was never linked (no prompt answered yet) has nothing to check and always loads. A file existing does not guarantee the tool can resume it, so a corrupt or foreign file still fails later, at `Send`, as a `PromptSessionException`.

The two config folders default to the tools' own (`CLAUDE_CONFIG_DIR` or `~/.claude`, `CODEX_HOME` or `~/.codex`). A folder given to `ClaudeEngine` or `CodexEngine` is also passed to the tool as that variable, so the library and the tool always look in the same place.

## The working folder

The tools need a working directory, and the provider's own session storage is keyed by it, but the AI works on mounts and not on that folder. So every session gets an empty folder, `markwardt.liveai-<id>` (the session's identifier) directly in the system temp folder, created with the session. The AI has no tool that reaches it (its workspace is the `Workspace` of the configuration, which is a different thing) and is told that the folder it runs in is empty. The shell starts there unless the workspace is a folder on disk. The library never deletes it: the stored link points at it and resumption depends on it. If the operating system has cleaned it by the time of a `Load` it is created again, which loses nothing because it never held anything.

A session created with a workspace path runs in that folder instead, because the caller already chose where the AI works: no scratch folder is made, the link holds the path as both the working folder and the workspace together with the sandbox switch, and the opener sets `Workspace` to `IStore.FromDisk` of it on every open (create, load, fork), so a loaded session has it without the caller setting it again. The folder must exist (create throws, and a load of a session whose folder is gone throws too instead of making an empty one), `Delete` never removes it, and attachments are written to the system temp folder and not into it. The AI is not told its folder is empty. Only that path is stored: assigning `Configuration.Workspace` afterwards changes the running session only (the tool keeps its working folder and a load starts from the stored path again), which is why moving the workspace of a stored session goes through `AttachTo`, which rewrites the link.

## Changed settings

The settings are one object, `PromptSessionSettings`, that implements the public `IPromptSessionConfiguration` and is what `IPromptSession.Configuration` returns. Its scalar setters validate their value and then assign it under one `lock`; the tool list and the two dictionaries (mounts and MCP servers) are small guarded collections that check each entry when it is added, hand out copies when enumerated and share the lock, so they are safe to change from any thread. Every change raises `Changed` after the lock is released, which is how the session notices that a kept process may no longer be wanted. A prompt takes `Snapshot()` when it starts, a copy of everything, and works from that: the record the provider is given is merged from it, the served tools and file tools are chosen from it, and the process is kept or restarted by comparing what it was started with to it. The two tool call hooks are the settings read when they are needed and not from the snapshot, so a change reaches a call that arrives in a prompt that is running; the session is itself what the tool server calls (`IPromptToolHooks`) and it forwards to whatever the hooks are at that moment. `Close` makes every later change throw, which the session calls first when it is disposed. Nothing of the settings is written. The fake session uses the same object, so it checks settings exactly as the real one does.

## The live process

`PromptSession` keeps the persistent process (if any) and the settings it was started with. Before each persistent prompt it keeps the process only if it is still running and the record it was started from is the same for the tool (`SameProcess`: instructions and external servers, which are fixed when the tool starts; the capability and the reasoning are not, since the process takes them with each prompt), the formatted schema (or the absence of one, unless the provider takes the schema with each prompt) and the tool server's address match what it started with; otherwise it stops it and starts a new one from the current record, which resumes the provider session when one is linked. A change of the settings decides in one place what has to happen to the process: turning `IsPersistent` off, or changing one of the settings the process was started with while one is live, schedules (once at a time) a background task that waits for the prompt gate, so a running prompt is never cut short, and only then ends the process (gracefully when persistence is off, immediately when it is merely stale), if it is still off or stale by then (the settings may have been put back). A change of the tools or the mounts is picked up by the next prompt through the tool server's address. A non-persistent prompt ends any leftover process before it starts its own, so two processes never work on one conversation. A tool that is always driven through a conversation process (Codex) gets one opened for a non-persistent prompt too, which the session disposes in the `finally` of the prompt; what it runs through is the same method either way, and `active` holds the process in use so that an interrupt reaches a process that is not the kept one.

The tool server (see the Tools component) is part of the same state: the session compares the offered tools with the ones the server was started for, with each tool compared by its name, description, schema and handler, and starts a new server when they differ. Disposal is one shared path, `Close`, that flips the disposed flag once and starts a single cleanup task (`Finish`) which takes the gate, ends the process, stops the tool server and waits for any pending background teardown. `DisposeAsync` is the graceful form: it only waits for the gate, so a running prompt finishes first, input still waiting is dropped and requests that wait for a mixed answer fail with `ObjectDisposedException`, `Output` is completed, and the process is released the graceful way (input closed, a few seconds to exit, then ended). `Dispose` is the immediate form: it cancels the closing token that every prompt is linked to, kills the process on the calling thread so nothing is left running when it returns, and lets the cleanup task finish in the background; calling it while a graceful disposal is waiting on the gate therefore hurries that one up too. Both return the same cleanup task's result, so they can be mixed and repeated. A prompt sent afterwards throws `ObjectDisposedException`.

## Prompt loops

## State, the pump and the three modes

Besides the turn gate (the semaphore that gives one operation at a time the engine, the process and the stored link), `PromptSession` has a state, `Waiting`, `Working` or `Responding`, that is changed only under the session's lock and reported on `Output` as a `PromptStateEvent` from the same place, so state events are in order with the rest. `Output` is a `Broadcast` without replay.

Direct requests take the state: under the lock they require `Waiting` and set `Responding` (or throw `PromptSessionStateException`), run `Turn` (the code that runs one prompt: validation, the gate, `Begin`, the engine, the events, interruption) and publish each event to `Output` as they pass it on, then set `Waiting` in a `finally`. A failure is published as a `PromptFailureEvent` before it is rethrown. `Output` is a `Broadcast<T>`: publishing only posts to the queue of each watcher, and each watcher has a pump that calls it in order, outside every lock, so a callback may call back into the session; a watcher that throws is dropped, and a late one is given the replay value (for `Output` none, for loop replies the latest).

`Send` and mixed requests go through `Deliver`, whose task completes when the input was written to the process (`Steer` returned) or was queued, not when the AI has acted on it. While the state is `Working` and a conversation process is running the work (`workProcess`, set in `Run` once the process exists), the input is written to it with `IPromptProcess.Steer` outside the lock, taking the pending notes that the running prompt did not start with (`notesInFlight` counts those, so a note is never sent twice), and is remembered as delivered before the write, so the end of the work cannot miss it. If the process refuses (the work just ended), the notes wait again and the input is queued, unless the session is responding by then, which throws; if the write fails, the notes wait again and the exception is thrown without queueing the input, since the caller was told it failed. Input with files for an engine that needs them written to a folder is not steered. Anything else is queued; if the state was `Waiting` it becomes `Working` and a pump task starts, which takes what is queued, joins the texts and attachments into one run with no schema, publishes its events, and repeats while input has arrived, then sets `Waiting`. Input queued after the work was started but before its process existed is joined to the prompt in `Run`. A failure is published and the pump goes on. When the work ends, a mixed request among the delivered input that was not answered is failed.

The `respond` tool is a library tool that is part of every `Serve`, so every session has a tool server and every work can take a mixed request (a tool cannot be added to work that is running, which is why it is not offered only once a mixed request exists). Its name is reserved. A pending request is a completion keyed by its unique identifier with the schema it must follow; the handler looks it up, checks the answer, completes it and answers the AI, or throws so that the AI sees what to fix. Fork requests call `Branch` without taking the gate (the fork is cut from what the tool has stored), run a direct request on the copy, then dispose it and have the provider delete it.

`PromptLoop<TReply>` runs one background task that calls `IPromptSession.Request` with its input and options, so it asks in the mode of the options like any caller (a direct loop finds the session busy if something else is using it) and needs nothing from `PromptSession`. State (the input, the options, the schedule, whether a send is in progress, whether a trigger is pending, when the last send started) is guarded by a `lock`. After a send the loop waits on a `SemaphoreSlim` signal with the time that is left as its timeout (none for a manual schedule, zero for a continuous one, the interval minus the time since the last send started for an interval): the schedule setter and `Trigger` release the signal, so a changed schedule or a trigger is noticed at once, and the state is checked again after every wake, which makes a surplus signal harmless. A send is marked as in progress already when the loop is made, so a trigger that comes before the first send has started does not queue a second one, and the trigger flag is only set while no send is in progress. Disposal cancels one token that both the send and the wait observe; the task treats that cancellation as a normal end, and any other exception leaves the task faulted. The answers are published through an internal broadcaster, a hot observable without a dependency on a reactive library: it remembers the latest value and gives it to each new watcher first, because the first send starts in the constructor and a watcher could otherwise never see that answer; it delivers under one lock so that the replayed value and a value published at the same moment cannot arrive out of order, and it drops a watcher whose callback throws. Values are published on the loop's own thread, one at a time, before the next send can start. The end is published from the same place that settles the task, completion for a normal end (including cancellation) and the exception for a failure. `DisposeAsync` waits for the task without rethrowing, since the failure is already on `Task`. With `WaitForWindow` a send that is stopped by the window limit is not the end: the exception carries the windows that reached the limit (`PromptLimitException.Windows`), the loop gives them to the caller's function, which returns the window to wait out, publishes that window's reset as `ResumesAt`, sleeps until then plus a margin (five seconds) under the loop's own token, so a timeout or a disposal ends the wait, and sends the same prompt again. The first window read of that send, which is made at once, decides whether the limit still holds; so when a limit is still reached the function is asked again and the loop waits again. A status without a future reset time (a custom provider's, or one that has passed) ends the loop with the window limit as without the option, which keeps it from spinning.

## Serializing prompts

`PromptSession` holds a `SemaphoreSlim` for the length of a turn. A second prompt waits (and can be cancelled while waiting), so the stored provider identifier is never read mid-update and the provider never gets two processes on one session. Two `PromptSession` objects for the same GUID (two `Load` calls) do not share the gate; callers who do that own the ordering.

## One prompt's run

A request hands the session a run: the text, the files, the schema and the options of that request (model, reasoning, extra tools and mounts). The session makes an effective record from its own with the model and reasoning of the run and starts the process from that, without changing its own, which also makes a kept process restart exactly when the effective settings differ. The extra tools and mounts are checked with the same rules as a configuration (names, no clash with the session's) before the turn gate is taken, and are served together with the session's: the file tools are built again for a run with extra mounts instead of reusing the cached ones (they are also built again when the workspace changes), and the tool server is replaced when the served set changes, which is why a run with extras restarts a kept process and the next run without them does too. The model and the reasoning of a run go with the prompt to the process, which is the reason they no longer restart it.

## Branching and rewinding a session

`Fork` takes the turn gate, so the branch starts after a running prompt, asks the provider to branch (Codex forks the thread through its app server and returns the new identifier; Claude Code returns the origin and the message to continue from, and the tool makes the copy at the first prompt), makes a new link from the current one (new identifier, own scratch folder or the same workspace folder and sandbox, what the provider returned), stores it, opens it, and copies all of the settings into the branch's configuration. A session without a conversation branches into an empty session without asking the provider; a branch at an entry of one is an error. The branch inherits what the original knows about the instructions its conversation holds, so a Codex branch is not told them again. A branch of a branch that has not been prompted yet keeps the original origin and its point.

`AttachTo` takes the gate, checks the workspace folder and (when one is given) asks the provider whether it has the session (a file or thread lookup, the same check `Load` makes), and only then rewrites the link: the session identifier (none for a new conversation), no origin or point, the working folder and workspace path (an empty folder named after the session in the system temp folder when there is no workspace, the folder `Create` would have made), and the sandbox switch. It ends the kept process, forgets which instructions the conversation holds, so the next turn tells a tool that keeps them the current ones, and finally sets `Workspace` to the new store or clears it. Nothing is changed when a check fails; the folder a session moves away from is never deleted, so moving back to no workspace finds its old scratch folder (and a Claude Code conversation made there) again.

`Rewind` takes the gate and the same branch from the provider, but stores it in its own link and ends the kept process instead of opening another session. Between `Rewind` and the next prompt nothing has been made for Claude Code (the tool makes the copy then, and an error from it shows at that prompt), which is why the point is checked while it is found.

## Compaction, context and notes

`Compact` and `GetContext` run through the same gate and the same setup as a prompt (the settings are read, the tool server serves the tools, so the system prompt and the tool descriptions that are counted in the context are the ones a prompt would have), and use the kept process when there is one and otherwise a process opened for the operation and disposed after it. A session whose provider cannot keep a process does not support them. A compaction follows the session identifier that the process reports, as a prompt does, because Claude Code continues a compacted conversation in a new one.

`Send` (or a request) with notes appends them to a list under the session's lock, once the state check has passed so a refused input leaves no note. If the input is steered into running work the list goes with it; otherwise the next work takes the list with it in its `PromptInput`, with the note about changed instructions after them, and removes what it took once the process produced anything other than a failure, so a prompt that failed to start does not lose a note. The notes are not stored anywhere else: a session that is disposed without another prompt drops them.

## History and status

`GetHistory` reads through the provider from the identifier of the session or, before the first prompt of a branch, of its origin; it does not take the turn gate, so it can be read while a prompt runs, and reads the file with sharing allowed. The provider reads the entries newest first, lazily, and the session passes them on as an async stream (an `IOException` while reading becomes a `PromptSessionException`), so a caller that takes a few reads only the end of the file; `OlderThan` and `NewerThan` are `SkipWhile` and `TakeWhile` on the points of the entries. The session's status read for a request's limit goes to its provider, which does not touch the session's conversation or gate.

## Deleting

There is no listing: the store only finds a link by its identifier. `Delete` works from the link, on the provider of the same tool (a stored name that differs from the engine's is refused): the engine deletes its conversation (when the session was linked to one), the scratch folder is deleted only when its name starts with the prefix the library gives them, and the link goes last, so a failure leaves a session that can be deleted again.

## Changed instructions

The session remembers, in memory only, the instructions its last turn used (once the turn has delivered anything). For a provider that keeps the instructions a conversation began with, the next turn that resumes a provider session carries a note when they differ from those, when they are cleared, or on the first turn of an object that was loaded or branched and has some (nothing is stored to compare with, so the same instructions given again after a `Load` are told to the conversation again). A turn on a session without a provider session yet only records them, since they start the conversation. The note is made at the start of the turn with the others and removed from the list only when the turn has delivered it, which makes a failed prompt try again.

## Interrupting, usage and defaults

A turn creates a source that `Interrupt` can cancel and a flag that says it was asked, both under the session's lock and cleared when the turn ends. If a process is running (the kept one, or the one a conversational tool opened for this prompt) the session asks it to interrupt; otherwise it cancels the source, which the turn treats as the end of the prompt and not as an error, also when it happens before the process has started. The flag is also what lets the turn swallow the failed result that an interrupted kept process ends with. The session adds up the usage events that pass through it, which is what `Usage` and the budget check read, and takes the defaults when `Prompt` makes the request, by applying them with the same methods a caller would use.
