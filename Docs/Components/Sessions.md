# Sessions

`PromptSessionLink`, `PromptSessionRecord`, `PromptSessionStore`, `PromptToolService`, `PromptSessionOpener` and `PromptSession` own a session's identity and persistence: the GUID, the stored link to the tool's session, the stored configuration, and what it takes to resume. The public `Prompter` sits above them and picks a `PromptToolService` per tool from the type of the options.

## Store

Each session is one JSON file, `Sessions/<id>.json`, under the data folder (by default `Markwardt.LiveAi` in the user's local application data folder). It holds the link (`PromptSessionLink`) and the configuration: the provider (`claude`, `codex` or `local`, the names of the `PromptProvider` values in lower case, the same as the `tool` of the setup), when it was last loaded (`lastLoaded`, which starts as the time of creation), the path of the folder the tools run in, the workspace folder when the session has one, the tool's session identifier once known, and, for a branch the tool makes itself at the first prompt, the identifier of the conversation it is made from and the message to continue from; then the setup the session was created with (polymorphic JSON, a `tool` discriminator per derived type: the API key, and for local models the overrides of the server, the models and the context sizes; the workspace is not in it, since the link holds it, and neither are the commands and configuration folders of the tools nor the configuration new sessions start with, which belong to the prompter's environment (the first are read when a session is loaded, the second only when one is created; the stored configuration of the session holds the values from then on)), the capability and effort, the shell, system access, web and image generation switches and the instructions (the image generation setup is not stored: the environment holds it). That is what lets `Load` and `Delete` work from an identifier alone and a session come back as it was. The tools, the MCP servers, the asker and the cache belong to the live object and are not stored, and neither is the model: it is chosen again from the capability and effort. The configuration is written when a prompt starts (if it differs from what is stored) and when the session is disposed (if it changed since and the link still exists, so a deleted session is not brought back); the link is also written when a session is created or branched, and when it is loaded, to record the time once the session has opened (a load that fails records nothing, and a store that cannot be written only means the time is not recorded, the session still loads), when the tool reports its session identifier and when a session is moved. Unknown fields in a file are ignored and missing ones take their defaults, so a field can be added without a migration; a change that is not just an added field is a new layout version. The file holds API keys, so it is created readable by the current user only (`UnixCreateMode`; Windows keeps the folder's permissions). Writes go to a uniquely named file in the same folder and are moved over the target, so a crash or a reader in another process sees either the old link or the new one, never half of one. Unreadable JSON is reported as `PromptSessionException` naming the GUID rather than as a JSON error.

Every file carries the version of its layout (`version`, currently 5), written first, and the store upgrades older files itself whenever it reads one, in `Find` and in `List`, so a session stored by any version of the library loads in this one. Version 1 is the layout of library version 1.x, which had no setup in the file (the tool was named only by its `provider`), the sandbox as `sandbox`, and the model and its settings; a file written by 2.0.0 has no number but has its setup, which is how it is told from version 1, and is version 2, whose `provider` was the name the tool calls itself (`Claude Code`, `Codex`, `OpenCode`); version 3 stores the provider as the lower case name of the `PromptProvider` value, and version 4 stores when the session was last loaded as `lastLoaded` in place of `created`, with the same value (a file that has none gets the time it was last written, so the time is never missing), and version 5 stores the file tools' confinement as `isSystemAccessAllowed`, the opposite of the `isSandboxed` it replaces (a file without one stays confined). An upgrade is a step per version on the JSON itself (so it does not depend on the types of the day): version 1 gets the setup of its tool from the provider name, `sandbox` becomes `isSandboxed`, the model becomes the capability whose tier its name says (the same hints that choose a model for a capability) and the effort setting (`variant` for OpenCode) becomes the effort; version 2 gets the provider in its new form (from the name, or from the `tool` of its setup when the name is not one the library knows); version 3 gets `lastLoaded` in the place of `created`; and version 4 gets `isSystemAccessAllowed` in the place of `isSandboxed`, with the opposite value. The shell, web and image generation switches and the instructions were never stored in version 1, so they keep their defaults; the library cannot know what the caller ran its sessions with, so the caller sets what it wants through the configuration of the loaded session, which is stored when it is disposed, and the original file kept beside the upgraded one (below) shows what the old layout held. The original is kept beside the file as `<id>.json.v<old version>.bak` (a copy that is already there is not overwritten, and deleting the session removes it too, since it holds the same API key; a folder that cannot be written only means the upgrade is not stored, the session still loads), and a file whose tool is not known is left alone, which makes it unreadable, since its provider is not a value of the enum. A file written by a newer version of the library is refused like an unreadable one: `Find` throws `PromptSessionException`, `List` leaves it out, and it is never rewritten.

The in-memory `PromptSessionRecord` is what a session starts its processes from (it becomes a `PromptEngineStart` for the engine): the link, with the engine of the tool service that created or loaded it in place of its stored name, plus the model and its settings that the provider selected for the capability and effort, the instructions and the external MCP servers taken from the settings when a prompt starts. `SameStored` compares the parts that are written, so a change of the tools alone does not cause a write. It is only written reduced back to a link.

## Linking to the provider's session

A session starts with no provider identifier. When a turn reports one and it differs from the stored one, `PromptSession` stores the new link before the turn continues. An identical report is not rewritten. When the first result of a branch reports the new identifier, the branch's reference to its origin (and to the message it continues from) is cleared in the same write. Because the identifier is only recorded from a turn that got far enough to report it, a first prompt that was cancelled or failed leaves the session unlinked and the next prompt starts the provider's session fresh instead of resuming one that may not exist.

## A deleted provider session

Both tools keep their sessions as files, which users and the tools' own cleanup remove: Claude Code as `projects/<project>/<session id>.jsonl` under its config folder, Codex as `sessions/<date folders>/rollout-<timestamp>-<thread id>.jsonl` under its home folder. `Load` checks for that file when the session is linked to one. If it is gone the session cannot be resumed with this provider, so `Load` throws `PromptSessionNotFoundException`; the stored link is kept, because the cause can be a provider pointed at another configuration folder than the one that made the session, and a caller who knows the session is lost deletes it. The check looks in every project folder rather than computing the one for the working folder, because the tool's folder naming for a path is its own detail (long paths are shortened). A session that was never linked (no prompt answered yet) has nothing to check and always loads. A file existing does not guarantee the tool can resume it, so a corrupt or foreign file still fails later, at `Send`, as a `PromptSessionException`.

The two config folders default to the tools' own (`CLAUDE_CONFIG_DIR` or `~/.claude`, `CODEX_HOME` or `~/.codex`). A folder given to `ClaudeEngine` or `CodexEngine` is also passed to the tool as that variable, so the library and the tool always look in the same place.

## The working folder

Every session has a workspace, the folder the tool runs in and the AI works on. When the caller gives no workspace path the library makes one: `Workspaces/<id>` in the data folder, named after the session (`IPromptSessionStore.GetWorkspaceFolder`), created with the session. It is a real, kept folder, so what the AI writes there stays until the session is deleted or moved elsewhere. The link records it as the working folder with no workspace path, which is how it is told from a folder the caller gave. If it has gone by the time of a `Load` it is created again (empty). `Delete` removes it with the conversation, and so does a `Move` to another folder, once the move has succeeded; a `Move(null)` back makes it again, empty, and a `Move(null)` while already in it keeps its files. A delegate helper uses the workspace of its parent as if the caller had given it, so it never deletes it, and a fork of a session in an automatic workspace gets an automatic workspace of its own, empty.

A session created with a workspace path runs in that folder instead, because the caller already chose where the AI works: no folder is made, the link holds the path as both the working folder and the workspace, and the session builds its workspace store, a `DiskStore` of it, confined unless the `IsSystemAccessAllowed` setting is on, whenever it is opened (create, load, fork) and again when `IsSystemAccessAllowed` has changed by the time the tools are served, so a loaded session has it without the caller doing anything. The folder must exist (create throws, and a load of a session whose folder is gone throws too instead of making an empty one), `Delete` never removes it, and attachments are written to the system temp folder and not into any workspace. The workspace cannot be assigned: the tool keeps the working folder it was started in, so moving the workspace of a session goes through `Move`, which rewrites the link.

## Changed settings

The settings are one object, `PromptSessionSettings`, that implements the public `IPromptSessionConfiguration` and is what `IPromptSession.Configuration` returns; it also holds the tools, the external servers and the asker, which the session exposes as its own properties. Its scalar setters validate their value and then assign it under one `lock`; the tool list and the two dictionaries (the MCP servers) are small guarded collections that check each entry when it is added, hand out copies when enumerated and share the lock, so they are safe to change from any thread. Every change raises `Changed` after the lock is released, which is how the session notices that a kept process may no longer be wanted. A prompt takes `Snapshot()` when it starts, a copy of everything, and works from that: the record the provider is given is merged from it, the served tools and file tools are chosen from it, and the process is kept or restarted by comparing what it was started with to it. `Close` makes every later change throw, which the session calls first when it is disposed. Nothing of the settings is written. The fake session uses the same object, so it checks settings exactly as the real one does.

## The live process

`PromptSession` keeps the process (if any) and the settings it was started with. Before each prompt it keeps the process only if it is still running and the record it was started from is the same for the tool (`SameProcess`: instructions and external servers, which are fixed when the tool starts; the model and its settings are not, since the process takes them with each prompt, unless the engine takes them when it starts, as OpenCode does), the formatted schema (or the absence of one, unless the tool takes the schema with each prompt) and the tool server's address match what it started with; otherwise it stops it and starts a new one from the current record, which resumes the tool's session when one is linked. Before that the capability and effort are turned into a model and settings by the tool service (`Select`), once for each pair of values the session has used. A change of one of the settings the process was started with while one is live schedules (once at a time) a background task that waits for the prompt gate, so a running prompt is never cut short, and only then ends the process immediately, if it is still stale by then (the settings may have been put back). A change of the tools is picked up by the next prompt through the tool server's address. `active` holds the process in use so that an interrupt reaches it. A process that is reused for a prompt but had died since the last one (its exit not yet noticed when the prompt was sent) reports a failure as its first event with itself no longer running; the session then starts a new process, which resumes the same conversation, and runs the prompt there once. A failure from a process that is still running (an API error, say) is not retried.

The tool server is part of the same state: the session compares the offered tools with the ones the server was started for, with each tool compared by its name, description, schema and handler, and starts a new server when they differ. Disposal is one shared path, `Close`, that flips the disposed flag once and starts a single cleanup task (`Finish`) which takes the gate, ends the process, stops the tool server and waits for any pending background teardown. `DisposeAsync` is the graceful form: it only waits for the gate, so a running prompt finishes first, input still waiting is dropped and requests that wait for a mixed answer fail with `ObjectDisposedException`, the event stream is completed, and the process is released the graceful way (input closed, a few seconds to exit, then ended). `Dispose` is the immediate form: it cancels the closing token that every prompt is linked to, kills the process on the calling thread so nothing is left running when it returns, and lets the cleanup task finish in the background; calling it while a graceful disposal is waiting on the gate therefore hurries that one up too. Before the process ends the configuration is written if it changed. Both return the same cleanup task's result, so they can be mixed and repeated. A prompt sent afterwards throws `ObjectDisposedException`.

## State, the pump and the three modes

Besides the turn gate (the semaphore that gives one operation at a time the engine, the process and the stored link), `PromptSession` has a state, `Waiting`, `Working` or `Responding`, that is changed only under the session's lock and reported in the event stream as a `PromptStateEvent` from the same place, so state events are in order with the rest. the event stream is a `Broadcast`.

Direct requests take the state: under the lock they require `Waiting` and set `Responding` (or throw `PromptSessionStateException`), run `Turn` (the code that runs one prompt: validation, the gate, `Begin`, the engine, the events, interruption) and publish each event to the event stream as they pass it on, then set `Waiting` in a `finally`. A failure is published as a `PromptFailureEvent` before it is rethrown. The event stream is a `Broadcast<T>`: publishing only posts to the queue of each watcher, and each watcher has a pump that calls it in order, outside every lock, so a callback may call back into the session; a watcher that throws is dropped.

`Send` and mixed requests go through `Deliver`, whose task completes when the input was written to the process (`Steer` returned) or was queued, not when the AI has acted on it. While the state is `Working` and a conversation process is running the work (`workProcess`, set in `Run` once the process exists), the input is written to it with `IPromptProcess.Steer` outside the lock, taking the pending notes that the running prompt did not start with (`notesInFlight` counts those, so a note is never sent twice), and is remembered as delivered before the write, so the end of the work cannot miss it. If the process refuses (the work just ended), the notes wait again and the input is queued, unless the session is responding by then, which throws; if the write fails, the notes wait again and the exception is thrown without queueing the input, since the caller was told it failed. Input with files for an engine that needs them written to a folder is not steered. Anything else is queued; if the state was `Waiting` it becomes `Working` and a pump task starts, which takes what is queued, joins the texts and attachments into one run with no schema, publishes its events, and repeats while input has arrived, then sets `Waiting`. Input queued after the work was started but before its process existed is joined to the prompt in `Run`. A failure is published and the pump goes on. When the work ends, a mixed request among the delivered input that was not answered is failed.

The `respond` tool is a library tool that is part of every `Serve`, so every session has a tool server and every work can take a mixed request (a tool cannot be added to work that is running, which is why it is not offered only once a mixed request exists). Its name is reserved. A pending request is a completion keyed by its unique identifier with the schema it must follow; the handler looks it up, checks the answer, completes it and answers the AI, or throws so that the AI sees what to fix. Fork requests call `Branch` without taking the gate (the fork is cut from what the tool has stored), run a direct request on the copy, then dispose it and have the provider delete it.

## Serializing prompts

`PromptSession` holds a `SemaphoreSlim` for the length of a turn. A second prompt waits (and can be cancelled while waiting), so the stored provider identifier is never read mid-update and the provider never gets two processes on one session. Two `PromptSession` objects for the same GUID (two `Load` calls) do not share the gate; callers who do that own the ordering.

## One prompt's run

A request hands the session a run: the text, the files, the schema and the mode of that request. The session makes an effective record from its own and starts the process from that, without changing its own, which also makes a kept process restart exactly when the effective settings differ. The model and the reasoning of a run go with the prompt to the process, which is the reason they no longer restart it.

## Branching and rewinding a session

`Fork` takes the turn gate, so the branch starts after a running prompt, asks the provider to branch (Codex forks the thread through its app server and returns the new identifier; Claude Code returns the origin and the message to continue from, and the tool makes the copy at the first prompt), makes a new link from the current one (new identifier, an automatic workspace folder of its own or the same workspace folder, what the provider returned), stores it, opens it, and copies all of the settings into the branch's configuration. A session without a conversation branches into an empty session without asking the provider; a branch at an entry of one is an error. The branch inherits what the original knows about the instructions its conversation holds, so a Codex branch is not told them again. A branch of a branch that has not been prompted yet keeps the original origin and its point.

`Move` takes the gate and checks the workspace folder, asks the engine to make the session's conversation resumable from the new working folder (`MoveSession`, for the conversation it continues or the origin of a branch that has not been prompted: Claude Code copies the conversation file, the others do nothing), and only then rewrites the link: the working folder and workspace path (the automatic folder `Workspaces/<id>` of the data folder when the new workspace is `null`, the folder `Create` would have made); the conversation, the origin and point of a branch and the system access switch stay. It ends the kept process, which ran in the old folder, and finally builds the workspace store for the new folder or clears it, which leaves the AI's file tools with the cache only. Nothing is changed when a check or the engine fails, or when the link cannot be stored (the session goes back to its old folder and a folder made for the move is removed); a folder the caller gave is never deleted, and the automatic one is deleted only after the move has succeeded.

`Rewind` takes the gate and the same branch from the provider, but stores it in its own link and ends the kept process instead of opening another session. If the link cannot be stored the session keeps the conversation it had. Between `Rewind` and the next prompt nothing has been made for Claude Code (the tool makes the copy then, and an error from it shows at that prompt), which is why the point is checked while it is found.

## Compaction, context and notes

`Compact` and `GetContext` run through the same gate and the same setup as a prompt (the settings are read, the tool server serves the tools, so the system prompt and the tool descriptions that are counted in the context are the ones a prompt would have), and use the process the session keeps (opened if there is none yet). A session whose tool cannot keep a process does not support them. A compaction follows the session identifier that the process reports, as a prompt does, because Claude Code continues a compacted conversation in a new one.

`Send` (or a request) with notes appends them to a list under the session's lock, once the state check has passed so a refused input leaves no note. If the input is steered into running work the list goes with it; otherwise the next work takes the list with it in its `PromptInput`, with the note about changed instructions after them, and removes what it took once the process produced anything other than a failure, so a prompt that failed to start does not lose a note. The notes are not stored anywhere else: a session that is disposed without another prompt drops them.

## History and status

`GetHistory` reads through the provider from the identifier of the session or, before the first prompt of a branch, of its origin; it does not take the turn gate, so it can be read while a prompt runs, and reads the file with sharing allowed. The provider reads the entries newest first, lazily, and the session passes them on as an async stream (an `IOException` while reading becomes a `PromptSessionException`), so a caller that takes a few reads only the end of the file; `OlderThan` and `NewerThan` are `SkipWhile` and `TakeWhile` on the points of the entries. 

## Deleting

`Prompter.List` reads every stored link, the most recently loaded first; the store finds a link by its identifier. `Delete` works from the link: the prompter reads the stored setup and its environment to pick the provider of the tool (the models of local sessions are not needed for it), which refuses a link stored for another tool, the engine deletes its conversation (when the session was linked to one; every copy a move made), the automatic workspace folder is deleted only when the link has no workspace path and its working folder is the one the store names for the session, and the link goes last, so a failure leaves a session that can be deleted again.

## Moving a stored session

`Prompter.Move` works from the link like `Delete`: the prompter picks the provider of the tool from the stored setup, which refuses a link stored for another tool, and the provider checks that the folder exists, has the engine bring the tool's conversation to it (`engine.MoveSession`, which for Claude Code copies the transcript to the folder key and leaves the old copy; the origin is the tool's session or, for a branch that has not prompted yet, the conversation it is made from), and stores the link with the new working folder and workspace path (everything else of the link is kept), removing the folder the library made for a session that had none. It never loads the session, since loading checks that the folder the link names exists, which is exactly what is not true when a workspace was moved on disk; nothing but the conversation's copy and the link is written, and the files of the workspace are never touched. The order makes it safe to fail: the folder is checked, then the conversation is brought over, then the link is stored, so a failure before the last step leaves the link as it was.

## Changed instructions

The session remembers, in memory only, the instructions its last turn used (once the turn has delivered anything). For a provider that keeps the instructions a conversation began with, the next turn that resumes a provider session carries a note when they differ from those, when they are cleared, or on the first turn of an object that was loaded or branched and has some (nothing is stored to compare with, so the same instructions given again after a `Load` are told to the conversation again). A turn on a session without a provider session yet only records them, since they start the conversation. The note is made at the start of the turn with the others and removed from the list only when the turn has delivered it, which makes a failed prompt try again.

## Interrupting, usage and defaults

A turn creates a source that `Interrupt` can cancel and a flag that says it was asked, both under the session's lock and cleared when the turn ends. If a process is running (the kept one, or the one a conversational tool opened for this prompt) the session asks it to interrupt; otherwise it cancels the source, which the turn treats as the end of the prompt and not as an error, also when it happens before the process has started. The flag is also what lets the turn swallow the failed result that an interrupted kept process ends with. The session adds up the usage events that pass through it, which is what `Usage` reads.
