# Tools

`PromptTool`, `PromptToolHost`, `PromptToolServer` and `ToolEndpoint` offer the caller's functions to the AI's tool. A session owns at most one server at a time; the providers only learn its address and secret.

## The server

The server answers MCP's Streamable HTTP in its simplest form: every request is a POST of one JSON-RPC message to `/mcp` and every answer is one JSON body, with no sessions and no event streams. It implements `initialize` (answering with the client's own protocol version, so a newer client is not refused), `ping`, `tools/list` and `tools/call`; a notification gets `202`, any other method a JSON-RPC "method not found", other HTTP verbs `405`. `tools/list` describes each tool with its schema and a `readOnlyHint` annotation. `tools/call` runs the handler and returns its text as the result; an exception or arguments that do not fit the input type come back as an error result (`isError`), not a protocol error, because that is the form the AI is shown and can act on. An unknown tool is a protocol error.

Requests are handled concurrently. Each handler gets a token that is cancelled when the server is disposed, so a long-running tool ends with its session. A request that is cancelled that way, or whose client has gone, ends quietly.

## Port and secret

`PromptToolHost` finds a free loopback port by listening briefly on port 0 and then binds the real listener there, retrying if another process takes the port in between. The secret is 32 random bytes in hex, compared in constant time. The listener is started on `127.0.0.1` rather than a wildcard so no firewall prompt or elevated rights are needed and nothing outside the machine can reach it.

## How each tool is told

Claude Code gets an MCP configuration as a JSON string (`--mcp-config`) with an HTTP server whose bearer header is written as `${LIVEAI_TOOLS_TOKEN}`, which Claude Code expands from its environment, plus `--allowedTools` for each tool as `mcp__liveai__<name>` (a tool that is offered but not allowed is refused in the `dontAsk` permission mode). Codex gets `-c` overrides for the server's URL, the name of the environment variable that holds the bearer token, the approval mode and a per-tool timeout just above the longest a shell command may run (so the tool's own limit does not cut a long command off); its read-only sandbox does not block the calls. In both, the secret travels in the environment only, so it is not in the process list. The AI knows a tool only by its name, description and input schema, so those carry everything it needs to use the tool well.

## The library's own tools

The shell tool, when `IsShellAllowed` is on, goes through the server too, as one more library tool that is built once per session (again when the folder it starts in changes) and is part of the endpoint's identity, which makes a persistent process restart when it is switched. The file tools of the library go through this same server: the session builds them over the workspace and the cache (every session has the cache, so every session has them) and serves them together with the caller's tools. They are built once and reused, so the server and a persistent process are not restarted every prompt; they are rebuilt when the workspace changes. Their names are reserved, so a caller's tool cannot take one.

## Images and the web

`view_image` is always offered, to a model that takes images and an engine that can be shown them, and `fetch_url` and the search are opt-in like the shell (`IsWebAllowed`, one switch for both). They are built by `PromptLibraryTools` and served with the others, under reserved names. A tool answers only in text, so `view_image` cannot return the picture: it reads the image from the same store as the file tools (cleaned path, PNG, JPEG, GIF or WebP, 5 MB at most) and has the session send it as an input of its own, `Here is the image <path> you asked to see.` with the image attached and a note that the tool sent it. It does not go through `Send`, which refuses input while a request is being answered (`Responding`), because the tool is called during exactly that: the session accepts it in that state too, and steers it into the work the AI is doing when the process can take input mid-work, which for Claude Code puts the picture in front of the AI right after the tool's result. Where it cannot be steered (an engine that has to write attachments as files, like Codex, or one that runs a process per prompt without a conversation process, like a custom engine; Claude Code steers it whether or not the session keeps its process) it waits, and the session starts work with it as soon as the request is over; likewise when no turn is running. The library does not send it a second time: a steered input leaves no trace in the stored conversation that could confirm it arrived, and the AI asked for the image itself, so the tool's answer tells it to call the tool again if the image never turns up. The tool is offered only while the model's `AcceptsImages` is not `false` and the engine accepts `image/png`, and it is built again with the file tools when the workspace changes. `fetch_url` is a plain GET with a 30 second timeout, at most 2 MB read, redirects followed by the tool itself (up to 5, to http or https addresses only) and not by the HTTP client, with no filter or other restriction on the address: the tool reads as this machine does, and what it may reach is the caller's decision when it switches `IsWebAllowed` on. Only text-like media types are read, and HTML is reduced to text by dropping scripts, styles and tags; failures come back as an error result the AI can read.

## Search and the tools every session has

Search has two implementations behind `IsWebAllowed`. An engine that reports `NativeSearch` (Claude Code and Codex) is told through `PromptEngineStart.Search` to allow its own search: Claude Code gets `--tools WebSearch` and `WebSearch` among its allowed tools (the native tool set is otherwise empty), and Codex gets `web_search: "live"` in the config of its thread; the guidance tells the AI it has the tool, and the calls come back as ordinary tool events (`WebSearch`, and `web_search` for Codex). The flag is part of the process (`SameProcess`), so switching it restarts a kept process. Because the tool searches outside the library's server, the library does not see what it searches. Any other engine gets the library's `search_web` instead, which posts the query to `https://html.duckduckgo.com/html/` and reads the result anchors and snippets out of the page (the real address behind DuckDuckGo's redirect links, ads left out), formats at most 10 of them as a numbered list marked as untrusted web text, and is rate limited on the session clock: one request at a time, at least two seconds after the previous one (the call waits), and after a refusal (status 202, 403 or 429, or a challenge page) a minute in which calls fail at once with the time left, so a model that keeps retrying neither hammers the site nor waits for it.

Four tools need no switch and are built once per session: `current_time` (the clock the session runs on, so tests control it), `tool_search`, `delegate` and `diff_files`. `tool_search` ranks the tools the session serves at the moment it is called by their names (weighted) and descriptions and returns descriptions with input schemas; it does not hide any tool, so it helps only with the tools of this server (a deferred, search-first tool list would need the AI tool to accept a changing list, which the server does not offer). `diff_files` is built with the file tools over the same store, compares lines with a Myers difference algorithm (line endings ignored, 2000 changed lines at most, 40000 characters of output at most) and prints a unified diff. `delegate` runs the task in a helper session: a new session of the provider with the model, workspace path and API key of this one and the whole configuration copied (tools, instructions and the other settings), sharing the cache, or, with `share_context`, a fork of this conversation made while the turn runs. The fork holds the conversation up to the last finished turn (Claude Code reports its session id only when a turn ends, so a request in flight, and everything of a session's first request, is not in it), which is why the helper is also given the text of the request being worked on as part of its task. The helper is told the task came from another AI and to answer with the result only, is not persistent and cannot delegate (the tool is not served to it), at most three run at once, its usage is added to the session's when it ends, and it is disposed and deleted from the provider afterwards, also when it fails.

## Making images

`generate_image` is offered while the session has `ImageGeneration` options. The generator is made from the options by their type (`PromptImageOptionsExtensions.CreateGenerator`, which also validates them when they are assigned) and rebuilt when the options or the workspace change, since its schema depends on the generator. An OpenAI generator resolves its model lazily: at the first image it lists the image models the key can use and takes the newest one of the kind the capability means (`mini`, `flare` or `sunburst` in the name, a model that refuses transparency left out), and falls back to a fixed model of that kind when the service cannot be asked. It is built with a hand-written schema, not from a record, because only the arguments the generator's `Features` allow are listed (`transparent` for a generator with transparency, `negative_prompt` and `seed` for one with those), and the generator's `PromptGuide` is added to the description, since models describe images differently (Stable Diffusion 1.5 style models want comma separated phrases, GPT Image and FLUX-class models plain sentences). The call checks that none of the files it might write is there (the path with each image extension, and with the numbers when there are several) before it asks the generator for anything, so a taken path costs nothing, checks that every image made is a real image before it writes any, writes each with the extension its bytes say (PNG, JPEG, GIF or WebP) in create mode so nothing is replaced (a failure part way names the images already saved), makes the folders above it, and answers with each saved path, its size in bytes, KB or MB (so a small image never looks empty) and the seed when there is one.

The OpenAI generator posts to `/images/generations` and sends only fields that GPT Image models accept (no `response_format`): the size is `auto`, or the one of 1024x1024, 1536x1024 and 1024x1536 nearest the shape asked for, the quality is `low`, `medium` or `high`, and a transparent background adds `background: "transparent"` with PNG output. The API refuses that for `gpt-image-2`, so that model reports no `Transparency` feature and the tool does not offer it; the model listing (`GET /models`, keeping the GPT Image and ChatGPT Image names) takes its features from the same rule. The generator reads `b64_json`, which is what the GPT Image models return. The Stable Diffusion generator posts to `/sdapi/v1/txt2img` of an AUTOMATIC1111 or Forge server: width and height are rounded to a multiple of 8 between 64 and 2048, the quality picks the steps it was given, the count is the batch size, the seeds come from the `info` of the answer, a given checkpoint is loaded with `override_settings` and kept loaded afterwards (`override_settings_restore_afterwards` off) so that repeated images do not swap checkpoints back and forth, and a server that cannot be reached is reported with the advice to start it with its API on. Its model listing reads `/sdapi/v1/sd-models` and uses the title of each checkpoint (the name the API takes in `sd_model_checkpoint`) as the id, with the model name as the display name when it differs. Both read the message of an error answer and report it as the error of the tool (the OpenAI one with the API key left out where the service repeats it), and both limit the count to four.

## Lifetime

The session starts a server when a prompt is sent with offered tools, keeps it across prompts so the address and secret are stable (a persistent process keeps using it), replaces it when the offered tools change, and ends it when none are offered or the session is disposed. Replacing the server changes the endpoint, which is also what makes a persistent process restart. With no tools, no server and no port exist.

## Tools of one prompt and external servers

The tools of a session are served in one server that lasts across prompts; a request cannot add its own, so everything the AI can use is what the session holds when the prompt starts, plus the library's `respond` tool, which every session offers, and the `ask_user` tool, which is offered only while the session has an `Asker`. Both are built once per session and cached, because the served tools are compared by their handlers to decide whether the server (and a persistent process behind it) must restart; the `ask_user` handler reads the current `Asker` when it is called. The names of every library tool are reserved case-insensitively, and serving refuses a set of tools that repeats a name, so nothing the caller adds can shadow `respond` or `ask_user`. External MCP servers are not served by the library at all: they are passed to the AI's tool, which starts or reaches them itself, so the library only has their definitions.
